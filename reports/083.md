The best corporate design is to use Copilot for Microsoft 365 for work that requires native Purview content-aware DLP, while allowing ChatGPT Enterprise only through managed endpoint or browser enforcement paths plus Purview compliance logging.

ChatGPT Enterprise supports Purview governance, audit, classification, retention, eDiscovery, Communication Compliance, and Insider Risk workflows, but Microsoft marks Purview DLP as unsupported for ChatGPT Enterprise AI interactions. A Purview connector can ingest and govern ChatGPT Enterprise conversations, but its approximately 24-hour ingestion timing means it cannot block the original prompt or upload before disclosure.

For ChatGPT Enterprise, deploy Purview Endpoint DLP and preferably Edge Browser Data Security to block covered sensitive pastes, typed prompts, and file uploads before submission, then use OpenAI Enterprise controls and the Compliance API as complementary governance rather than as DLP. Prohibit or separately control unmanaged browsers, mobile and desktop clients, direct API use, personal accounts, and any route that does not traverse the chosen inspection point; a non-overridable block is the strongest true-DLP outcome, while an audited override is a deliberate exception path.[1][2][3]

## Native Purview DLP support

True Data Loss Prevention (DLP) is not a product label or an audit record. It is a **content-aware preventive control**: it identifies sensitive information and stops an inappropriate disclosure at the relevant sharing point. Here, that means before a user’s typed prompt, pasted text, or uploaded file reaches ChatGPT. This distinction matters because ChatGPT Enterprise can be governed and investigated through Microsoft Purview without Purview being able to stop the original submission.

**Control-surface map (20 November 2026).** The relevant control surfaces are: (1) Microsoft 365 source data, including its sensitivity labels and access rights; (2) the managed endpoint, browser, or routed network path through which a user copies, types, pastes, or uploads content; (3) the Microsoft 365 Copilot interaction, which has its own Purview DLP policy location; (4) the OpenAI-hosted ChatGPT Enterprise interaction, which Purview receives through a compliance-data connector; and (5) a separately built OpenAI API application, whose ChatGPT workspace and API Platform organization have separate memberships and permissions. Protecting a Microsoft 365 source, collecting an interaction after submission, and stopping a submission are different controls.[4][5][1][6]

Direct answer: ChatGPT Enterprise does not have native Microsoft Purview DLP for its AI interactions. Microsoft’s current Purview capability table marks Data loss prevention, sensitivity labels, and encryption without sensitivity labels as unsupported for ChatGPT Enterprise AI interactions. Purview can collect, classify, audit, retain, investigate, and review those interactions, but those are not an in-product, pre-submission Purview DLP decision point.[1]

### Scope and DLP test

Microsoft defines Data Loss Prevention (DLP) as the practice of helping prevent users from inappropriately sharing sensitive information with people who should not receive it. Its DLP engine uses deep content analysis rather than a simple text scan, including keywords, regular expressions, validation functions, proximity evidence, and machine-learning methods.[7]

For this comparison, use the following **Pre-submission Test**:

> A control counts as true DLP for ChatGPT use only if it can inspect relevant sensitive content in the actual prompt, paste, or upload path and block that sharing action before the content leaves the managed endpoint or reaches ChatGPT.

This is stricter than merely finding sensitive content later. OpenAI’s own description of DLP says DLP systems monitor, detect, and block sensitive data while in use, in motion, and at rest; a ChatGPT-focused DLP description similarly defines it as inspecting prompts or files and applying policy before submission.[8][9]

Microsoft Purview rules combine conditions—such as a sensitive information type (SIT), a pattern-based classifier for data such as a Social Security number, bank account number, or custom corporate identifier—with actions that determine the outcome. Those actions can include warning the user, blocking with an override and recorded justification, blocking without override, or taking protective action against stored data.[7][10][11]

The timing and action are decisive:

A block with override is still a preventive DLP control because the default state stops the transfer. It is weaker than a non-overridable block because the organization deliberately allows an exception route. An audit-only policy is not preventive because Microsoft expressly states that the user activity is allowed to occur.[12][10]

Judgment — DLP is path-specific, not a general property of an application or license. A company may accurately say that it has Purview DLP and still lack DLP for a particular ChatGPT Enterprise action if the actual route—desktop app, browser profile, mobile app, API, unmanaged device, personal account, connector, or direct network connection—does not pass through the inspection-and-blocking point.

Microsoft’s documentation supports this path-specific view. Endpoint DLP can detect attempts to paste into a restricted service domain in supported browsers; it can separately control protected-file uploads to configured cloud-service domains; and Purview Browser Data Security in Microsoft Edge can inspect text typed or pasted into AI prompts in real time and block submission before it leaves the browser. These are different control points with different coverage conditions.[15][3]

Content detection also has practical limits. Microsoft says encrypted files cannot be inspected for sensitive information types or trainable classifiers. High-confidence SIT matches generally produce fewer false positives but can produce more false negatives; low- and medium-confidence matches can catch more candidate content but create more false positives.[10][11] Microsoft further warns that the same SIT can produce different results in different workloads, so a custom SIT must be tested in each intended workload rather than assumed to work identically across Exchange, SharePoint, OneDrive, and Endpoint DLP.[11]

For paste controls specifically, Purview evaluates the clipboard content rather than the source file’s location. Paste to Browser supports SITs but not sensitivity labels or Advanced Classification; it does not evaluate text shorter than 30 characters, waits 2 seconds before allowing the paste, and classifies only the first 4 MB of clipboard text.[10][16] These are important limits, but they do not alter the central classification: when configured to block, this is preventive endpoint DLP for the covered paste route.

### Native Purview DLP status for ChatGPT Enterprise

Microsoft’s direct answer is clear. In the capability table for AI interactions with ChatGPT Enterprise, Microsoft marks sensitivity labels, encryption without sensitivity labels, and Data loss prevention as unsupported.[1]

That table is scoped specifically to the enterprise version of ChatGPT, not consumer ChatGPT. Microsoft separately directs readers seeking consumer ChatGPT controls to Network Data Security and Data Loss Prevention for Cloud Apps in Edge for Business documentation.[1][2] This product boundary is crucial: a browser or network control for OpenAI ChatGPT traffic is not the same thing as native Purview DLP inside the ChatGPT Enterprise interaction integration.

Microsoft does support a substantial set of Purview functions for ChatGPT Enterprise. The capability table lists DSPM and DSPM for AI, auditing, data classification, Insider Risk Management, Communication Compliance, eDiscovery, Data Lifecycle Management, and Compliance Manager as supported.[1] Those are valuable corporate governance capabilities, but none change the explicit DLP status from unsupported to supported.

The Purview–ChatGPT Enterprise integration is a **compliance-data integration**. OpenAI lists Microsoft Purview among third-party integrations for the Enterprise Compliance API, which gives workspace owners access to time-stamped records including conversations, uploaded files, workspace GPT configuration and metadata, memories, and workspace users.[23] OpenAI’s Compliance Platform provides workspace logs and metadata that customers can connect to eDiscovery, DLP, and SIEM tools.[8]

Microsoft describes the Purview connector as a way to register ChatGPT Enterprise workspaces as a data source so that Purview can discover and govern enterprise AI interactions.[2] The connector supports metadata extraction, full scans, incremental scans, and classification. It does not support scoped scans, labeling, access policy, lineage, data sharing, or live view.[2]

The connector’s scan levels range from level 1 technical metadata to level 3 sampling and classification where supported; the sampling and classification take place after collection, not before a ChatGPT Enterprise submission.[2][113][114][115]

The connector is deliberately retrospective. Microsoft states that, because of OpenAI API limitations, conversations are ingested **24 hours after they occur**.[2] A scan can start from the current date or a chosen prior date, and Microsoft recommends using incremental scans after the first scan to avoid duplicate ingestion.[2] A process that receives an interaction a day after it occurred can support detection, investigation, retention, and response; it cannot make a pre-send block decision for that interaction.

The connector documentation describes extraction of text prompts and text responses only; complete connector-extraction coverage should not be assumed for uploads, outputs, or routes outside the configured workspace.[115][2]

Microsoft’s July 18, 2024 announcement described an out-of-the-box Purview integration with the ChatGPT Enterprise Compliance API, then in private preview. Microsoft said it provided visibility into prompts and responses, user counts, and user-associated risk levels from Insider Risk Management.[32] Microsoft also said the integration would enable Purview Audit capture, retention policies for prompts and responses, Communication Compliance detection and mitigation of communication and safety risks, and eDiscovery preservation and collection.[32]

Those capabilities are useful, but they are distinct control types:

- **Audit and Activity Explorer:** Purview can capture prompts and responses in the unified audit log. Events can include how and when the user interacted with the AI app, the Microsoft 365 service involved, references to accessed Microsoft 365 files, and any sensitivity labels on those referenced files. Authorized Content Explorer Content Viewer role members can drill into AI activity details, including prompts and responses. [1]

- **Data classification:** Purview can apply SITs and trainable classifiers to find sensitive data in prompts and responses, surfacing results in Purview reports and Activity Explorer. [1]

- **Insider Risk Management:** Purview’s Risky AI usage template can detect risky activity such as prompt injection and access to protected materials, with signals integrated into Microsoft Defender XDR. [1]

- **Communication Compliance:** Purview can detect and manage communication or conduct violations in AI prompts and responses, including sharing sensitive information. Matching prompts and responses appear as policy matches for review, escalation, tagging, resolution, download, or export. [1][14]

- **eDiscovery and retention:** Purview can preserve, search, export, review, retain, or delete interaction records under legal and records-management processes. [1]

Microsoft Data Lifecycle Management can delete applicable compliance content under configured rules, including content not accessed for at least three years; it does not delete information already embedded in an AI conversation, copied elsewhere, or retained under another provider’s terms.[116]

None of these functions makes Purview a native inline enforcement point in the ChatGPT Enterprise prompt path. Microsoft’s own implementation sequence says to wait at least one day for data before viewing reports after configuring the ChatGPT Enterprise governance workflow.[1]

Microsoft Purview’s Data Security Posture Management (DSPM) for AI also supports collection policies that capture prompts and responses from Enterprise AI apps, explicitly including ChatGPT Enterprise, so that the material can be managed in Purview solutions such as eDiscovery and Data Lifecycle Management.[19] Again, capture for compliance management is not pre-submission blocking.

The older classic DSPM for AI documentation makes the distinction particularly clear. Microsoft described registering ChatGPT Enterprise workspaces to detect sensitive information shared with ChatGPT Enterprise and identify exposure risks.[33] It also called the related one-click policy a mechanism to capture prompts and responses for regulatory compliance from Entra-registered AI apps, the ChatGPT Enterprise Connector, and Microsoft Foundry applications.[33] Detection and capture occur after the information has been shared.

The connector has operational prerequisites:

1. **First**, establish the connector prerequisites: an active Azure subscription, an active Enterprise Microsoft Purview account, the Data Source Administrator and Data Reader Microsoft Purview Data Governance classic permissions, and a ChatGPT Enterprise plan. Then enable pay-as-you-go billing, which Microsoft requires for managing ChatGPT Enterprise interactions through Purview; scans are subject to the Purview billing model. [2][1]

For source registration and management, the required Purview Data Governance classic permissions include Data Source Administrator and Data Reader.[115]

2. **Second**, create a collection policy allowing ingestion of prompts and responses. [2]

3. **Third**, obtain and secure the required OpenAI Compliance API authority. Microsoft describes Purview using OAuth 2.0 with an API-key credential mapped to Azure Key Vault. The same setup guidance says that required Compliance API scopes must be granted by OpenAI after a support request. [2]

The OpenAI API key needs at least Compliance API read scope; that scope is not selected when the key is created in the OpenAI API Platform Portal, and the documented process is to request read or delete scope from OpenAI support using the key identifiers.[115][117][118]

Key Vault setup can require administrator and secret-user role assignments, storage of the key’s correct version, and association of the vault through Purview Data Map credential management. If public vault access is disabled, the documented alternatives are to allow trusted Microsoft services including Purview or use a private endpoint and integration runtime.[113][115]

4. **Fourth**, run the connector scan before Purview can manage the interactions, then use incremental scans operationally. [1][2]

Registering the source in Purview Data Map requires a catalog name, workspace ID, domain, and collection; source registration and scan configuration are separate activities.[115]

The connector setup includes a Test connection step before the initial or full scan.[2][113][114][115]

5. **Fifth**, assign access to collected content carefully. OpenAI says only a workspace owner can grant broad compliance access or Conversation messages permission; a workspace owner or admin can grant access to supported individual log categories. [8]

Because collected employee prompts can form a sensitive compliance dataset, deployment requires privacy, legal, works-council, records-management, and employee-monitoring approval, with restricted access and defined retention and investigation procedures.[1][119]

This produces governed evidence and a central compliance record. It does not place a Purview classifier or block action inside the ChatGPT Enterprise composer, upload handler, model-routing flow, or OpenAI API request path.

On December 11, 2025, OpenAI announced that the ChatGPT Compliance API became part of the OpenAI Compliance Logs Platform. The platform exports observability and compliance data in immutable, time-windowed JSONL log files, with minutes-level latency and one ingestion pattern across multiple log categories; it is not a synchronous request-interception service.[23] OpenAI describes the platform as append-only compliance log events for auditing and the Stateful Compliance API as an audit-oriented query interface for state and legacy data types.[8] The Compliance Logs Platform retains data for 30 days, so organizations requiring longer retention must continuously download and retain the data under their own policies.[8]

OpenAI says its Compliance API cannot delete data logged internally for OpenAI audit or security purposes and that data is retained internally for no more than 30 days after a deletion request.[8] This is another reason not to characterize the API as an in-line DLP service: it is an evidence and governance interface, not a transaction gate.

OpenAI’s enterprise data-use commitment is also important but separate. OpenAI states that it does not use content submitted to business offerings, including ChatGPT Enterprise, to improve model performance.[34] That limits one downstream use of submitted content.

It does not decide whether an employee is permitted to submit the content in the first place, inspect it against a Purview policy, or block it before transfer.

Sensitivity labels do not change this result for ChatGPT Enterprise interactions. Microsoft labels classify and protect information, and labels that apply encryption can control who accesses content and what they can do with it.[35] But labels must be understood at the enforcement point.

A labeled or encrypted file may protect itself when an application honors Microsoft Purview Information Protection; it does not mean Purview automatically inspects all text typed into ChatGPT Enterprise or blocks every submission involving content that originated in a labeled file.[35][36]

ChatGPT Enterprise does have some Purview-related connector settings. OpenAI says workspace administrators can configure Microsoft Purview sensitivity labels in SharePoint app settings, and Teams sync can use an optional Microsoft Purview sensitivity-label filter when selecting Teams content to include.[24][37] OpenAI’s current Safety & Security Controls can allow or block supported SharePoint site collections and exclude selected sensitivity labels; they can exclude Outlook messages with selected sensitivity-label GUIDs; and they can control Teams by Microsoft 365 group IDs and selected team sensitivity labels.[38]

Those controls regulate what ChatGPT can retrieve through particular connected Microsoft apps. They are meaningful source-data minimization controls. They are not general Purview DLP for user-entered prompts, attachments, ordinary conversations, or every connector path. In particular, the Outlook setting does not independently inspect labels inside attachments, and Teams team rules do not cover ordinary one-to-one, group, or meeting chats.[38]

**What follows:** use the Purview connector for evidence, compliance, retention, and investigation of ChatGPT Enterprise use; do not represent it to management, auditors, or users as a native Purview DLP control that blocks sensitive prompts or uploads before ChatGPT receives them.

### Adjacent Purview enforcement paths

The fact that ChatGPT Enterprise lacks native Purview DLP does not mean Purview cannot prevent any sensitive data from reaching ChatGPT. It means prevention occurs only through a separately deployed **endpoint, browser, or network enforcement path**. This is adjacent or indirect DLP, not DLP delivered by the ChatGPT Enterprise connector.

Microsoft lists OpenAI ChatGPT for Edge for Business and Network options under its inline DLP coverage.[7] Microsoft separately lists DLP as supported for browser interactions with third-party AI sites such as ChatGPT, Google Gemini, and DeepSeek.[22] At the same time, Microsoft says unmanaged cloud app features apply to the consumer versions of ChatGPT and Microsoft 365 Copilot, while enterprise versions have their own Purview feature documentation.[21] Read together, these statements support a precise conclusion: the inline traffic paths can be preventive where deployed and supported, but they do not contradict the explicit unsupported status of native DLP for ChatGPT Enterprise AI interactions.

Cloud-app browser DLP works directly in Edge for Business in the two latest stable versions beginning with Edge version 144.[41][21] The documented action to audit or restrict activities when users access sensitive sites in Edge is specifically a Windows-device action in the illustrated setup.[41]

Microsoft Edge for Business provides a more direct inline path for some cloud-app activities. Microsoft says Purview DLP monitoring and protection are built into Edge for Business; unmanaged-app policies apply to Intune-managed Windows 10 and Windows 11 devices.[21] For upload text to unmanaged apps on managed devices, the documented actions are allow or block, and both actions are audited. Upload-file actions are also allow or block.[21]

Microsoft Edge can also restrict upload, download, copy/paste, and print involving unmanaged BYOD devices.[122]

This has material capacity limits. Microsoft evaluates up to 4 MB of upload-text content and files up to 3 MB for upload-file inline evaluation.[21] Some unmanaged AI apps, including ChatGPT, may intermittently send content encoded or through dynamically generated endpoints, which can affect policy enforcement.[21] Detection for unmanaged-app browser policies is based on destination-app traffic, which Microsoft says may not exactly match the originating app.[21]

DSPM for AI one-click recommendations can create policies that block, or allow an override when elevated-risk users paste or upload sensitive information in Edge, Chrome, and Firefox. They can also block Edge prompts based on user risk or selected sensitive information types.[22]

The unmanaged-app Edge route has deployment and bypass controls. Policies apply across Edge work, personal, and InPrivate profiles on managed devices; if configured to block, in-scope users cannot use unprotected browsers where the policy does not apply.[21] However, Microsoft says Purview browser and network data security policies do not apply to B2B guest users.[21] On unmanaged devices, Edge for Business DLP policies apply only to the work profile, not personal or InPrivate profiles unless the work profile that opens the InPrivate window has a policy.[42]

Administrators need the right permissions for Edge automatic configuration. When an organization saves its first unmanaged-app Purview DLP or collection policy, the Edge management service creates required policies and configurations outside Purview. Microsoft lists Directory Reader, Microsoft Edge administration, and Microsoft Intune administration permissions as required to fully activate the policies.[21] If the automatic synchronization fails, Purview does not enforce the DLP or collection policy for unmanaged apps in Edge until an authorized administrator resolves the issue and resynchronizes.[21]

Managed-app browser protection is a separate architecture. Microsoft describes managed apps as business apps set up for Microsoft Entra SSO, accessed in the Edge for Business work profile using work or school credentials.[21] The setup requires app onboarding to Conditional Access app control, importing user groups, creating an Entra Conditional Access policy with custom session controls, enabling Edge in-browser protection, and creating a Purview DLP policy for managed-app interactions.[21][42] Both the user and app must be in scope, and Microsoft says the policy will not apply until all prerequisites are met.[42]

This may be relevant only if the organization can onboard the actual ChatGPT Enterprise access pattern as a qualifying managed app. It should not be assumed merely because users authenticate to ChatGPT with corporate SSO. Microsoft’s documentation establishes the managed-app mechanism generally; it does not say ChatGPT Enterprise is automatically onboarded or automatically protected through it.[21]

Policy interactions can also produce unexpected outcomes. Microsoft says managed-app browser protections might not apply when a user is simultaneously in scope for a Purview managed-cloud-app DLP policy and a Defender session policy or Purview Endpoint DLP policy. Enforcement can also wait for an existing app token to expire and for the user to sign in again.[21] Where Endpoint DLP and inline DLP for cloud apps in Edge for Business cover the same user, context, and action, Endpoint DLP takes priority.[21]

Network Data Security broadens visibility but should not be described as a guaranteed universal blocking layer. Microsoft says it can detect sensitive data shared with cloud apps through non-Microsoft browsers, applications, APIs, add-ins, and other channels, extending DLP protection beyond Edge to network-level traffic.[3] Microsoft also says that a SASE or Security Service Edge (SSE) integration can analyze prompts and responses at the network layer.[22] For DSPM for AI, Microsoft says detection of AI interactions depends on the network partner’s implementation, and prompt/response capture requires an explicit content-capture configuration.[19]

Optional full-content capture through Purview Network Data Security sends the complete AI conversation to Purview, creating privacy, records-management, and restricted-access obligations for captured prompts and responses.[39]

Judgment — A Network Data Security DLP policy configured with the Block action is true DLP for a supported, routed ChatGPT interaction because Microsoft documents real-time policy communication and blocking of sensitive content before the sharing action completes. A collection policy alone is monitoring because its communication is asynchronous.[39]

Purview Network Data Security documents Audit only and Block actions, with supported activities and actions varying by integrated SASE or secure-browser service. Microsoft Entra Global Secure Access supports all four listed activity directions—text sent, files uploaded, text received, and files downloaded—and both actions.[39]

Purview supports network and browser policy structures that can apply blocks in covered scenarios. Managed cloud apps can use Audit only or Block for browser and network activities on Windows and macOS. Unmanaged cloud apps can use Audit only or Block for browser and network activities on Windows.[10] However, the fact that a generic location exists does not prove every ChatGPT Enterprise client route is inspected or blocked. The organization must test its actual enterprise workspace, browser, desktop application, mobile application, API, and network egress paths.

Network Data Security policies can target applications through the Defender for Cloud Apps cloud-app catalog or adaptive scopes such as generative AI. Microsoft illustrates an All unmanaged AI apps adaptive scope applied to a Finance department group.[39][121]

For browser-path prevention, configure the control deliberately:

1. **First**, identify the approved ChatGPT Enterprise domains and clients, including whether the organization permits browser-only use, desktop apps, mobile apps, API calls, Voice, connected apps, or agent browsing. ChatGPT Voice uses UDP port 3478, with TCP 443 as an alternative if UDP is blocked, so a browser-only DLP design does not automatically govern voice-related network paths. [43]

2. **Second**, onboard supported managed endpoints and confirm that both users and devices are in Purview policy scope. [15]

3. **Third**, define SITs and, where applicable, sensitivity labels that represent regulated data, credentials, source code, customer identifiers, financial data, and other protected corporate information. Microsoft provides preconfigured SITs and supports custom SITs built with regular expressions, keywords, keyword dictionaries, Exact Data Match, and PowerShell. [11]

4. **Fourth**, configure separate actions for clipboard copying, browser pasting, and file upload. Do not assume a restricted cloud-service-domain setting also controls paste. [15][16]

5. **Fifth**, apply an audit-only or simulation policy to a pilot group, test synthetic prompts and files in each approved access route, tune SIT confidence and exceptions, then move to Block or Block with override only where the test proves the sharing action is stopped. Microsoft recommends incremental deployment through simulation, policy-tip pilot, tuning, and enforcement. [7][12]

6. **Sixth**, inspect Activity Explorer, audit data, alerts, user feedback, and endpoint evidence after each test. Microsoft says DLP-monitored activities flow to the Microsoft 365 Audit log and Activity Explorer, which provides the most recent 30 days of DLP information through preconfigured filters. [7]

Endpoint DLP also has direct coverage limitations. It cannot scan or classify data that is never saved to a local file, which limits file-based inspection scenarios.[15] In Azure Virtual Desktop, Microsoft says Endpoint DLP cannot monitor Copy to Clipboard or enforce browser-based Endpoint DLP. On offline Windows endpoints, existing policies continue to apply, but policy updates are not synchronized or enforced until the device reconnects; Microsoft says the relevant just-in-time protection behavior is not supported on macOS.[40][15]

**What follows:** Purview can provide preventive enforcement for documented, covered ChatGPT web paste, upload, and browser activities when the deployed Enterprise browser and account route passes a blocking test; this remains a deployment-specific egress control rather than native ChatGPT Enterprise DLP. It preserves ChatGPT Enterprise use only to the extent that the organization can force and validate those paths; it does not create a native Purview DLP policy location inside ChatGPT Enterprise.[1][4][21]

The restricted-cloud-service-domain upload list supports 50 domains, whereas sensitive website groups can represent up to 15,000 websites; the former is 0.333% of the latter configuration scale.[16]

### trade-offs

A corporate program should implement the ChatGPT Enterprise–Purview connector because auditability, retention, investigation, and compliance evidence remain important. It should implement endpoint, browser, or network prevention separately where ChatGPT Enterprise use is permitted. These are complementary layers, not substitutes.

**Implementation: establish governance first**

1. **First, map permitted data flows.** Inventory ChatGPT Enterprise web access, desktop and mobile clients, personal versus corporate account use, API use, Voice, files, connected apps, custom GPT actions, agent browsing, and any external browser or native-app capabilities. OpenAI’s Work Local guidance explicitly says organizations should apply endpoint, file-access, proxy, and DLP controls to the specific device and workflow, then confirm that those controls stop sensitive information before processing. [25]

2. **Second, set the DLP standard.** Define which SITs, custom classifiers, sensitivity labels, users, device groups, domains, applications, and exception processes apply. Purview policy construction requires choosing what to monitor, administrative scope, monitored locations, match conditions, and actions. [7]

3. **Third, use least-privilege administration.** Microsoft lists Compliance administrator, Compliance data administrator, Information Protection, Information Protection Admin, and Security administrator as eligible roles to create and deploy DLP policies. Microsoft also provides granular DLP Compliance Management, Information Protection Analyst, Information Protection Investigator, and Information Protection Reader roles. [12]

Purview portal role-based access does not grant every permission needed in connected services; those service permissions must be administered separately.[119][123]

4. **Fourth, activate Purview governance for ChatGPT Enterprise.** Enable pay-as-you-go billing, create the required collection policy, configure Azure Key Vault-backed credentials, obtain required OpenAI Compliance API scopes, register the workspace, run the initial scan, and operate incremental scans. [1][2]

5. **Fifth, protect the compliance-data path.** OpenAI says a workspace-scoped Admin key should have only required permissions and that Conversation messages permission needs workspace-owner authorization. Download compliance logs continuously if the organization requires retention beyond the platform’s 30-day period. [8]

Operating the connector also entails key rotation and protection, Key Vault administration, collection-policy upkeep, permissions management, and scan monitoring; its read-capable credential and vault are high-value assets.[1][115][117][119]

6. **Sixth, configure Purview records management and investigations.** Create retention policies for Enterprise AI apps, define eDiscovery procedures, scope Communication Compliance reviewers, and route relevant DLP and Insider Risk alerts to the right response teams. Purview’s retention configuration for ChatGPT Enterprise interactions uses the Enterprise AI apps location. [1]

Implementation: deploy pre-submission prevention for permitted ChatGPT use

1. **First, choose the enforcement path by client.** Use Edge Browser Data Security or Endpoint DLP for managed-browser prompts and paste actions; use Endpoint DLP service-domain controls for protected-file uploads; use an SSE/SASE or secure web gateway only where the traffic is actually routed through it and its inspection can enforce a synchronous block. [3][15][19]

2. **Second, force use of managed clients where feasible.** Configure Edge for Business policies and restrict unprotected browsers for users who require access to unmanaged AI applications. Microsoft recommends configuring DLP for Edge and blocking other browsers to prevent use of unmanaged AI apps in unprotected browsers. [21][44]

3. **Third, configure domain and activity controls separately.** Create sensitive service domain groups for paste and sensitive-site activities; configure restricted cloud service domains for uploads; add the actual approved ChatGPT domains and any required subdomains; and test URL versus IP matching behavior. [16][41]

4. **Fourth, start in simulation.** Microsoft states that simulation mode does not enforce actions, although it can generate audit data and policy tips. Test with synthetic sensitive text, labeled documents, encrypted documents, files over and under applicable size limits, Chrome/Firefox extension scenarios, Edge work/personal/InPrivate profiles, and corporate versus personal ChatGPT accounts. [12][21][45]

5. **Fifth, tune before blocking.** Review false positives in Activity Explorer, adjust SIT confidence, remove irrelevant SITs, define override conditions only where business need justifies them, and retain evidence of every approved exception. Microsoft recommends simulation, pilot feedback, tuning, and then enforcement. [12][11][3]

6. **Sixth, turn on blocking only after an observed block.** A successful test must demonstrate that the matching prompt, paste, or upload was stopped before reaching ChatGPT, not merely that an alert later appeared in Purview. This is the Pre-submission Test applied operationally. [12][10][3]

ChatGPT Enterprise administration reduces exposure but does not replace DLP. Workspace owners can restrict GPT actions to approved domains, manage GPT sharing, inspect configurations, remove GPTs, transfer ownership, set global GPT capabilities, and use group permissions or third-party GPT controls.[23] Enterprise apps and connectors are disabled by default, and administrators can govern availability, RBAC access, synchronization, and permitted actions.[24]

Administrators should use these controls to limit sources and capabilities:

- **Connected apps and connectors:** Enable only required apps, restrict access by role, and permit only required actions. OpenAI says new custom connector actions are disabled by default until approved. [24]

- **External actions:** Use approved domain lists for GPT actions and restrict browser/agent destinations. OpenAI supports workspace allowlists for GPT action domains and allows owners to request blocks for websites or domains in agent browsing and actions. [23][24]

- **Share and library controls:** Disable unnecessary share links and Library sharing. OpenAI notes that disabling Library sharing prevents future shares and permission changes but does not revoke existing shared content. [24][37]

- **Network access:** Use ChatGPT Enterprise IP allowlisting to limit workspace and Compliance API access to approved source IP addresses. This does not apply to the OpenAI API Platform. [24]

- **Corporate workspace enforcement:** Use OpenAI’s `ChatGPT-Allowed-Workspace-Id` HTTP header through the network configuration to allow only specified ChatGPT workspaces. OpenAI says a SASE partner can enforce this at the network level; organizations must separately block anonymous access under `https://chatgpt.com/backend-anon/`. [46]

These controls are useful because they reduce accidental use of personal workspaces, anonymous ChatGPT, unauthorized connectors, unreviewed GPT actions, and unapproved data sources. They do not scan the text of an allowed prompt for a sensitive information type and block it. In other words, they are access and capability governance rather than content-aware DLP.

Certificate pinning is a material trade-off for proxy or TLS-inspection designs. OpenAI says ChatGPT desktop and mobile applications use certificate pinning, and organizations that enable SSL inspection for the documented network controls need to add their certificates to the pin list and distribute them through MDM. Cato similarly documents that trusted root deployment is insufficient by itself: the organization must deploy the ChatGPT app’s certificate-pinning exception, ensure TLS inspection is enabled, and ensure no bypass rule matches the traffic.[46][47]

The relevant operational lesson is simple: a successful ChatGPT desktop-app sign-in does not prove that the proxy inspected the traffic. Cato’s documentation instructs customers to verify the TLS Inspection event field, where `1` means inspected and `0` means bypassed.[47] This is the kind of deployment-specific evidence required before claiming a proxy-based control meets the Pre-submission Test.

Judgment — Treat every prevention claim as a test case, not an architectural assumption. For each approved ChatGPT Enterprise client and route, use a synthetic sensitive prompt and file; verify the user-visible block, verify that ChatGPT did not receive the content, and verify the audit evidence. A policy that blocks browser paste but not desktop application upload is not a failed DLP program; it is a program with a documented residual route that must be closed, prohibited, or accepted.

### known limitations

Microsoft’s documentation creates an apparent contradiction only if different control surfaces are conflated. Microsoft lists OpenAI ChatGPT for Edge for Business and Network inline options and supports DLP for browser interactions with third-party AI sites.[7][22] Microsoft also explicitly marks DLP unsupported for ChatGPT Enterprise AI interactions.[1] The documented distinction is between **traffic mediated by a Purview-controlled endpoint, browser, or network path** and **the ChatGPT Enterprise connector-based interaction integration**.

The closest direct statement of this boundary is Microsoft’s description of ChatGPT Enterprise as an Enterprise AI app and ChatGPT discovered through browser activity as an Other AI app.[4] The Enterprise AI app category supports connector-based management and governance.

The browser-detected category supports browser and endpoint-oriented controls. Those categories can coexist in one organization, but they do not mean the ChatGPT Enterprise connector itself becomes a DLP enforcement engine.

A company should therefore avoid four inaccurate statements:

- Purview captures ChatGPT Enterprise prompts, therefore Purview blocks them. This is false because capture, classification, audit, and compliance review happen in a governance flow, while DLP is explicitly unsupported for ChatGPT Enterprise interactions. [1][2]

- ChatGPT Enterprise does not train on submitted business content, therefore sensitive content may be submitted without restriction. This is false because OpenAI’s no-training commitment is a model-improvement data-use control, not a corporate disclosure policy. [34]

- Purview DLP works with ChatGPT, therefore it natively governs ChatGPT Enterprise. This is false because Microsoft separates browser/network DLP for third-party or unmanaged AI traffic from the ChatGPT Enterprise capability table. [7][1][21]

- A CASB, proxy, or SSE sees ChatGPT traffic, therefore it blocks sensitive prompts. This is false unless the deployed product and client route perform content inspection and enforce a block before submission. Microsoft’s network integration documentation describes detection and makes interaction detection dependent on the network partner’s implementation. [3][19]

There are also residual technical routes that must be explicitly governed. Endpoint and browser policies do not automatically cover unmanaged devices, unsupported browsers, B2B guests, non-enrolled virtual desktop browser sessions, mobile applications, desktop applications with unconfigured certificate-pinning exceptions, APIs, and traffic that does not traverse the chosen proxy or SSE. ChatGPT Enterprise IP allowlisting does not apply to the OpenAI API Platform, which has separate membership and permission boundaries from ChatGPT workspaces.[21][40][46][3][24][6]

The verdict changes only under two conditions. First, it would change if Microsoft and OpenAI document and validate a direct ChatGPT Enterprise Purview DLP policy location that synchronously inspects prompts and uploads and blocks them before OpenAI receives them. Second, it changes operationally if the business can replace the ChatGPT workflow with a Microsoft 365 Copilot workflow; that alternative is addressed in the next section, where Purview has a dedicated Copilot policy location for restricting prompt processing.[5][51]

**What follows:** for ChatGPT Enterprise, do not buy or configure the Purview connector on the premise that it supplies native DLP. Buy and configure it for compliance governance, then separately prove preventive enforcement on every allowed client and egress route.

For Edge inline controls, the upload-text inspection ceiling is 4 MB, which is 33.3% larger than the 3 MB upload-file ceiling; test plans therefore need distinct maximum-size cases for text and file submissions.[21]

For Network Data Security, the documented maximum interval from integration until first policy/data distribution (24 hours) plus a request appearing in audit evidence (up to 30 minutes) is 24.5 hours. This separates enforcement-time behavior from the later availability of operational audit evidence.[39]

ChatGPT Enterprise has a real Microsoft Purview integration, but it is a compliance-data integration rather than native Purview DLP. Purview can collect, classify, audit, retain, search, investigate, and review ChatGPT Enterprise interactions after collection; Microsoft explicitly marks DLP, sensitivity labels, and encryption unsupported for those interactions, and conversation ingestion is documented as occurring 24 hours after the conversation.[1][2]

Microsoft documents blocking for specified ChatGPT web paste, upload-text, and upload-file actions on covered managed paths, while its ChatGPT Enterprise interaction capability table marks native DLP unsupported; the organization must test the actual ChatGPT Enterprise browser and account combination before treating the route as preventive DLP. Those controls qualify only when they inspect the actual sensitive paste, prompt, or upload and block it before submission.[1][4][22][21] Their coverage is bounded by client, operating system, browser, extension, policy scope, encrypted-content handling, content size, account context, and routed traffic.[10][3][21][19]

The correct corporate position is therefore: **use Purview governance for ChatGPT Enterprise, but require separately tested in-path prevention for any ChatGPT route approved for sensitive work.**

## Copilot for Microsoft 365 as an alternative

Microsoft 365 Copilot is not a Purview control added to ChatGPT Enterprise. It is an alternative AI interaction surface: Copilot works inside the Microsoft 365 service boundary, is integrated with Word, Excel, PowerPoint, Outlook, Teams, and other Microsoft 365 services, and uses Microsoft Graph and Work IQ to ground responses in the signed-in user’s work context.[52][53][54][55]

**For Microsoft 365-centric work, replacing ChatGPT Enterprise interactions with licensed Microsoft 365 Copilot provides the strongest Purview-aligned preventive control surface.** Purview can apply DLP policies directly to covered Copilot interactions, including rules that restrict Copilot from processing or answering a typed prompt matching a configured sensitive information type (SIT), and rules that prevent Copilot from processing selected labeled files and emails for grounding or summarization.[5][56] That is a product substitution, not an integration: Purview protections configured for Copilot do not thereby govern a separate ChatGPT Enterprise conversation.[5][57]

### concrete implementation steps

First, decide which work should move to Microsoft 365 Copilot. Microsoft 365 Copilot Premium is the relevant licensed experience when users need automatic reasoning over Microsoft 365 work data. It can automatically use organizational and web data through Microsoft Graph and Work IQ; Copilot Chat Basic and Microsoft 365 Copilot Basic cannot use organizational data through Microsoft Graph in a chat interaction unless the user uploads a file, has content open in Teams or Outlook, or uses an authorized pay-as-you-go agent.[55][58] Microsoft 365 Copilot is available with Microsoft 365 E7 or as an add-on for eligible commercial, government, and education plans.[17][54]

Second, establish the content-access baseline before enabling broad Copilot use. Copilot runs prompts in the initiating user’s security context and returns organizational content only where the user already has permission; for encrypted content, the user also needs both VIEW and EXTRACT rights for Copilot to summarize or return it.[5][53][57] For unopened SharePoint and OneDrive documents labeled and encrypted with user-defined permissions, Copilot and agents cannot access the documents, except where a default sensitivity label extends SharePoint permissions to downloaded documents or a user directly references the document by typing `/`; both exceptions require EXTRACT rights.

For encrypted content, VIEW permission without EXTRACT permission may allow Copilot to return only a link rather than a summary.[35][52]

Copilot can use those documents when they are open in the app, and label inheritance is unsupported for content encrypted with user-defined permissions. Copilot and agents cannot access Double Key Encryption (DKE)-protected content; if a DKE-protected item is open, Copilot is unavailable in the app.[57] Review SharePoint and OneDrive permissions, remediate oversharing, use Restricted Content Discovery for sites that should not appear in Copilot or organization-wide search, and use restricted-access controls, site access reviews, and inactive-site policies where appropriate. Fix overshared sites and folders, apply sensitivity labels and retention, and disable inappropriate anyone links.[52][57][59]

SharePoint Advanced Management reports can show permission snapshots, sensitivity-label distribution, sharing-link activity over the prior 28 days, and which sites a user can access and how access was granted.[124]

The default SharePoint data-risk assessment runs weekly for the top 100 sites by organizational usage; its first results appear after four days, and custom assessments take at least 48 hours.[116][125]

Microsoft Entra Conditional Access authentication contexts can be applied to high-risk repositories alongside SharePoint restricted-access controls.[124][125]

Third, deploy and test Purview sensitivity labels. A sensitivity label is a classification and protection marker applied to information, such as Public, Confidential, or Highly Confidential. Microsoft 365 Copilot, Microsoft 365 Copilot Chat, and Copilot agents recognize and use the organizational sensitivity labels applied to protect data. A Purview DLP policy can prevent Microsoft 365 Copilot and agents from summarizing data with sensitivity labels selected by the organization, and can restrict Copilot from using selected labeled files and Exchange emails for response summarization or prompt grounding.[35][33][5] Where Copilot creates supported new content from labeled source material, the highest-priority source label can be inherited; users can replace or remove inherited labels unless mandatory labeling is configured.[49][52]

Where conversation-label inheritance is supported, Copilot selects the highest-priority sensitivity label from referenced content and applies that label’s protection policies to the conversation.[35][126]

Sensitivity labels on containers—including Teams, SharePoint sites, Microsoft 365 Groups, Loop workspaces, and Viva Engage—are not inherited by the items they contain.[127]

Fourth, create separate Custom-template Purview DLP policies for the Copilot location. The Microsoft Copilot, Copilot Chat, and Copilot Cowork location is available only through the Custom policy template, and selecting it disables other locations in that same policy.[5] For sensitive-information-type (SIT) prompt protection, configure **Content contains > Sensitive information types** and select **Restrict Copilot from processing content > Processing prompts**.

SITs are Purview detectors for regulated or organization-defined patterns, such as credit-card numbers, passport numbers, or custom identifiers. The prompt-processing feature is in preview, is rolling out to tenants with access to Microsoft 365 Copilot and Copilot Chat, and currently supports only out-of-the-box and custom SITs. With the Processing prompts action, Microsoft documents that Copilot does not respond to a matching typed prompt and does not use that prompt for internal or external web searches.[18][5][56]

Fifth, create a separate label-based rule for source-content protection. A single Copilot DLP rule cannot combine the conditions Content contains sensitive information types and Content contains sensitivity labels, although separate rules may coexist in one policy.[5][60] Configure the label rule to prevent Copilot from processing selected labeled files and Exchange emails.

Also consider the distinct web-search action: **Prevent Copilot from processing content > Performing Web Searches** blocks external web search for a matching SIT prompt but still permits a response grounded in allowed internal Microsoft 365 data.[5]

Sixth, begin in simulation mode, analyze matches, then move tested rules to enforce mode. Simulation logs events without blocking prompt processing; enforce mode is required to block processing. Purview supports DLP alerts, notifications, and policy simulation for Microsoft 365 Copilot and Cowork, but policy changes can take up to four hours to appear in the Copilot experiences.[5][61] Microsoft recommends checking that Purview Audit is active, using DSPM for AI to assess oversharing and Copilot activity, waiting at least one day for policy-report data, and assigning the Content Explorer Content Viewer role only to personnel who need to view prompt and response details.[49]

Copilot DLP monitoring can surface `DLPEvaluationDeferred` reasons, including timeout, authentication error, and service unavailability.[128]

These steps create a layered Copilot control plane: permissions restrict what Copilot may retrieve, labels and encryption restrict sensitive source content, and the Processing prompts DLP action prevents the covered Copilot experience from processing or answering a matching typed prompt.[5][56]

Seventh, review the tenant’s default Microsoft 365 Copilot DLP policy, which Microsoft provides to restrict Copilot and agents from using sensitive information in Copilot interactions, and tailor or replace it with the organization’s approved SITs, sensitivity labels, user/group scope, and exceptions. A DLP policy for this location is scoped to the user who submits the prompt, rather than to the owner of a file or email accessed by Copilot.[62][18]

Eighth, where external email must not become Copilot grounding, create a separate rule using **Email is received from > External users** and **Prevent Copilot from processing content**. This preview control compares the sender domain with tenant accepted domains; it applies to Microsoft 365 Copilot and Copilot Chat, including email summarization and reasoning, but not Cowork.[18][5]

Ninth, delegate policy administration to the least-privileged supported role: Microsoft Entra AI Admin, Purview Data Security AI Admin, Purview Compliance Administrator, or Microsoft Entra Global Admin. Microsoft recommends minimizing Global Administrator assignments. Where available, use administrative-unit scoping to delegate regional or departmental policy management for the users in that unit.[18]

Tenth, configure the organization’s destination page for the **Learn about access restrictions** link in the standard block message for Microsoft Copilot and Copilot Chat, so blocked users receive the approved handling instructions. The link changes only its destination; it does not change the standard block text or the enforcement action.[62]

Before production rollout, test representative sensitive prompt text, labeled files, and direct file uploads in each intended Copilot experience. Document which cases block, which are merely excluded from grounding, and which remain outside the rule’s inspection scope.

For Microsoft 365 Copilot Chat on the web, deploy Endpoint DLP alongside the Copilot-location DLP policy. ### trade-offs

Copilot’s principal advantage is governance alignment with Microsoft 365. Copilot uses the same Microsoft 365 data-protection, access-control, and compliance capabilities that already apply within the tenant. Purview can audit Copilot interactions, retain their records, search them through eDiscovery, and use Communication Compliance to detect risky or inappropriate activity. Copilot interaction records include the user’s prompt, Copilot’s response, and citations to information used to ground the response; Microsoft processes and stores those records in alignment with the organization’s contractual commitments for other Microsoft 365 content.[52][51][53] Prompts and responses are stored in a hidden folder in the user’s Exchange Online mailbox; uploaded Copilot Chat files are stored in the user’s OneDrive.[57]

When enabled, Audit Standard records Copilot and AI activity; Audit Premium can retain relevant activity for up to one year for appropriately licensed users, with longer retention requiring applicable add-ons.[128][129][130][49]

This is materially more than post-event monitoring. For typed prompts that match configured SITs, the Processing prompts action is preventive in the documented Copilot interaction: Copilot does not respond to the prompt or use it for internal or external web searches.[5][56] For labeled source items, the DLP control can prevent the content from being used in a Copilot summary or as grounding.[5][56] By contrast, Audit, retention, eDiscovery, DSPM for AI reporting, and Communication Compliance provide visibility, investigation, preservation, or remediation after activity has occurred; they are governance controls, not prompt-submission blocks.[53][14]

The trade-off is functional scope. Microsoft 365 Copilot is designed for work conducted in the Microsoft 365 stack, while ChatGPT Enterprise can remain useful for general-purpose work and workflows involving non-Microsoft tools. Copilot can call third-party tools and services through Microsoft Graph connectors or agents, but those agents may receive a query generated from the user’s prompt, activity history, and accessible Microsoft 365 data.[53] Therefore, third-party connectors and agents need their own data-flow review; Copilot’s Microsoft 365 protections should not be assumed to make every external agent path equivalent to an in-tenant Copilot interaction.

**The decision criterion is workflow fit: use licensed Microsoft 365 Copilot as the primary AI service where the business need is work over Microsoft 365 data and Purview-enforced prevention is required; retain another service only where its distinct capabilities justify deploying separate controls.**[55][54][52]

Defender for Cloud Apps adds operational visibility to this alternative: since March 2024, its Microsoft 365 connector has provided detections for risky Microsoft Copilot for Microsoft 365 user activities, exposes those activities in the Defender for Cloud Apps activity log, and makes them available in the `CloudAppEvents` table for Advanced Hunting. These are detection and investigation capabilities, not the Purview DLP enforcement point that blocks a matching Copilot prompt.[63][18]

### known limitations

Copilot’s Purview DLP protection is substantive but not universal. The SIT prompt rule evaluates text typed directly into the prompt; it does not inspect the contents of files uploaded directly to a Copilot or Cowork prompt.[5][56] This direct-upload gap means an organization cannot treat typed-prompt DLP as complete file-content DLP. Use sensitivity labels and access controls for source documents, and apply endpoint or upload-path controls where file exfiltration prevention is required.

Label-based exclusion also has defined boundaries. Copilot can still show a citation or link to a labeled file or email whose content it did not process; covered email is limited to mail sent on or after January 1, 2025, and calendar invites are unsupported.[5][57] In Word, Excel, and PowerPoint, a label applied during an open session takes effect for this DLP behavior only when the file is next opened.[5] Copilot and agents also do not currently recognize sensitivity labels that protect Teams meetings and chats.[52][57]

Copilot honors existing permissions; it does not repair excessive permissions. If SharePoint or OneDrive content is already overshared, Copilot can surface it to anyone who already has access.[52][57] Microsoft 365 Copilot expands the practical impact of those permissions because it can access and generate content across organizational data, increasing unintended-exposure risk if the tenant’s permissions, labeling, and discoverability controls are weak.[64][5]

The feature status is also mixed. The Copilot policy location, prompt processing controls, and some external-email restrictions are documented as preview features.[10][5] Microsoft’s policy-reference table presents an apparent inconsistency: its content-definition matrix lists sensitivity labels, but not SITs, for Microsoft 365 Copilot, while its Copilot-specific conditions explicitly list both sensitivity labels and SITs and its Copilot DLP guidance documents SIT-based prompt blocking.[10][5] Configure and validate the behavior in the tenant rather than relying solely on a support matrix.

Microsoft says prompt safeguards are available to all Microsoft Copilot and Copilot Chat users, whereas restricting files or emails requires E5/A5 or specified Purview suites; automatic labeling also requires higher licensing than manual labeling.[129]

These limitations rule out describing Copilot as a complete solution to every outbound data-loss scenario, but they do not diminish its specific value: it supplies a native Purview enforcement point for the covered Copilot prompt and source-content paths.

For SIT-based prompt protection, the documented enforcement point is the covered Copilot experience: the Processing prompts action prevents that experience from processing or answering a matching typed prompt. Microsoft does not describe this action as blocking a request before it reaches the Copilot service. The action evaluates typed prompt text only, not the contents of a directly uploaded file. Neither the typed-prompt action nor the sensitivity-label action applies to ChatGPT Enterprise.[5][1]

A DLP rule that protects a Copilot prompt is not a comprehensive inspection control for every generated response, external website result, plug-in or agent action, or data that subsequently leaves Microsoft 365 through another application. It also cannot prevent a user who can legitimately view information from retyping it into a different service.

Purview cannot inspect encrypted files for SITs or trainable classifiers.[10]

Microsoft describes the preview Exclude content action as applying only to SharePoint and OneDrive for Business content.[65]

### Replacement boundary

Replacing ChatGPT Enterprise with Microsoft 365 Copilot changes both the workflow and the security boundary. Copilot can draft, edit, summarize, analyze, and assist within Microsoft 365 applications while grounding responses in documents, email, calendars, chats, meetings, contacts, and other Microsoft Graph context that the user can access.[53][54][55] This reduces the need for employees to copy Microsoft 365 content into a separate AI interface for many common tasks.

It does not convert ChatGPT Enterprise into a Purview-governed Copilot workload. The Purview DLP policy location is specifically Microsoft 365 Copilot, Copilot Chat, and Cowork, scoped to accounts or distribution groups; its rules apply to those Copilot interactions.[7][10][5] A user who continues to paste information into ChatGPT Enterprise is using a separate interaction path, even if the organization also licenses Copilot and protects Microsoft 365 content with Purview.

Judgment — Treat Copilot replacement as a risk-reduction architecture decision, not an integration project. It moves eligible Microsoft 365 work to a distinct, Purview-governed Copilot control surface where Purview can restrict Copilot's processing of covered prompts and labeled source items; it does not solve governance for remaining ChatGPT Enterprise usage.[5]

The reduction in ChatGPT Enterprise exposure is proportional to the work that users actually move to Copilot. Make Copilot the approved path for the displaced Microsoft 365 use cases and restrict or actively discourage ChatGPT Enterprise use for those same sensitive workflows; otherwise the separate ChatGPT disclosure path remains available.

Microsoft 365 Copilot provides a Purview-native alternative for Microsoft 365 work: user permissions and encryption rights constrain retrieval, sensitivity-label DLP can exclude selected source content, and SIT-based DLP can stop a matching typed prompt from being processed. Audit, retention, eDiscovery, DSPM for AI, and Communication Compliance add investigation and lifecycle governance around those interactions.[5][52]

The strongest conclusion is bounded but clear. Copilot replacement offers stronger preventive Purview control than retaining ChatGPT Enterprise for the same Microsoft 365-centric workflow, because Purview can directly act on covered Copilot prompts and labeled source content. It remains incomplete for uploaded-file contents, overshared Microsoft 365 data, unsupported content types, and external agent paths. Most importantly, Copilot policy coverage ends at the Copilot boundary: any retained ChatGPT Enterprise use requires the separate controls addressed in the later sections.[5][52][53]

## Defender for Cloud Apps / CASB and proxy controls

Judgment — A cloud access security broker (CASB) is a control layer between users and cloud services. A proxy-based CASB can provide true DLP only when it sees the actual submission before it reaches ChatGPT and can deny that submission. App discovery, session logging, compliance-log ingestion, and after-the-fact deletion are valuable governance functions, but they are not preventive DLP.

### Enforcement boundary

Microsoft Defender for Cloud Apps is Microsoft’s CASB. Its Conditional Access App Control uses Microsoft Entra Conditional Access to monitor and control cloud-app access and interactive sessions in real time. Access policies decide whether a user may enter an app; session policies allow entry but restrict selected activity during the session.[66][67][68]

For ChatGPT Enterprise, the important boundary is not the workspace but the **routed interactive browser session**. Conditional Access App Control supports interactive SAML 2.0 single sign-on and, for Microsoft Entra applications, interactive OpenID Connect sign-on. Apps using another identity provider require manual onboarding. Session controls apply only to web-browser access during interactive browser sessions.[66]

A Defender for Cloud Apps **access policy** can enforce Audit or Block based on app, user, user group, device, client type, IP address, location, ISP, or user-agent attributes. This can stop disallowed users, unmanaged devices, risky locations, or unapproved client types from accessing an onboarded ChatGPT Enterprise service at all. It is access control, however, not inspection of a prompt’s contents.[68]

A Defender for Cloud Apps **session policy** is the CASB mechanism when the organization intends to permit ChatGPT Enterprise but constrain supported activity within the routed interactive browser session. Defender for Cloud Apps is the enforcing product: its policy types are Monitor only, Block activities, Control file upload with inspection, and Control file download with inspection. It can block selected supported activities and inspect, audit, block, or protect supported file transfers. Microsoft Purview Information Protection sensitivity labels can be policy inputs for those file controls, but Purview does not enforce the Defender session policy. Microsoft documents activity filters such as printing, clipboard actions, sending, sharing, unsharing, and editing for supported apps; it gives sensitive-message blocking in Teams or Slack as an example.[67]

**For ChatGPT Enterprise, establish in a successfully onboarded interactive browser session whether Defender for Cloud Apps recognizes prompt submission as a supported activity that it can inspect and block. Its documented file and activity controls do not by themselves demonstrate a DLP gate for arbitrary text typed into a ChatGPT Enterprise prompt.** File-upload policies can inspect a file and block it where it matches content or label conditions.[66][67] A block-activities policy can inspect the content of a supported activity. The available activity types depend on the application’s integration and its successful onboarding to Conditional Access App Control.[67]

Microsoft Purview Endpoint DLP provides the clearest Microsoft-documented preventive control for browser-entered ChatGPT content. On Windows computers onboarded to Microsoft Purview, Endpoint DLP can warn or block a user from sharing sensitive information with third-party generative-AI sites through a browser. Microsoft’s example is preventing a user from pasting credit-card numbers into ChatGPT, or warning with an optional override.[4][49]

Purview classifies ChatGPT as an unmanaged cloud-app route for its inline web controls rather than treating this as native workspace-level DLP. Purview lists OpenAI ChatGPT for the Edge for Business and Network options, and its unmanaged-cloud-app browser controls can allow or block covered upload-text and upload-file actions with auditing.[7][21]

A true preventive outcome requires an applicable Block action at the same enforcement point. Conditional Access App Control has two browser enforcement paths: Microsoft Edge provides direct in-browser protection, while other browsers are redirected through the reverse proxy and display an `*.mcas.ms` URL suffix. ### concrete implementation steps

For outputs as well as submissions, supported browser and endpoint controls can restrict copying, printing, Save As, downloading, clipboard transfers, USB transfers, and unauthorized network saves.[122][16][21]

First, use Defender for Cloud Apps Cloud Discovery with the Generative AI category filter for two to four weeks to build an inventory of generative-AI use, including user counts, upload volumes, and application risk scores. Defender for Cloud Apps classifies ChatGPT in its Generative AI app-catalog category; the category provides visibility into generative-AI application use and helps organizations manage that use securely.[75][63]

Then map every approved ChatGPT Enterprise route before creating controls. Test browser prompts typed directly, browser-pasted text, direct file upload, drag-and-drop upload, uploads from SharePoint or OneDrive, desktop-app use, mobile use, API use, Custom GPTs, GPT Actions, connected apps, and Work or agent features separately. ChatGPT Enterprise supports uploads directly from a computer, Google Drive, SharePoint, OneDrive, GPT Knowledge, Project Files, and GPT Actions; it accepts DOCX, PDF, TXT, HTML, XML, JSON, YAML, spreadsheets, presentations, and multiple audio formats. ChatGPT can analyze text and images in PDFs, including charts and diagrams.[76][34]

Second, decide which routes the organization will permit. The strongest manageable baseline is browser-only ChatGPT Enterprise access on corporate-managed endpoints, with native desktop and mobile applications blocked or separately controlled. Microsoft explicitly advises blocking native-client access while allowing browser sessions when browser-session protection must not be bypassed.[66][67]

Third, deploy Purview Endpoint DLP as the primary prompt and file-transfer control for managed endpoints. Onboard the intended Windows devices and scope both users and devices: Endpoint DLP does not apply unless both are in policy scope. Configure sensitive information types, Exact Data Match where required, and sensitivity labels for files; then apply Block, Block with override, or Audit only according to risk category.[10][4][22][3]

Fourth, configure the browser routes separately because browser paste and file upload are separate enforcement paths:

- **Sensitive prompt paste:** Create a Sensitive service domain group containing the approved ChatGPT web domains and configure the Paste to supported browsers action. Purview can audit, block with override, or fully block pasting sensitive data to an excluded website. [16]

- **Sensitive file upload:** Configure the Sensitive service domains list and use the Upload to a restricted cloud service domain action. The Service domains setting governs uploads through Microsoft Edge, or through Chrome and Firefox only when the Microsoft Purview Chrome Extension is installed. [16]

- **Browser steering:** For unmanaged apps, Purview DLP in Edge for Business applies on Intune-managed Windows 10 and Windows 11 desktop devices. When configured to block, in-scope users cannot use unprotected browsers where the policy does not apply. Chrome and Firefox can also be redirected to Edge for designated sensitive sites when the Purview extension is installed. [21][41]

Fifth, use Defender for Cloud Apps for access gating and, only after verification, for supported file/session restrictions. The deployment prerequisites are a Defender for Cloud Apps license, Microsoft Entra ID P1, an Entra Conditional Access policy, and application onboarding to Conditional Access App Control. For apps using a non-Microsoft identity provider, onboard the identity-provider integration manually. In the Conditional Access App Control list, select Onboard with session control and then select Use the app with session controls in the Edit this app form. Ensure that no Conditional Access policy restricts the Microsoft Defender for Cloud Apps – Session Controls enterprise application, which Conditional Access App Control uses internally; except that application from restrictive policies unless the block is deliberate.[67][68][77][63]

Sixth, create the Entra Conditional Access policy with Conditional Access App Control as the session control. Scope it first to a test group and browser clients, enable Report-only, examine policy impact and application behavior, then turn it on. Microsoft gives this report-only-to-enforcement sequence for both access and session-control deployment.[67][68]

Seventh, create Defender for Cloud Apps policies only for functions proved to operate in the ChatGPT Enterprise browser flow:

- **Access policy:** Block ChatGPT Enterprise from unmanaged devices, prohibited locations, unapproved browser types, or excluded user groups. [68]

- **Upload policy:** Use Control file upload with inspection to block a file with sensitive content that lacks the required Purview sensitivity label, or to block content matching a sensitive-information rule. Defender for Cloud Apps can use Purview sensitivity labels as file filters. [67]

- **Download policy:** Use Control file download with inspection to audit, block, or apply an encrypting Purview sensitivity label to supported downloaded files. This protects the downloaded copy; it does not modify the original cloud file. [67]

Eighth, test the exact end-user path rather than treating policy configuration as proof of enforcement. Microsoft recommends a dedicated test user, signing out of existing sessions before reauthentication, testing managed and unmanaged devices, testing mobile and desktop applications, visiting all pages in the normal workflow, and validating uploads and downloads. In Edge, verify direct in-browser protection; in other browsers, verify that the reverse-proxy session uses the `*.mcas.ms` route.[66][67][68]

Ninth, inspect policy results and make a deliberate decision on failures to inspect. Defender for Cloud Apps Conditional Access App Control logs every routed user session, including time, IP address, user agent, URLs visited, and bytes uploaded and downloaded.[67] The policy report identifies redirected sign-ins and actions such as downloaded or blocked files.[67]

**These steps make browser-path DLP deployable, but they do not turn a browser-session control into coverage for every ChatGPT Enterprise client, API, connector, or agent path.** That boundary should drive the access-policy decision: block unsupported routes, or govern them with a separate endpoint, egress, API, and workspace-control design.[66][25][78]

Before enabling a Conditional Access App Control policy, confirm the required identity path. The Microsoft Entra route requires Entra ID Premium P1 or higher, Defender for Cloud Apps, app single sign-on, and SAML 2.0 or OpenID Connect; a non-Microsoft identity-provider route requires that provider’s license, Defender for Cloud Apps, single sign-on, and SAML 2.0. Configure the Entra Conditional Access session control as Monitor only, Block downloads, or Use custom policy as appropriate.[79][80]

For any SASE, secure-web-gateway, or forward-proxy design, install and enforce the endpoint agent or explicit proxy configuration, force corporate ChatGPT traffic through that egress path, and block direct egress, alternate DNS, and unapproved VPN bypasses. Validate that the gateway decrypts and parses the actual ChatGPT prompt-submission request body and uploaded-file transfer, then blocks a matched policy before forwarding either object to OpenAI.

### trade-offs

Inline control preserves legitimate ChatGPT Enterprise use while enforcing rules at the point of submission. That is materially better than a domain block for organizations that need employees to use ChatGPT but must prevent regulated data, credentials, financial records, health information, source code, or other protected material from leaving the managed environment. Purview describes DLP as deep content inspection and contextual analysis tied to policy enforcement.[4][49]

The cost is deployment complexity. Endpoint DLP requires managed and correctly scoped devices; browser controls require the right browser, extensions where applicable, service-domain groups, policy precedence, and testing. For unmanaged-app browser controls, Purview’s automatic Edge-management configuration must successfully synchronize before enforcement starts.[10][21][19][16]

CASB session control adds identity and application-integration dependencies. Conditional Access App Control can apply to interactive SAML and Entra OpenID Connect sessions, but a non-Entra identity configuration must be onboarded manually. Existing app tokens can also delay new policy enforcement until the user signs in again.[66][21]

A reverse proxy can alter application behavior because it modifies underlying application code. Microsoft says built-in apps and browser extensions are not supported by this reverse-proxy mechanism, and server-side blocking can in rare cases make an application unusable. Administrators therefore choose whether a policy that cannot be enforced should allow access or block it entirely.[81][66][82]

A strict, fail-closed policy reduces data-leakage risk but increases disruption. Defender for Cloud Apps session policies apply to files up to 50 MB. Content inspection runs only for files smaller than 30 MB and fewer than 1 million characters; larger or otherwise unscannable files follow the configured action for data that cannot be scanned.[81][82]

Encrypted content makes that choice more consequential. Purview states that encrypted files cannot be inspected for sensitive information types or trainable classifiers. In the Defender for Cloud Apps coauthoring scenario for encrypted sensitivity-labeled files, content inspection cannot read the files; if the fallback is fail closed, every such file can be blocked regardless of its actual contents.[10][81][82]

Purview browser inspection also has bounded evaluation sizes. Edge for Business evaluates up to 4 MB of upload-text content and files up to 3 MB for upload-file. Paste to Browser evaluates only clipboard data, ignores text under 30 characters, waits 2 seconds before allowing paste, supports sensitive information types but not sensitivity labels or Advanced Classification, and classifies only the first 4 MB of clipboard text.[21][10]

Privacy and data-residency review are also required. Defender for Cloud Apps uses globally located Azure datacenters, so a session might be hosted outside a particular region, although Microsoft says those datacenters do not store session data and its proxy does not store data at rest. A secure-web-gateway design additionally exposes decrypted traffic to the gateway’s inspection architecture, policy administrators, and incident-handling systems.[66][71]

This trade-off decides the control pattern: use fail closed for restricted classifications and workflows where no disclosure is acceptable; use narrowly scoped overrides or controlled exceptions for business processes where false blocking would cause disproportionate operational harm. Purview supports Block, Block with override, and Audit only, and an endpoint override can permit the restricted activity for one minute before enforcement resumes.[10][16]

Defender for Cloud Apps session policies accept files up to 50 MB, but content inspection applies only below 30 MB and one million characters: the maximum inspectable size is 60% of the session-policy limit, leaving a 20 MB size gap governed by the configured unscannable-data action.[81]

Microsoft states that requiring Microsoft Edge for access to corporate resources raises the barrier to circumventing session controls compared with reverse-proxy technology.[63]

Using the stated limits, Edge inline upload-file evaluation (3 MB) is 4.7% of the 64 MB Endpoint DLP file-content-inspection ceiling, while Edge upload-text evaluation (4 MB) is 6.2%. This quantifies the substantially smaller content-size envelope of the Edge inline route.[21][83]

Conditional Access App Control can apply session policies to files up to 50 MB, but content inspection applies only below 30 MB; the resulting 20 MB uninspectable band represents 40% of the session-policy file-size limit.[81]

### known limitations

Purview browser and Endpoint DLP are preventive for covered paths, not universal for ChatGPT Enterprise. Endpoint DLP browser controls apply to managed-device activity; the Service domains file-upload control is limited to Edge and to Chrome or Firefox with the Purview extension. Purview browser and network policies also do not apply to B2B guest users.[16][21]

Browser and network inspection do not replace endpoint controls for local exfiltration through clipboard, local files, USB, printing, or screenshots.[39][122]

ChatGPT can intermittently send content in encoded form or through dynamically generated endpoints, which Microsoft says can affect unmanaged-app policy enforcement. Detection for unmanaged cloud apps is based on destination traffic, which may not precisely match the originating application.[21]

CASB session controls do not cover native or noninteractive routes by default. Defender for Cloud Apps says that session controls apply only to interactive browser sessions; noninteractive sign-in flows cannot use access controls. The ChatGPT Windows app, desktop applications, mobile apps, API Platform, integrations, and agent workflows therefore need distinct access, endpoint, network, or API governance decisions.[66][37][78]

ChatGPT desktop and mobile apps also use certificate pinning. OpenAI states that organizations using SSL inspection for its network controls must add their own certificates to the app pin list and distribute them through mobile-device management. OpenAI separately warns that SSL inspection or decryption can disrupt the macOS app.[46][43]

Network inspection must account for transport protocols. ChatGPT uses secure WebSocket connections over TCP 443 for conversation updates and notifications. OpenAI says proxy, filtering, and inspection controls must not block, rewrite, or prematurely close the WebSocket handshake or long-running connection; Zscaler advises blocking and dropping WebSocket protocols for inline DLP where WebSocket inspection is unavailable.[43][71]

Conditional Access App Control has further network and session constraints. Its IP-based rules support IPv4 only; IPv6 requests do not receive IP-based policy enforcement. Edge in-browser protection can retain stale policy enforcement after a user is removed from Conditional Access because cached policy data remains until refreshed or removed.[81][82]

Monitoring must not be misrepresented as control. A Monitor only session policy observes only login activity. To monitor activity beyond downloads and uploads, Microsoft requires an Audit action on a Block activities, Control file upload, or Control file download policy, and monitoring non-file activities requires at least one block-per-activity policy.[67]

Purview Network Data Security and SASE/SSE integrations extend analysis beyond Edge. Microsoft says this route can detect sensitive data shared through non-Microsoft browsers, applications, APIs, add-ins, and other network channels, and can analyze prompts and responses through SASE or SSE integration. Detection depends on the network partner’s implementation; it should be treated as preventive only where the selected provider demonstrably blocks the matched request in line.[3][22][19]

Judgment — The deciding operational question is whether every sanctioned route is forced through an inspection point that identifies and blocks the relevant submission. The test matrix must include account type, client, browser, typed prompt, pasted prompt, file type, upload mechanism, connected-storage upload, GPT Knowledge, Project Files, GPT Actions, MCP tools, Work and Codex mode, HTTP, HTTPS, WebSocket use, and API route.[84][85][86][87][39]

A browser CASB session policy does not control OpenAI API calls made by servers, scripts, developer tools, or custom applications. Put API-mediated use behind an application or API gateway that authenticates callers, restricts API credentials and outbound egress, applies request-content policy before the API call, and logs the decision.

Defender for Cloud Apps is useful for ChatGPT Enterprise access governance and for supported browser-session file controls: it can block application access by user, device, location, or client, and it can inspect and block supported file transfers in routed sessions. Purview Endpoint DLP and Edge for Business provide the clearer documented Microsoft route for blocking sensitive pasted content and covered uploads before submission to ChatGPT in a browser.[68][67][4][21][49]

The deciding criterion is enforcement-path coverage. A browser control is true DLP for the browser action it intercepts; a CASB monitor, collection policy, DSPM view, compliance-log integration, or API scan is not preventive control for content already submitted. The recommended architecture therefore combines endpoint/browser DLP for prompts and uploads, CASB access restrictions to eliminate bypass paths, and separate controls for native clients, APIs, connected apps, and agent workflows.[21][23][8][66][25]

## ChatGPT Enterprise admin/settings and API-side controls

Judgment — ChatGPT Enterprise administration can reduce the number of people, devices, features, integrations, and network routes that may handle corporate data. It does not, by itself, make a content-aware decision on a user’s ordinary prompt or uploaded file before ChatGPT receives it. That distinction matters: governance controls constrain the environment; true DLP is an inline control that can inspect content and allow, redact, require approval, or block before transmission.

### concrete implementation steps

First, establish the approved AI use paths. Classify each business use case as either (a) Microsoft 365 Copilot for work that can remain in the Microsoft 365 control plane, (b) ChatGPT Enterprise browser or desktop use, or (c) a corporate-built application using the OpenAI API. Treat these as separate paths because ChatGPT workspaces and API Platform organizations have separate memberships and permissions, and ChatGPT IP allowlisting does not apply to the API Platform.[6][37]

Second, restrict ChatGPT Enterprise access before enabling sensitive-data workflows:

1. **Identity and access:** Configure SSO through the corporate identity provider, use SCIM for provisioning and deprovisioning, assign users through synchronized groups, and use custom roles for functions that need different feature access. SCIM manages provisioning while SSO manages authentication; access through direct invitations, other groups, and manually assigned workspace permissions must also be reviewed during offboarding. [88][89]

OpenAI distinguishes the enterprise tenant, which provides organization-wide identity administration, from ChatGPT workspaces and API Platform organizations; each has separate membership and permissions, and synchronized groups must still be assigned to the applicable workspace or API organization.[6][132]

A group has no permissions until assigned a role; SCIM assignment does not confer workspace-owner or custom workspace roles, and API-organization membership does not confer membership in every API project.[132][6]

2. **Network restriction:** Enable the ChatGPT Enterprise IP allowlist, which is off by default, and configure its separate lists for workspace access and Compliance API access so that requests from unlisted IP addresses are refused even with valid credentials; changes take 5 to 15 minutes to apply. [90][24][37] This applies to ChatGPT endpoints and Compliance API keys, but not to `platform.openai.com` or other API Platform access. [24][37]

Users outside an approved IP range can still sign in and switch workspaces, but cannot load new data from an IP-restricted workspace.[133]

3. **Least-functionality configuration:** Start by reviewing the selected apps that are enabled in new Enterprise workspaces, keep new apps and plugins disabled unless approved, grant plugin installation and app access through separately evaluated role-based access control (RBAC), and allow only necessary read actions or specifically approved write actions. [91][38][24] New custom-connector actions are disabled by default until approved; write actions for supported Google and Microsoft apps are also disabled until administrators enable them per app. [24]

4. **Disable high-exposure capabilities unless justified:** Limit GPT creation, sharing, third-party GPTs, and GPT Actions; use approved destination domains for GPT Actions. Disable or restrict Work with Apps, Work Local or Work Cloud, Canvas code execution, Record, agent browsing, scheduled tasks, and public Sites where they are not required. These features introduce data paths through local files, desktop apps, browser sessions, connected applications, web sources, voice, and automated tasks. [23][24][92][37]

5. **Constrain connected sources:** For each enabled app, separately review RBAC access, provider-account authorization, source permissions, enabled actions, saved-content restrictions, and Microsoft Graph permissions where applicable. Company knowledge respects existing company permissions, so ChatGPT has access only to content each user is authorized to view; administrators enable connectors for the workspace and manage access with RBAC. [24][38][25] A shared or agent-owned connection may use permissions broader than an individual user’s own rights, so shared accounts should be limited to required data and actions. [38][25]

Third, deploy a pre-submission DLP enforcement point for every ChatGPT use path that is approved for sensitive data. For browser-based ChatGPT Enterprise use, test Microsoft Purview Endpoint DLP in the actual managed-device, browser, account, and data-action combination. Microsoft documents policies that can block prompts from being sent to AI apps in Microsoft Edge and can block paste or upload of sensitive information to AI sites in supported browser scenarios. The tested path must include typed prompts, pasted text, uploads, and the specific browser and desktop clients deployed.[19][9]

Fourth, for API-based use, require that all production applications call OpenAI through a corporate application gateway or embedded policy service. The Responses API accepts direct model requests and supports base64-encoded file data, uploaded file IDs, and external file URLs.[93][26] The company must engineer the gateway’s content classification, policy decision, and rejection workflow.

OpenAI Admin APIs can automate invitations, audit review, projects, API keys, spending, retention, and rate limits, but admin keys cannot call non-administration endpoints. Project model permissions support allowlists or denylists, and a monthly hard spending limit returns HTTP 429 when reached.[134]

It must inspect prompt text and files while the corporation still holds them, before it transfers a file to OpenAI to obtain a file ID or forwards base64 file data. For external-URL input, it must retrieve and inspect the content, make the policy decision, and only then provide the URL to OpenAI. The gateway should then allow, redact, tokenize, route for approval, or block according to the organization’s policy, and submit only permitted content.[26][93][27]

Fifth, tune policies in a simulation period before broad enforcement. Purview’s generative-AI templates can begin in test mode, be narrowed to selected users, and be adjusted for sensitivity classifiers; Microsoft’s demonstration states that a policy can be moved to immediate enforcement and enforced within an hour. Configure notifications and decide whether any block may be overridden, because Purview can permit administrator-configured overrides.[19][94][10]

Sixth, implement evidence retention and incident response. Stream immutable ChatGPT compliance events to the SIEM, export supported records for investigation and eDiscovery, and define retention and legal-hold procedures. The Compliance Logs Platform supports append-only event collection, while the Stateful Compliance API supports request-time queries and joining event-referenced information.[8][95]

**The implementation decision is simple: restrict the ChatGPT workspace as a baseline, but use an inline Purview endpoint/browser control or a corporate API policy gateway whenever the requirement is to stop sensitive content before submission.**[25][19][93][27]

Review every already enabled action explicitly: Disable new actions applies only to actions introduced later and does not disable actions already enabled. Treat each custom app as an unreviewed integration because OpenAI does not verify custom apps.[91]

Review role assignments, SCIM group mappings, enabled write actions, and GPT Action domains each quarter and after every major OpenAI feature release. When additive RBAC is enabled, review each member’s effective access because members with several roles receive their combined permissions.[91]

Apply the gateway policy not only to the user’s initial prompt and attachments, but also to retrieved corporate content, tool-call arguments, and outbound connector or action parameters. Evaluate those inputs against the organization’s sensitivity labels, sensitive-information types, exact-data-match datasets, customer-data rules, and business-specific restrictions before any model or external-service transmission.

For a corporate API application, use Microsoft Purview APIs before each relevant activity. Compute the protection scope for activities such as uploading text input or prompts and downloading AI responses; the returned scope directs the application to evaluate and block, evaluate without blocking, or perform no evaluation. Process content and enforce a returned `restrictAccess` action whose `restrictionAction` is `block`.[96]

Use the Microsoft Purview Information Protection REST API with the existing and desired sensitivity labels to inform the application of label-handling actions, including metadata application, watermark generation, and protection. The corporate application must use those actions in its own policy workflow before submitting permitted content to OpenAI.[27]

For custom-app API enforcement using Microsoft Purview APIs, register the application in Microsoft Entra ID with the appropriate permissions, maintain an Azure subscription with Microsoft Purview configured, and ensure the application has access to the user inputs and app outputs to evaluate, including GenAI prompts and responses. Compute protection scopes immediately after user authentication using the user's Entra ID.[96]

Parse the returned `activities` and `executionMode` for every protection scope. The application must call `processContent` for `evaluateInline` and `evaluateOffline` activities; for `uploadText`, it must block the main thread while calling `processContent`, while for `downloadText`, it must make an asynchronous call. Cache the `ETag` returned by `protectionScopes/compute` and send it in the `If-None-Match` header on every `processContent` call. Recompute protection scopes when 60 minutes have elapsed since the last `processContent` call.[96]

Create DLP policies for the Entra-registered application with the `New-DlpComplianceRule` PowerShell cmdlet and confirm that the policy is listed and enabled in DSPM > Collection policies. Policies created in the Microsoft Purview portal UI do not apply to Entra-registered applications.[96]

Cover every API surface used by the corporate application. The OpenAI API identifies Responses for direct model requests, tool use, audio, image, and text inputs, and stateful interactions; Realtime API for low-latency voice or audio sessions over WebRTC, WebSocket, or SIP; and Administration for users, invites, projects, API keys, and audit logs.[97]

Maintain an allowlist of approved connectors, agents, and custom GPTs, deny all others, and record the data that each approved connector can access.[98]

1a. Verify company domains, disable automatic account creation, and migrate company-email personal accounts into the Enterprise workspace; until migration, their conversations remain outside workspace controls.[99][90][91]

Domain verification establishes control of an email domain but does not itself enable SSO, SCIM, or product access. Automatic account creation is enabled by default for the first eligible Enterprise workspace in a new tenant.[135]

For SSO and lifecycle control, verify every existing guest and invitation as well as synchronized users. Required SSO applies to members whose email address uses a verified domain covered by the workspace policy; invited members from other domains may use another permitted sign-in method, and disabling Allow External Domain Invites does not remove existing guests or invitations already sent. Configure MFA, device restrictions, and conditional-access rules in the identity provider, while recognizing that those controls apply when a person authenticates through that provider.[89]

Disable automatic account creation unless it is governed in the offboarding design. Automatic account creation is separate from SCIM, does not require SSO, and can create users who are not SCIM-managed; removing such a user from the identity provider may not remove product access.[88]

For a proxy-enforced browser route, configure account restriction as well as content enforcement. dope.security Cloud Application Control decides which account is allowed and injects OpenAI's tenant restriction header inside the decrypted session, allowing ChatGPT Enterprise while blocking a personal login on the same domain.[100]

### trade-offs

ChatGPT Enterprise administration is valuable because it provides practical attack-surface reduction. Workspace owners and administrators can manage members, seat defaults, feature access, GPT governance, apps, analytics, and identity controls. Permissions and roles can limit models, GPT creation and sharing, Canvas, Projects, Memory, link sharing, Work Local, and Work Cloud.[92] IP allowlisting limits access to corporate network locations, while SSO, SCIM, and role assignment limit who can enter and what they can use.[24][6]

Connected-app controls further reduce exposure. Administrators can choose who can use an app, what actions it can take, and when ChatGPT must ask before using it. App access, action control, and app permissions are separate settings: access controls who can use the app; actions control what it can do; permissions control when confirmation is requested.[38] Existing source-system permissions remain relevant: ChatGPT connectors are described as respecting existing company permissions, so a user sees only content they are already allowed to access.[24]

These controls do not turn source authorization into DLP. A user who is authorized to read a confidential SharePoint document may still copy its content into a ChatGPT prompt unless an independent inline DLP control blocks that action. Similarly, confirmation before a connected-app action is not a sensitivity classification of the data being read or submitted.[24]

Compliance capabilities provide accountability rather than prevention. The Compliance API supports audit, security, legal, governance, and investigation workflows; the Compliance Logs Platform exports immutable, time-windowed JSONL records, including audit, authentication, and Codex usage logs.[95][24][37] These exports can support SIEM monitoring, eDiscovery, retention, and investigation after activity occurs, but audit logs do not stop a prompt or a file from reaching a model.[25][8][6]

API-side controls have a different trade-off. A corporate application that owns the OpenAI API request can make a policy decision before a direct model request. Microsoft Purview sensitivity-label metadata can be read through the `extractLabel` API, enabling the application to interpret the label and decide handling actions.[27] This enables a stronger design than post-event logging: the organization can refuse to submit a labeled or detected secret, replace it with a token, or require a business approval.

That strength comes with engineering responsibility. The gateway must normalize content across prompt text, base64 uploads, file uploads that would create file IDs, and external-URL content; inspect each item before its transfer to OpenAI; avoid logging the sensitive original unnecessarily; secure service credentials; and provide a safe user explanation and appeal path.[26][93] PDF handling is particularly important: for vision-capable models, the Responses API sends both extracted text and page images to the model, so a text-only scanner is not a complete check of the content being supplied.[26] Local preflight handling can also leak data into terminal history or captured logs if engineers print prompts during development or operations.[101]

**The operational trade-off is coverage versus friction: workspace governance is broad but not content-aware, while an API gateway can be content-aware but only covers applications that are forced through it.**[98][89][37][93]

The gateway adds latency and can reduce model usefulness when redaction or tokenization removes context. It must also handle false positives and false negatives across attachments, images, archives, and multilingual content, while minimizing the sensitive content retained in policy-decision logs.

### known limitations

ChatGPT Enterprise settings are not a sensitivity-aware DLP engine. OpenAI documents controls for identity, access, apps, connectors, actions, retention, encryption, logs, and network access, but these controls do not classify ordinary prompt text or uploaded files against Microsoft Purview sensitive-information types and block them before ChatGPT receives them.[23][24][98][102]

Feature restrictions are also path-specific. Supported Browser Use policies can restrict website access, uploads, downloads, browser history, and browser-debugging access, and a user approval cannot override an administrator denial. However, ChatGPT Work documents that Browser Use policies do not apply when Computer Use operates a browser as an approved native application.[25] Administrators must therefore validate each deployed route independently: regular browser, desktop in-app browser, browser extension, native Computer Use, local task execution, API client, and connected application.[25]

Logging coverage is not complete activity coverage. For Local computer access with Work Cloud, Compliance API records and separately collected OpenTelemetry events do not establish a complete record of every local command, file operation, screenshot, approval, or external action. OpenAI also states that it does not store a separate complete record of Chrome actions performed through its extension.[95][25] Monitoring is necessary, but it is not proof that all data movements were seen or blocked.

ChatGPT-side retention and encryption controls protect data after it enters the service; they do not prevent submission. ChatGPT Enterprise administrators can control retention, and OpenAI states that customer content is encrypted in transit and at rest and not used for training by default.[102][23][38] Separately saved Library or Space files may have a different lifecycle from the chat in which they were used, and deleting a chat does not delete separately saved files.[34]

For newly provisioned ChatGPT residency workspaces, in-scope data stored at rest in the selected region includes conversations, files, custom GPT prompts and outputs, Memory, Data Analysis artifacts, image inputs and outputs, backups, and replicas. Apps/MCP, web search, transient processing, workspace metadata, billing, and login data may remain outside that region.[136]

Inference residency adds supported in-region GPU execution to data residency’s at-rest storage commitment; neither control prevents a sensitive submission. Third-party network services apply their own retention policies.[136][6][103]

API data controls are likewise not DLP. Zero Data Retention and Modified Abuse Monitoring can reduce API retention, but OpenAI requires approval, allows project-level settings that can explicitly select no retention control, and identifies endpoints or capabilities that may still retain application state.[103] Enterprise Key Management encrypts customer content using a customer-controlled external key-management system; it does not inspect prompts for confidential information.[103]

For the OpenAI API, default abuse-monitoring logs may contain prompts, responses, and metadata for up to 30 days; API data is not used to train models unless the customer opts in.[103]

OpenAI API Zero Data Retention excludes customer content from abuse-monitoring logs and forces `store=false` for Responses and Chat Completions. It does not make all API functions stateless: conversations, threads, assistants, vector stores, files, fine-tuning jobs, batches, and other listed endpoints remain stateful or ineligible until deletion.[103]

OpenAI API Responses otherwise retain state for 30 days by default or with `store=true`; background responses may be written to disk for roughly 10 minutes.[103]

Controls for API workloads do not automatically govern the ChatGPT Enterprise interface. A ChatGPT Enterprise license and workspace controls are distinct from API Platform administration, and a ChatGPT IP allowlist expressly excludes the API Platform.[104][6][37] Conversely, an API gateway cannot protect a user who bypasses the corporate application and pastes content directly into ChatGPT Enterprise, a personal ChatGPT account, another AI service, or an unmanaged device.

**The limiting rule is route coverage: a control can only prevent loss on the client, browser, application, API request, file path, or connector path that actually passes through its enforcement point.**[25][78][9]

The policy service becomes an availability dependency: failure open can disclose data, while failure closed stops the protected workflow. For high-risk data, configure the gateway to fail closed and use an approval-based exception process rather than allowing an unavailable inspection service to be bypassed.

**Verdict —** Use Microsoft 365 Copilot with Purview first for substitutable Microsoft 365 work. For continued ordinary ChatGPT Enterprise use, use a validated in-path control first: Purview Endpoint DLP and Microsoft Edge Browser Data Security for the managed browser route. For a corporate-built API application, use an inspected API gateway first for that application’s controlled workflow. Use ChatGPT Enterprise administration and the Purview compliance connector as complementary governance, evidence, and investigation controls, not as preventive substitutes.[5][3][4][1][19][6]

The decisive factor is whether the control blocks content before OpenAI receives it. Purview Endpoint DLP and Edge Browser Data Security provide documented blocking on covered browser actions, and an inspected corporate API gateway blocks the requests it owns. ChatGPT Enterprise settings, Compliance API records, and the Purview connector provide governance or post-event management rather than that content-aware enforcement point.[3][4][21][93][1][19][37]

Use Microsoft Defender for Cloud Apps session control as a supplemental browser-session control where its selected app and activity are supported. Use a forward proxy or SASE/SSE integration as a supplemental detection path where the organization requires network-level visibility across AI apps, applications, APIs, add-ins, and more. Neither replaces a validated in-path browser block or an inspected application gateway for preventive ChatGPT Enterprise DLP.[66][67][19][3][93]

The verdict would change if ChatGPT Enterprise introduced and documented a native Purview policy enforcement point that classified and blocked prompts and uploads before submission across its supported clients. It would also change if business requirements demand ChatGPT-specific functionality that Microsoft 365 Copilot cannot replace, or if a corporate API gateway cannot be made the exclusive access path.[1][5][6]

ChatGPT Enterprise administration should be treated as the corporate guardrail layer: it limits identity, network access, enabled features, connected apps, actions, sharing, retention, and audit exposure. It cannot substitute for true DLP because its documented controls do not classify and stop ordinary sensitive prompts or uploads before they reach ChatGPT.[24][23][98]

Purview Endpoint DLP and a corporate API gateway supply the missing preventive layer, but each is route-bound. Endpoint DLP is appropriate for managed browser activity in supported scenarios; an API gateway is strongest for custom applications whose every request it owns. Proxy controls can add coverage where interception is technically and legally acceptable, but must be tested against every deployed route.[19][94][93][105][9]

If an ordinary ChatGPT Enterprise prompt or upload has no inline enforcement point that blocks it before submission, ChatGPT receives the content; Microsoft Purview lists DLP as unsupported for ChatGPT Enterprise AI interactions, and its connector ingests conversations 24 hours after they occur.[25][1][2]
