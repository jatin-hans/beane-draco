# Comparison of Warehouse Detectors on Jetson AGX Orin

## Executive summary

Adopt YOLOv8 with TensorRT and DeepStream as the first production candidate, while using NVIDIA TAO DetectNet_v2 where its managed NVIDIA lifecycle is the deciding requirement and qualifying EfficientDet-D4 only if 1024-pixel evaluation proves a material small-label or damage advantage.

A single Jetson AGX Orin is not a credible architecture for 200 cameras at 30 fps because the requirement is 6,000 aggregate frames/s, whereas NVIDIA’s warehouse-adjacent reference is four 30-fps streams for a different detector, or 120 frames/s per module.[1] YOLOv8 has reported AGX Orin timings of 30.36 ms end to end for one live 640×480 stream and 3 ms isolated GPU INT8 inference for YOLOv8s, but neither establishes pallet-label or package-damage performance, sustained power, or 200-camera capacity.[2][3] TensorRT is the required deployment path for all three candidates because it compiles an engine for the target Orin and can use FP16 or INT8, but the speed gain and accuracy loss must be accepted only against matched FP16 and INT8 engines on the warehouse holdout set.[4][5] The 92% precision objective and any accuracy floor below the 100 MB OTA limit remain conditional: they can be claimed only when the chosen compressed model sustains at least 92% precision at a predeclared operating threshold on new-SKU and normal warehouse test slices, with recall reported separately.

## Warehouse detection performance and 200-camera capacity

**Evidence date — 19 November 2026.** The requested comparison dimensions are deployment path and task fit; INT8 per-frame latency; FP16-to-INT8 warehouse mAP change; sustained power; completed 6,000-frame/s capacity; monthly new-SKU updates; sub-100 MB OTA deployment accuracy; and TensorRT gain. INT8 is eight-bit integer inference, a reduced-precision execution mode that uses calibration scale factors; FP16 is 16-bit floating-point inference. Per-frame latency is the time for one frame at a stated measurement boundary, while aggregate throughput is the completed-frame rate across all concurrent cameras. The 200-camera requirement is 6,000 input frames/s, calculated as 200 cameras × 30 fps, rather than a 33.3-ms single-camera test. Incremental learning means updating a model with newly labelled data while retaining prior knowledge; over-the-air (OTA) deployment means transmitting the release to installed devices over the network.[6][7]

Judgment — Average precision (AP) is the normalized area under the precision–recall curve for one class. Mean average precision (mAP) is the mean of class AP values under a declared intersection-over-union (IoU) convention: mAP@0.50 uses one 0.50 IoU threshold, whereas mAP@0.50:0.95 averages AP across several IoU thresholds. Precision is different: at a fixed operating confidence threshold and IoU match rule, it is the fraction of emitted detections that are correct. A system can report high precision by rejecting uncertain detections while suffering low recall, so neither mAP nor a latency result proves the required precision target by itself.[1][6]

Provisional ranking criterion — YOLOv8 is the first *performance experiment* because it has related package-and-shipping-label evidence and a documented TensorRT export path. TAO DetectNet_v2 is the provisional first *monthly-pipeline choice* because its documented route exports TAO checkpoints to ONNX, builds a device-specific TensorRT engine, and feeds that engine to DeepStream. EfficientDet-D4’s possible small-target benefit is a hypothesis arising from its 1024-pixel configuration, not a measured warehouse advantage. Measured warehouse accuracy, capacity, sustained power, OTA size, and update-retention results can change both provisional choices.[8][5][9][10]

The three candidates occupy different deployment paths. YOLOv8 is a PyTorch-originated one-stage detector with documented ONNX and TensorRT export. EfficientDet-D4 is a 1024-pixel EfficientNet-B4/BiFPN detector that needs TensorRT OSS plugins and a custom DeepStream bounding-box parser. NVIDIA TAO DetectNet_v2 is a TAO model that exports through ONNX to a device-specific TensorRT engine and integrates with DeepStream.[5][11][9]

### How does YOLO v8 perform on Jetson AGX Orin for

YOLOv8 has a direct Jetson deployment route through TensorRT and DeepStream. Ultralytics lists TensorRT export for YOLOv8 detection models, and NVIDIA’s Jetson Platform Services documents a DeepStream 7.1 perception service for real-time multi-stream detection and tracking, with YOLOv8s as an optional detector, followed by NvDCF tracking and metadata publication to Redis.[5][12]

A TensorRT engine is a compiled, serialized inference plan optimized for one GPU architecture, TensorRT version, input profile, precision mode, and batch configuration. TensorRT selects kernels for the target GPU, can fuse graph operations, manages tensors, and can use FP16 or INT8 arithmetic.[4][5][13] The engine must therefore be built for the deployed AGX Orin environment rather than copied unchanged from an x86 training server or a different Jetson installation.[5][14]

The supplied AGX Orin YOLOv8 evidence is useful but narrow. A forum participant running YOLOv8n against a 640×480 RealSense stream on AGX Orin reported 23.5 ms inference, 2.0 ms preprocessing, 2.8 ms postprocessing, and 30.36 ms for object detection in one live-camera pipeline.[2] That is consistent with a single 30-fps camera under that reported setup, because 30 fps permits 33.3 ms per frame.

It does not size a 200-camera system, because the report does not represent pallet labels, package damage, INT8 inference, a saturated multi-stream pipeline, or power under sustained load.[2]

A second AGX Orin forum report gives a more favorable isolated engine timing: its author reported INT8 YOLOv8s inference at 3 ms on the GPU and 12 ms through cuDLA. NVIDIA’s response explains the difference: DLA is designed for energy efficiency, but supported operators, latency requirements, throughput requirements, and the power budget determine whether GPU or DLA is preferable; GPU and DLA engines can also operate together for throughput.[3] That 3 ms GPU result is a valuable planning point for one reported configuration, but it is not an end-to-end per-camera latency measurement and should not be converted into an installation-wide camera count.

Another reported Jetson AGX Orin 64 GB result puts YOLOv8n INT8 inference at approximately 2.5 ms/frame; it is a different variant and measurement from the reported YOLOv8s GPU timing. [115]

The closest task-adjacent published result is a YOLOv8n package-detection experiment on a Jetson Orin NX 16 GB, not AGX Orin. Its dataset was curated for packages and shipping labels and contained 12,042 training images, 1,187 validation images, and only 16 test images.[8] At batch size 1, the package experiment reported 23.67 fps; at batch size 4, it reported 32.04 fps, with per-frame detection time declining from 27.07 ms to 16.27 ms.[8] TensorRT outperformed PyTorch at batches 1, 2, and 4, with the largest stated advantage of 17.7% at batch 2.[8]

The same Orin NX package experiment shows why batching must be treated as a throughput mechanism rather than as proof of 30-fps service to every stream. Its TensorRT engine crashed at batch size 8, while the PyTorch representation continued running and reached its best reported performance at that batch size.[8] The authors also used active cooling and warned that passive cooling in an embedded enclosure could throttle earlier and reduce sustained fps below their stated results.[8] The deployment implication is direct: benchmark the installed enclosure, cooling, power mode, and stream mix, not only an exposed development board.

Published YOLOv8 reference tables establish model scale but not warehouse performance. At 640 pixels on COCO, Ultralytics lists YOLOv8n at 3.2 million parameters and 8.7 billion FLOPs; YOLOv8s at 44.9 mAPval 50–95, 1.20 ms A100 TensorRT speed, 11.2 million parameters, and 28.6 billion FLOPs; YOLOv8m at 50.2 mAPval 50–95, 1.83 ms, 25.9 million parameters, and 78.9 billion FLOPs; YOLOv8l at 52.9 mAPval 50–95, 2.39 ms, 43.7 million parameters, and 165.1 billion FLOPs; and YOLOv8x at 68.2 million parameters and 257.8 billion FLOPs.[15] The same table’s TensorRT times are A100 measurements, ranging from 0.99 ms for YOLOv8n to 3.53 ms for YOLOv8x, and cannot be used as AGX Orin latency values.[15]

A further Orin Nano benchmark illustrates the potential benefit of TensorRT and INT8 but not the target hardware. For YOLOv8n at 640×640 and batch 1, it reported GPU latency of 20.88 ms for PyTorch FP32, 8.36 ms for TensorRT FP32, 4.43 ms for TensorRT FP16, and 3.49 ms for TensorRT INT8.[16] Its corresponding reported power values were 11.4 W, 14.3 W, 14.1 W, and 12.5 W, respectively, on an Orin Nano in MAXN_SUPER mode.[16] These figures demonstrate that optimization path and power mode change measured latency and power; they are not sustained-load AGX Orin measurements.

A published YOLOv8s TensorRT FP16 thermal test on Jetson AGX Orin achieved 108.8 frames/s at 640×640 input and drew 19.1 W average power; these are not INT8 measurements for the warehouse workload. [116]

The Orin Nano result also makes a practical comparison point. Its INT8 latency of 3.49 ms is 1.27× lower than its FP16 latency of 4.43 ms, calculated from the reported values, while the underlying report describes INT8 as 6× faster than PyTorch FP32 for that YOLOv8n configuration.[16] The difference between this result and the 3 ms AGX Orin YOLOv8s report shows why model variant, software stack, measurement boundary, batch size, and power mode must be named with each result.[16][3]

An external COCO comparison reports 1.2–1.6% mAP50–95 degradation from TensorRT FP16 to INT8 post-training quantization across YOLOv8 sizes; this is not a result on warehouse labels or damage. [117]

YOLOv8’s documented DeepStream path has a current multi-stream caveat. NVIDIA’s DeepStream perception documentation says the default YOLOv8s configuration supports one stream because of known issues with the custom DLA-supported model and the legacy DeepStream test5 application.[12] Its documented workaround changes the application so it does not override the primary inference-engine batch size, sets `max-batch-size` to 8, and sets the stream threshold to 8.[12] This supplies an engineering path toward more streams, but it makes eight streams a configuration threshold rather than a demonstrated 200-stream capacity.

In a separate eight-camera YOLOv8-L TensorRT FP16 test on Jetson AGX Orin, aggregate throughput was 82.9 frames/s; it does not establish INT8 capacity for the warehouse fleet. [118]

DeepStream supports multiple simultaneous sources, and a camera source can be configured to request 30/1 fps.[17] Its capacity is bounded by decode, memory, and compute resources, rather than by a fixed number promised by the framework.[7] The DeepStream FAQ identifies an operational failure mode at even lower scale: in one loop case, 30 streams of 1080p, 30-fps video caused initial I/O load that led `decodebin` to drop frames when `qos=1`; NVIDIA recommends `qos=0` for that case.[7]

YOLOv8 uses an anchor-free detection head and a C2f backbone module; Ultralytics says the anchor-free head reduces box predictions and speeds non-maximum suppression (NMS), the process that removes duplicate overlapping boxes.[19] This architecture is well suited to a first warehouse candidate because it has a simple training-to-export path and related package-label evidence.

Small targets remain a design risk: Ultralytics says image tiling can improve small-object detection by dividing larger images into smaller segments, including 1280×1280 images into multiple 640×640 segments, and supports tiled inference through SAHI; each extra tile raises inference work and can increase end-to-end latency.[20]

**Conclusion — YOLOv8 is the leading candidate to benchmark first, not the only model to qualify.** It has a documented AGX Orin/TensorRT deployment route, reported AGX Orin single-stream timings, and a package-and-label-adjacent Orin NX experiment with TensorRT. It has not yet demonstrated the required INT8 latency, FP16-to-INT8 mAP change, sustained power draw, pallet-label accuracy, package-damage accuracy, or 6,000-fps aggregate throughput on the client’s installation.[2][3][8] The decision this subsection makes is to use YOLOv8 as the performance baseline for the controlled acceptance test, not to approve a one-Orin 200-camera design.

Comparison judgment — YOLOv8 is the first performance candidate because it has the only supplied task-adjacent package-and-label evidence and a reported AGX Orin INT8 engine time. DetectNet_v2 is the NVIDIA-native operational comparator. EfficientDet-D4 advances only if the locked warehouse test shows that its 1024-pixel path improves pallet-label or damage precision enough to justify its compute demand.[8][3][9][10]

A drone-application study using TensorRT at 640×640 reported YOLOv8n on Jetson Orin NX at 52.19 fps, mAP50-95 of 0.8420 and mAP50 of 0.9621 in FP32; its INT8 version reached 65.83 fps, mAP50-95 of 0.7190 and mAP50 of 0.8276. INT8 therefore added 13.64 fps, or 26.1%, and reduced mAP50-95 by 0.1230, or 12.3 percentage points, in that study.[23]

The same study reported YOLOv8s on Jetson Orin Nano at 27.00 fps with FP32 and 41.20 fps with INT8; mAP50-95 changed from 0.8608 to 0.7968, a 6.4-percentage-point reduction.[23]

These two results show that INT8 speed and accuracy effects vary by YOLOv8 variant and Jetson configuration. The warehouse acceptance comparison must retain the requested matched FP16 baseline, rather than substitute either FP32 reference result.[23]

### How does EfficientDet-D4 perform on Jetson AGX Orin for detecting

EfficientDet-D4 is a compound-scaled one-stage detector. Its D4 configuration uses 1024-pixel input resolution, an EfficientNet-B4 backbone, BiFPN width 224, BiFPN depth 7, and class/box prediction depth 4.[10] BiFPN, or bidirectional feature pyramid network, combines image features at multiple scales through repeated top-down and bottom-up paths.[10][32]

The original EfficientDet publication reports D4 COCO performance of 49.4 AP on test-dev, 69.0 AP50, 53.4 AP75, 49.0 AP on validation, 21 million parameters, 55 billion FLOPs, 74 ms GPU latency, and 4.8 seconds CPU latency.[10] Its latency measurement used batch size 1, 10 runs, a Titan V GPU, and a single-thread Xeon CPU. These values establish that D4 is a high-resolution detector with substantial computation; they do not describe INT8 execution or Jetson AGX Orin behavior.[10]

Google’s EfficientDet repository supplies a second reference point. It lists D4 at 49.7 COCO test-dev AP, 68.4 AP50, 53.9 AP75, 20.7 million parameters, and 55.2 billion FLOPs.[33] On a single Tesla V100 without TensorRT, it reports 42.8 ms end-to-end batch-1 latency, 23 fps batch-1 throughput, and 35 fps batch-8 throughput.[33] A fixed-size D4(640) variant is listed at 45.7 mAP and 21.7 ms, but the table does not identify the test hardware.[33]

A third published reference is a T4 TensorRT10 COCO table, which lists EfficientDet-d4 at 1024 pixels, mAP50-95 of 49.7, and 33.55 ms speed.[19] The three latency values—74 ms on Titan V, 42.8 ms on V100 without TensorRT, and 33.55 ms on T4 TensorRT10—are not conflicting results. They use different GPUs, execution paths, and possibly different timing boundaries.[10][33][19]

EfficientDet-D4’s 1024-pixel input creates a particular warehouse trade-off. Higher input resolution can preserve small pallet-label text regions and local damage patterns, but it increases feature-map sizes and compute. The published D4 architecture combines high resolution with 55.2 billion FLOPs.[10][33] The deployment question is therefore not whether D4 is accurate on COCO, but whether the camera geometry gives it enough target pixels to justify its heavier 1024-pixel path.

An external V100 batch-one comparison without TensorRT reported COCO mAP of 49.7 for EfficientDet-D4 at 1024-pixel input and 45.7 at 640-pixel input, a 4.0-point reduction at the smaller resolution; these are not warehouse results.[22]

The selected EfficientDet-D4 implementation can run in DeepStream through NVIDIA’s documented EfficientDet-to-DeepStream integration path. That path requires a label file, DeepStream configuration file, TensorRT 8+ OSS, and an EfficientDet bounding-box parser compiled for DeepStream; it also requires the `ResizeNearest_TRT` and `EfficientNMS_TRT` plugins from TensorRT OSS. NVIDIA documents two paths: use an exported `.etlt` model directly in DeepStream or generate and integrate a TensorRT engine using `tao-converter`.[11]

The resulting deployment graph is still a standard DeepStream architecture: source decode, `nvstreammux` batching, primary inference, tracking when needed, and metadata output. The main configuration controls input source, resolution, inference count, tracker, and output sinks; the inference configuration controls model, inference resolution, batch size, class count, and related settings.[11] That means EfficientDet-D4 can participate in the same multi-camera acceptance test as YOLOv8 and DetectNet_v2, but it must carry its parser and plugin dependencies into every reproducible release.

EfficientDet’s INT8 path is documented. NVIDIA says TensorRT engines can be generated in INT8 mode to improve performance and require a calibration cache.[11] The recommended calibration approach uses the training data loader, applies the same preprocessing as training, and samples batches randomly across the training dataset; alternatively, a randomly subsampled image directory should represent the training data.[11] This is directly relevant to a warehouse where labels, package surfaces, glare, packaging textures, camera angles, and illumination vary materially across shifts.

INT8 behavior must be validated more carefully for EfficientDet than a generic “INT8 is faster” statement suggests. A TensorRT issue reported that EfficientDet-lite1 and EfficientDet-lite2 produced no detections in some INT8 experiments across V100, Xavier NX, and Xavier AGX systems.[34] In one reported Lite1 case, using 1,000 calibration images, calibration batch size 1, input shape 1×3×720×1280, and a suitable calibration-image selection produced good detections; Lite2 still did not.[34] A later user reported that an EfficientDet-lite1 pretrained checkpoint worked in INT8 under TensorRT 8.6.1.6, while a locally trained model still did not.[34]

In a COCO experiment on EfficientDet-D0, not D4, INT8 post-training quantization reduced mAP@0.5 by 2.7 points, while quantization-aware training reduced it by 0.8 points. [120]

The cited EfficientDet-lite1 report identifies TensorRT 8.5.2.2 as the version under which its INT8 output was unusable; it does not establish the behavior of EfficientDet-D4.[121]

The reported EfficientDet-lite1 failure produced no bounding boxes or unusable results after INT8 conversion with TensorRT 8.5.2.2, despite expected behavior at 16-bit precision; the report concerns Lite1, not EfficientDet-D4.[121]

The reported locally trained EfficientDet-lite1 model produced no bounding boxes or unusable results with TensorRT 8.5.2.2 INT8; a pretrained checkpoint worked with TensorRT 8.6.1.6, but the local model still did not.[121]

Those reports concern Lite variants rather than D4, but they identify the operational risk correctly: a successful engine build is not a substitute for labelled post-export validation. D4 must be tested at the intended resolution and with representative calibration frames, then evaluated on the same held-out images as its FP16 engine.

In an EfficientDet-D0 experiment on COCO mAP@0.5, FP32 scored 42.8% ±0.4 percentage points, INT8 post-training quantization scored 40.1% ±0.5 percentage points, and INT8 quantization-aware training scored 42.0% ±0.4 percentage points. QAT recovered 1.9 of the 2.7 absolute mAP points lost with post-training quantization, but did not reach the FP32 result; these are D0, not D4 or warehouse, measurements.[120]

Judgment — EfficientDet-D4 is technically credible where labels and damage areas are genuinely small in the source image, because its 1024-pixel design preserves more image detail than a 640-pixel default. It should not be selected solely for that reason: a crop, region of interest, higher-resolution YOLOv8 configuration, or two-stage design can sometimes preserve target detail with lower full-frame compute.

No D4-on-AGX-Orin INT8 per-frame latency, FP16-to-INT8 mAP degradation, or sustained-load power reading is supplied. The relevant AGX Orin platform specifications are up to 275 TOPS and configurable 15–60 W power, with the 32 GB module rated 15–40 W and the 64 GB module 15–60 W. These are module envelopes, not application measurements.[35]

NVIDIA’s current product information uses more than one performance label. The datasheet lists 200 INT8 TOPS for the 32 GB module and 275 INT8 TOPS for the 64 GB module.[35] NVIDIA’s product page lists 275 TOPS for the developer kit, 248 TOPS for AGX Orin 64 GB, and 241 TOPS for AGX Orin Industrial; its separate comparison table labels its values as sparse INT8 TOPS. These labels should not be converted into detector fps, because TOPS measures theoretical arithmetic capability rather than video decode, preprocessing, memory traffic, postprocessing, and scheduler overhead.[36]

The 200-camera demand remains 6,000 fps for EfficientDet-D4 as it does for YOLOv8. The closest AGX Orin warehouse-specific context is NVIDIA’s estimate of four 30-fps RT-DETR streams on one AGX Orin iGPU. RT-DETR is not EfficientDet-D4, but the estimate reinforces that multi-camera warehouse sizing is governed by aggregate video analytics throughput rather than by a single engine’s isolated latency.[1]

DeepStream can process multiple sources, but it can also drop frames if the pipeline cannot keep up. Its sink Quality-of-Service setting can generate events that cause dropping when pipeline fps is below stream fps.[17] Rendering must be disabled for maximum inference performance because tiling and visual output consume GPU resources.[17] A D4 capacity test that displays an on-screen mosaic is therefore a different workload from a headless operational pipeline that transmits metadata only.

DeepStream’s detector interval provides an explicit capacity trade-off. Running inference every other frame rather than every frame can effectively double channel throughput, while the tracker predicts locations between detector frames.[17] For EfficientDet-D4, this can make a high-resolution model feasible on more channels only if warehouse validation shows that label status and damage events remain detectable at the reduced detector cadence.

**Conclusion — EfficientDet-D4 is the accuracy-oriented candidate, but it is not the candidate to assume for 30-fps-per-camera operation.** Its COCO references show a 1024-pixel, 55.2-billion-FLOP detector with 20.7 million parameters and published batch-1 speeds below 30 fps on a V100 without TensorRT. The decision is to benchmark D4 only where label and damage error analysis demonstrates that the 1024-pixel detail materially improves held-out warehouse mAP or precision over a smaller model; otherwise its integration complexity and compute burden work against the 6,000-fps aggregate requirement.[33]

Derived — D4’s 1024×1024 input contains 2.56× as many pixels as YOLOv8’s documented 640×640 default, quantifying why a full-frame D4 comparison carries a materially heavier image-processing workload before architecture-specific differences are considered.[10][37]

Derived — The listed 33.55 ms EfficientDet-D4 TensorRT10 timing corresponds to 29.81 frames/s on the cited T4, at 1024-pixel input.[19]

Derived — EfficientDet-D4’s reported V100, non-TensorRT batch-1 throughput of 23 fps is 23.3% below a 30-fps camera rate.[33][17]

EfficientDet-D4 can be fine-tuned to detect pallet-label and package-damage bounding boxes, but its accuracy on the client’s 50,000 warehouse images is unmeasured.

### How does NVIDIA TAO DetectNet_v2 perform on Jetson AGX Orin

DetectNet_v2 is NVIDIA’s object-detection model inside TAO Toolkit.[6] It is integrated into the NVIDIA deployment stack: TAO checkpoints export to ONNX, TAO Deploy’s `gen_trt_engine` action takes the ONNX file produced by the `export` action to generate an optimized TensorRT engine, and DeepStream runs that engine in the video pipeline.[9][38][39] TAO-trained models are described as working with DeepStream out of the box.[9][38]

DetectNet_v2 supports FP32, FP16, and INT8 TensorRT backends. INT8 requires a calibration cache containing tensor scale factors intended to limit quantization errors created by reduced-precision arithmetic.[6] The engine-generation process supports `fp32`, `fp16`, and `int8`; in INT8 mode, a calibration cache is generated.[40] DetectNet_v2 also has an `enable_qat` setting for quantization-aware training (QAT), which trains while simulating quantization effects.[6]

In NVIDIA’s PeopleNet examples, INT8 post-training quantization lost 19.31 mAP points with a ResNet18 backbone and 18.2 mAP points with ResNet34, while quantization-aware training remained within 0.31 and 0.63 mAP points, respectively, of the FP32 baselines. These are people-detection results, not measurements on the warehouse images.[122]

Its input-data route is more prescriptive than YOLOv8’s. TAO detection applications expect KITTI-format data for training and evaluation, and DetectNet_v2 converts KITTI or COCO inputs to TFRecords for optimized training iteration.[6][41] Input images must have one or three channels, minimum width 480 pixels, minimum height 272 pixels, and dimensions that are multiples of 16.[6] The dataset converter lowercases KITTI class names, and class names in the training configuration must match that converted naming or training can yield 0 mAP.[41]

DetectNet_v2 generates coverage and bounding-box tensors on a 16×16 grid.[42] Its postprocessor filters candidates by coverage confidence and can cluster raw predictions with DBSCAN, NMS, or HYBRID clustering, in which DBSCAN supplies candidate boxes to NMS. These details matter for a fair comparison because confidence threshold, clustering method, IoU match threshold, and minimum/maximum valid box sizes all affect final detections and measured mAP.[6][42]

DetectNet_v2 evaluation permits class-specific IoU requirements when reporting class-level AP and mAP. [122] [6]

DetectNet_v2 has a particular small-object concern. An NVIDIA forum response says objects are expected to be larger than 16 pixels and that larger objects are better for training.[43] Pallet labels may be smaller than that at the model’s resized resolution, especially in wide-angle or overhead cameras; package damage may also occupy a small irregular region rather than a large object. The camera design must therefore preserve adequate target pixels before the detector comparison begins.

The detector can infer at a resolution different from training resolution, but NVIDIA warns that accuracy may regress because convolutional kernels see object features at a different shape.[6][41] This means reducing DetectNet_v2 input size to obtain a 30-fps throughput result must be paired with a fresh label and damage accuracy evaluation. A lower-resolution result is not the same model behavior at a lower cost.

The available TAO documentation contains a preprocessing ambiguity that needs explicit version testing. One response says `enable_auto_resize=true` allows the dataloader to resize images to the input resolution.[44] Another says that when output dimensions differ from input dimensions, preprocessing pads with zeros or crops and does not resize images and labels.[44][42] The operational response is straightforward: generate training and inference visualizations from the selected TAO version and confirm box geometry before treating the evaluation metrics as meaningful.

DetectNet_v2’s engine lifecycle is strict. NVIDIA says machine-specific optimizations happen during engine creation, requiring a distinct engine for each hardware and runtime configuration.[45][38] It also says that a new engine must be generated after a new model is created or after TensorRT or CUDA changes, including minor version changes; mismatched engines can yield degraded accuracy, instability, refusal to load, or other undefined behavior.[45][38]

The cited TAO deployment guidance also requires INT8 calibration caches to match the runtime TensorRT version.[123][124][47][125]

In a reported DetectNet_v2 INT8 failure, a calibration cache generated under TensorRT 8.5.2.2 was consumed under TensorRT 10.3.0.30; NVIDIA advised regenerating the cache under the matching runtime version. The same discussion reported that TAO Deploy 5.0 required a workspace-configuration API change to support TensorRT 10.3.0.[47]

This matters to the warehouse because every model release creates at least two deployable test artifacts: a matched FP16 engine and an INT8 engine. Engine generation should be completed and validated before rollout rather than leaving 200 live systems to build plans on first use. DeepStream can generate an engine automatically from a model artifact, but NVIDIA notes that generation can take time; TAO Deploy can generate it ahead of time.[45]

DetectNet_v2 has an NVIDIA-native deployment advantage over EfficientDet-D4. NVIDIA’s open-model deployment table lists DetectNet_v2 as prunable and INT8-capable, compatible with DeepStream 5.1 and 6.0, with no TensorRT OSS requirement.[38] By contrast, EfficientDet’s DeepStream path requires OSS plugins and a custom parser.[11] This reduces deployment surface area for DetectNet_v2, although it does not determine model accuracy or throughput.

DeepStream’s `nvinfer` can reference a pre-generated engine through `model-engine-file` and an INT8 calibration cache through `int8-calib-file`. Custom detector outputs may require a box-and-class parser, while TensorRT layers that are unsupported may require a plugin library.[124]

The practical INT8 path still needs verification. One user reported approximately a 20% decrease in mAP when exporting a DetectNet_v2 model to INT8, without clarifying whether this was percentage points or relative change.[46] Another user reported that a corrected model selection allowed an FP32 TensorRT engine to work but that the remaining INT8 issue appeared to be calibration.[43] A separate report described a TensorRT calibration failure with no scaling factors detected after a calibration file had been generated.[47] These cases establish that calibration artifact creation, engine construction, and post-export labelled evaluation are separate acceptance gates.

In a published PeopleNet DetectNet_v2-ResNet18 people-detection comparison, FP32 mAP was 78.37, INT8 post-training-quantized mAP was 59.06, and INT8 quantization-aware-trained mAP was 78.06; none measures warehouse detection or loss relative to FP16. [122]

The forum report of approximately 20% lower mAP after DetectNet_v2 INT8 export concerned a quantization-aware-trained model evaluated on the reporter’s own test set.[46]

There is also a QAT/DLA limitation. TAO documentation says that its current QAT version does not natively support DLA INT8 deployment on Jetson and directs users to force post-training quantization to create a calibration cache for that use case.[39][40] This matters only if the selected architecture is assigned to DLA; GPU INT8 remains a separate engine path. The GPU should be the default performance path unless a measured power or throughput allocation shows DLA provides an advantage.

A forum participant reported INT8 YOLOv8s at 3 ms on AGX Orin GPU versus 12 ms through cuDLA. NVIDIA’s response says both resources can operate independently and together to increase throughput.[3] DetectNet_v2 should be tested in the same way: GPU-only, DLA-only where supported, and concurrent GPU-plus-DLA assignment when the multi-stream scheduler can exploit it.

A published AGX Orin GPU reference reports 390 INT8 inference-only frames/s for PeopleNet DetectNet_v2-ResNet18, equivalent to approximately 2.56 ms per inference; it is not a custom pallet-label or package-damage latency measurement. [18]

After using a conversion script and enabling `jetson_clocks`, the same forum participant reported 14 ms for the INT8 YOLOv8s DLA model, compared with the previously reported 12 ms DLA result.[3]

Jetson AGX Orin has two NVDLA v2 accelerators alongside a 2,048-core Ampere GPU and 64 Tensor Cores.[3][36]

No supplied source reports DetectNet_v2 INT8 latency, mAP degradation against FP16, or sustained power on AGX Orin for pallet labels or package damage. The recorded precision modes and engine path make the test implementable.[6][39][45] The requested performance values must come from paired warehouse engines using the same class mapping, input size, clustering configuration, confidence thresholds, and held-out evaluation split.

**Conclusion — DetectNet_v2 is the cleanest NVIDIA-native deployment stack, but not an established accuracy or throughput winner for this warehouse.** Its TAO-to-ONNX-to-TensorRT-to-DeepStream route, built-in INT8 support, pruning support, and lower plugin burden make it a strong operational comparator.[9][38][48] Its 16×16 grid, larger-than-16-pixel object guidance, and resolution sensitivity make it a potentially weaker fit when pallet labels or damage occupy very small image regions.[42][43][6]

DetectNet_v2 is a detector architecture and TAO workflow rather than one fixed-capacity checkpoint directly equivalent to a named YOLOv8 variant or EfficientDet-D4. Its comparison configuration must therefore lock the selected backbone, input size, pruning state, precision mode, and postprocessing settings before latency, power, or accuracy results are interpreted.

TAO permits DetectNet_v2 ResNet backbones ranging from 10 through 101 layers.[18]

### What about the automated warehouse’s 50K-image dataset

Judgment — The acceptance test needs two linked test beds. The first is an offline accuracy test on immutable labelled images. The second is a live or replayed video test that exercises camera ingress, decoding, batching, preprocessing, inference, tracking if enabled, metadata delivery, thermals, clocks, and power. Mixing those tests hides whether an apparent gain came from model execution, frame dropping, different preprocessing, or different confidence thresholds.

The warehouse corpus should be split by scene and time rather than by randomly adjacent frames. Near-identical video frames in train and test create data leakage: the model appears to generalize because it sees virtually the same pallet, package, camera view, and lighting in both partitions. Ultralytics’ benchmark practice checks for exact and near-duplicate images across splits and removes confirmed leakage.[49]

Judgment — **Proposed allocation —** Allocate 30,000 images to training, 5,000 to validation/model selection, 5,000 to INT8 calibration, and 10,000 to a locked test set. Stratify the allocation by target type, class, SKU family, camera, viewing angle, shift, illumination, label scale, package material, damage severity, and occlusion. Group adjacent video frames, the same physical item, and the same capture sequence before allocation, and place each group in one partition only.[49][50]

Each candidate needs a matched FP16 and INT8 version. “Matched” means the same trained checkpoint, class definitions, image preprocessing, input dimensions, letterbox or resize policy, postprocessing algorithm, NMS or clustering thresholds, confidence thresholds, maximum detections, and evaluation set. TensorRT supports FP16 and INT8, while DeepStream states that FP16 requires only the mode change and INT8 requires an INT8 calibration cache.[51][17]

The comparison should report per-class AP and mAP for at least pallet label, package damage, and any subtypes that have enough examples for meaningful evaluation. AP measures the normalized area under a precision–recall curve for one category.[1] mAP should be reported with an explicit definition—preferably COCO-style mAP50-95 and mAP50 as a secondary operational measure—because DetectNet_v2 can use either SAMPLE, based on 11 recall points as in Pascal VOC 2007, or INTEGRATE, as used in the 2011 challenge.[6][41]

Ultralytics exposes per-category mAP50–95 and image-level precision, recall, true positives, false positives and false negatives for separate pallet-label and package-damage reporting.[126]

TAO DetectNet_v2’s evaluator allows configurable per-class IoU validity thresholds, which must be recorded alongside its AP convention when comparing class-level results.[6][122]

Derived — Define the principal quantization result as mAP degradation in percentage points: INT8 mAP minus FP16 mAP, evaluated on the identical held-out warehouse images. A negative result means the INT8 engine lost mAP. Report the same calculation per class, because an acceptable aggregate mAP loss can conceal an unacceptable package-damage loss.

The accuracy table should have the following fixed structure.

Precision must be reported at a stated operating point. Ultralytics notes that its validation summaries use the confidence threshold that maximizes F1, while confusion-matrix results use an explicit confidence threshold or a default of 0.25.[37] This distinction is material.

A target such as 92% precision means the installed system must predeclare the threshold, IoU rule, class, and camera population at which 92% is measured.

Judgment — Use two precision reports for each target: (1) precision at the model’s maximum-F1 threshold to describe its best balanced operating point; and (2) precision at the fixed production threshold chosen to control false alarms. Report recall beside both. A 92% precision claim without recall can represent a detector that simply rejects most difficult cases.

INT8 calibration images must be representative of deployed imagery. TensorRT’s post-training quantization calculates activation scales by running representative inputs through the network and collecting activation statistics.[50] NVIDIA’s TensorRT documentation says the amount of data required is application-dependent; its ImageNet classification example refers to about 500 images.[50] Ultralytics’ Jetson guidance says NVIDIA recommends at least 500 images and its example uses 1,000; an Ultralytics maintainer separately advises at least 1,000 dataset images to represent variability.[54][55]

Ultralytics’ YOLOv8 TensorRT exporter uses images from the configured validation split for INT8 calibration by default and emits them at the deployment input shape; its exporter documentation recommends more than 300 calibration images.[127][5]

Ultralytics’ exporter warns when fewer than 300 calibration images are supplied for relevant INT8 export formats.[127]

For this warehouse, use the 5,000-image calibration split proposed above rather than a generic COCO subset. It should include all camera geometries, day and night shifts if applicable, light states, reflective labels, damaged and undamaged packaging, low-contrast defects, partial occlusion, common backgrounds, and difficult negative examples. TensorRT warns that calibration batch size and ordering can affect entropy-calibration scales; it recommends the largest feasible batch and randomized batches with similar distributions.[50] `IInt8EntropyCalibrator2` is TensorRT’s recommended entropy calibrator for CNNs and is required for DLA.[50]

Warehouse calibration should cover pallet labels at the lowest expected pixel height, oblique views, barcode reflections, label tears, shrink-wrap occlusion and motion blur, as well as subtle dents, punctures and wet package surfaces.[128]

Calibration should use the same preprocessing as training and inference. NVIDIA’s DetectNet_v2 and EfficientDet documentation both state that their recommended calibration route uses training preprocessing and random sampling across the training dataset.[6][11] This controls a frequent failure mode: calibration on visually clean or differently resized images can make activation scales unsuitable for glare, small text, dark cartons, or damaged surfaces.

QAT should be a fallback experiment when post-training quantization (PTQ) causes an unacceptable loss. TensorRT describes QAT as simulating quantization during training, allowing the model to compensate for quantize/dequantize effects; it generally achieves better accuracy recovery than PTQ but needs the full labelled training dataset and more training time.[50] YOLO supports INT8 QAT with `quantize=8`, and TAO DetectNet_v2 supports QAT through `enable_qat`.[56][6]

Latency needs two reported boundaries. The first is isolated engine latency: input already resident in memory, preprocessing and postprocessing either excluded or separately measured, with warmed-up TensorRT execution. TensorRT advises at least three warm-up iterations because CUDA kernel JIT compilation and engine deserialization are one-time costs.[57] The second is full pipeline latency from frame arrival to emitted detection metadata. DeepStream’s own performance definition includes capture and decode, preprocessing, batching, inference, and postprocessing to generate metadata.[58]

A specified reproducible benchmark configuration for a Jetson AGX Orin 64 GB module uses MAXN mode, fixed clocks, batch size 1, 500 warm-up runs and 200 timed runs, with GPU-compute and end-to-end timings reported separately.[129]

Record mean, median or p50, p95, p99, minimum, maximum, and sample count. The p95 and p99 values are important because a system that averages 20 ms but periodically stalls for hundreds of milliseconds can build queues and trigger drops. DeepStream has frame-latency APIs enabled through `NVDS_ENABLE_LATENCY_MEASUREMENT=1` and component-latency APIs enabled through `NVDS_ENABLE_COMPONENT_LATENCY_MEASUREMENT=1`.[17]

A clean isolated-engine benchmark can use `trtexec` and CUDA event timing. NVIDIA’s TensorRT example records CUDA events before and after inference, synchronizes the stream, and averages timing over repeated runs.[59] A DeepStream system benchmark should separately log decoder-to-sink buffer latency when needed, using pad probes at decoder input and output sink components.[7]

The timing report should identify every condition that changes performance:

- **Hardware and module:** Record AGX Orin model, memory capacity, carrier board, storage, camera interfaces, active or passive cooling, and enclosure. The 32 GB and 64 GB modules have different listed CUDA core counts, tensor core counts, maximum GPU frequencies, and power envelopes. [35]

- **Software stack:** Record JetPack, CUDA, TensorRT, cuDNN, DeepStream, TAO version where applicable, model-export version, and plugin versions. TensorRT engine behavior is tied to its build runtime, and TAO requires engine regeneration after model or TensorRT/CUDA changes. [5][45]

- **Model path:** Record exact checkpoint hash, input dimensions, class map, FP16 versus INT8, PTQ versus QAT, calibration-set identity, engine build flags, DLA or GPU assignment, batch profile, NMS or clustering configuration, and confidence thresholds. TensorRT’s optimization decisions depend on model, precision, batch size, and GPU. [4][50]

- **Video path:** Record source codec, resolution, fps, transport, decode engine use, `live-source`, streammux batch size, inference interval, tracker configuration, output sink configuration, and whether rendering is disabled. DeepStream recommends matching `nvstreammux` batch size to connected sources or primary inference batch size. [7][17]

Power must be measured under the same test that establishes throughput. AGX Orin’s published 15–40 W and 15–60 W figures are configurable module ranges for the 32 GB and 64 GB variants.[35] They are not the wattage of a warehouse video pipeline. A sustained power result should state whether it measures module input, carrier-board input, or full cabinet input, because those boundaries produce different values.

`tegrastats` can log Jetson telemetry at a configured interval; the default is 1,000 ms.[60] For AGX Orin it reports GPU activation proportion and the frequencies of the GPU’s graphics processing clusters, while it also reports memory-controller bandwidth usage and frequency.[60] Use at least one-second telemetry for the full overnight-scale soak test and a faster external meter for shorter transients if the hardware supports it.

Judgment — Run each full-load test long enough to reach thermal equilibrium, not merely until initial fps stabilizes. Report steady-state median watts, p95 watts, peak watts, temperature, clock-frequency behavior, average aggregate fps, p95 frame latency, and dropped frames over the same interval. Repeat after cold start and after the system has been heat-soaked in its installed enclosure.

Cooling is a required test condition. NVIDIA’s DeepStream performance guidance says devices must be properly cooled to achieve peak performance.[58] The related Orin NX YOLO study used active cooling and warned that passive deployment enclosures could throttle earlier.[8] Under sustained load, dynamic voltage and frequency scaling can constrain throughput when a power or thermal threshold is reached; an Orin Nano concurrency study observed non-linear throughput behavior when the device reduced throughput to keep power within a ceiling.[61]

The full 200-camera test should use 200 representative live streams or replayed recordings that preserve actual codec, frame rate, resolution, scene complexity, and object density. DeepStream reports FPS per stream; its console’s unbracketed value is the average for the most recent five seconds and the bracketed value is the whole-run average.[7] Report aggregate completed frames per second in addition to per-stream fps, because 200 cameras can each appear near nominal while a subset drops heavily or falls behind.

Derived — The pass condition for all-frame detection is: 200 streams × 30 fps = 6,000 delivered and inferred frames per second, with `interval=0`, no unaccounted source or QoS frame drops, and latency within the client’s operational limit. If tracking and interval skipping are used, report detector fps separately from video-output fps; they answer different questions.[17]

The test should use batched multiplexing, not 200 isolated inference processes. DeepStream defines `nvstreammux` batch size as the number of frame buffers grouped in one muxed buffer and recommends matching it to source count or the primary inference batch size.[7] A concurrent-workload study found that batching increases throughput with diminishing returns, while increasing independent process count can create time-sharing, preemption, deferred scheduling, and rising memory consumption.[61]

**Conclusion — the required evaluation is a paired FP16/INT8 accuracy test plus a full-pipeline soak test.** The paired test produces pallet-label and package-damage mAP degradation, precision, recall, and separate SKU-recognition results on the locked warehouse test set. The soak test produces completed detector throughput, per-stream latency distribution, drops, thermal behavior, and sustained power at the intended stream count.[17][7][60] This method makes all three detector stacks comparable on the criteria that decide the warehouse deployment.

If inventory actions depend on SKU identity, evaluate a separate recognition stage on cropped detected labels, reporting detection recall, recognition accuracy conditional on a correct crop, and end-to-end SKU correctness. DetectNet_v2 target-class mapping groups source classes into target classes and is not a barcode or text-recognition result.[6]

Measure TensorRT gain in two separate paired comparisons: framework-native FP16 execution versus TensorRT FP16 isolates graph compilation and runtime optimization, while TensorRT FP16 versus TensorRT INT8 isolates quantization. Hold the checkpoint, input resolution, preprocessing, postprocessing, batch profile, and confidence threshold constant in each comparison.

### What the 50K-image warehouse dataset and the 200-camera requirement

The 50,000-image corpus is large enough to support model training, calibration, and a meaningful held-out test population if its labels reflect the installed cameras. DetectNet_v2 requires KITTI or COCO conversion to TFRecords and has fixed input-format constraints.[6] YOLOv8 accepts a dataset YAML identifying training and validation paths, class names, and class count.[37] EfficientDet’s TensorRT calibration route similarly depends on a representative training-data distribution and matching preprocessing.[11]

Pallet labels and package damage are not identical detection problems. A pallet label is often a small, rectangular, high-contrast target with variable glare, skew, occlusion, barcode detail, and text scale. Package damage can be subtle, irregular, low-contrast, and visually confounded with tape seams, shadows, folds, printing, and surface texture.Judgment — The training label taxonomy should separate visible damage types where operations require separate actions, such as torn carton, crushed corner, puncture, open seam, wet stain, and missing label, rather than using one broad damage box that hides operational failure modes.

Judgment — Camera geometry is part of model selection. Before choosing a detector family, measure the distribution of pallet-label widths and heights in source frames and the distribution of damage-region sizes. If important targets fall below roughly 16 pixels after resize, DetectNet_v2’s documented object-size guidance makes it a poor default.[43] If labels are small at 640 pixels but adequately resolved at 1024 pixels, test EfficientDet-D4 or a higher-resolution/tiled YOLOv8 configuration rather than accepting a lower-resolution detector’s false negatives.[10][20]

The 200-camera target also changes the architecture decision. The AGX Orin camera-interface specification of up to six cameras, or 16 through provisional virtual channels, concerns directly attached camera interfaces; it is separate from the number of network-video streams a DeepStream pipeline can ingest and process.[35][17] A 200-camera warehouse therefore requires distributed edge nodes or edge aggregation with central GPU inference, not 200 direct camera attachments to one module.[35]

Judgment — Start capacity planning with a node budget, not a single-device benchmark. Determine how many cameras each AGX Orin can process at the target resolution, detector interval, and accuracy target under sustained thermal conditions. Divide 200 by that measured per-node camera count, round up, and add headroom for failover, model rollouts, peak object density, and camera reconnect storms.

NVIDIA’s warehouse RT-DETR documentation gives a useful planning anchor: one AGX Orin iGPU is estimated at four 30-fps streams for that different detector.[1] DeepStream’s own AGX Orin RT-DETR benchmark lists 39 GPU fps on sample 1080p H.265 video with FP16, 544×960 inference resolution, and an MV3DT tracker.[58] These are not substitute results for the three requested detectors, but they show that real warehouse video analytics capacity is commonly counted in single-digit streams per embedded module rather than hundreds.

Judgment — The physical architecture should reserve GPU compute for the primary detector, use hardware decode for compressed streams, disable display rendering, transmit metadata rather than rendered video where possible, and use tracking only where validation shows it does not miss required events. This is the most practical route to maximize camera density without confusing a high displayed video fps with a high detector-inference rate.

Monthly new-SKU learning, the below-100 MB cellular OTA constraint, and the ability to maintain precision above 92% belong to the following sections because they involve model lifecycle, artifact packaging, and active-learning policy rather than this section’s measured performance comparison. Their immediate consequence here is that every performance candidate must retain reproducible model, engine, calibration, and dataset metadata. TensorRT engines are hardware- and runtime-specific, and TAO requires regeneration when a model or relevant runtime changes.[5][45]

**Conclusion — the dataset and camera fleet make this a system-engineering decision, not a model-zoo choice.** The detector must be selected jointly with camera resolution, target-pixel size, engine precision, stream batching, cooling, and the number of AGX Orin nodes.[10][43][7][8] A smaller detector that meets the required held-out precision at a higher camera density is operationally preferable to a larger detector whose isolated mAP is higher but whose node count, power, or latency prevents deployment at scale.

Derived — At the cited reference capacity of four 30-fps RT-DETR streams per AGX Orin, the 200-camera requirement would require 50 modules before failover headroom.[1][18]

### Synthesis

**YOLOv8 should be benchmarked first because it combines the clearest TensorRT/DeepStream route with related package-label evidence, while TAO DetectNet_v2 should be retained as the NVIDIA-native operational comparator and EfficientDet-D4 should be reserved for a demonstrated small-target accuracy advantage.** None of the three has a supplied AGX Orin result for INT8 latency, paired FP16-versus-INT8 warehouse mAP, sustained power, or 6,000-fps delivery across 200 cameras.[8][9][38][10][6][11][35][1] The governing acceptance test is therefore a paired engine-accuracy evaluation on the held-out warehouse images followed by a thermally sustained, headless, multi-stream DeepStream soak test with interval 0, delivered-frame accounting, latency percentiles, power telemetry, and dropped-frame reporting.[17][8][7][60]

## Monthly new-SKU model updates

Monthly **class-incremental learning** applies only when a new SKU requires a newly introduced detector class that must be recognised alongside all prior classes at inference time. A new SKU that merely changes the appearance of an existing pallet-label, SKU, or package-damage class is a **domain-incremental** update: it adds new examples for an existing class rather than expanding the detector’s class taxonomy. DetectNet_v2 can map similar source classes to an existing target class, and YOLO’s `cls_remap` retains matching named classification-head rows across dataset revisions. In both cases, the candidate must pass the frozen old-SKU regression gate; YOLOv8 does not natively provide experience replay, so retaining and mixing representative historical examples remains an explicit operational control.[62][6][52][63] The central failure mode is **catastrophic forgetting**: training on newly arrived images changes shared weights and reduces performance on earlier classes. Checkpoint resumption is useful operationally, but it is not continual learning because it restores a training job rather than protecting old-SKU behaviour.[64][65]

Judgment — Use the same six-stage release contract for all three stacks: (1) human-review and approve new-SKU and package-damage labels; (2) train with a representative replay set of labelled historical pallet-label, SKU, and damage examples, or use an old-model distillation retention control; (3) gate the candidate separately on frozen old-SKU, new-SKU, pallet-label, and damage holdouts; (4) version the calibration data or QAT ranges, class-label file, model checkpoint, TensorRT engine, and serving configuration as one release manifest; (5) canary the signed release on a camera subset; and (6) retain an immutable prior artifact set and use atomic model-level activation with rollback. Replay mitigates catastrophic forgetting by replaying stored exemplars, while distillation uses the prior model’s outputs as soft labels for old tasks. TensorRT engines require trusted delivery and compatible TensorRT and GPU environments. Mender supports customized Jetson software updates, and its A/B update design installs a release completely or not at all and rolls back after failed installation; apply those atomicity and rollback properties to the model-artifact activation layer. “Precision” should be monitored with recall and mAP, because a model can obtain high precision simply by returning few detections.[65][66][67]

### How robust is YOLO v8’s model update pipeline for incremental

YOLOv8 provides a usable model-lifecycle toolchain: a unified Python API and command-line interface, custom-data training, validation, inference, export, and benchmarking modes. Training records metrics, plots, and checkpoints in the run directory and can stream them to Comet, ClearML, TensorBoard, MLflow, Weights & Biases, and DVCLive.[15][37][52]

YOLOv8’s detection-validation interface exposes mAP75 and per-class mAP50–95, as well as per-image precision, recall, F1, true positives, false positives and false negatives.[126]

YOLO checkpoint resumption restores model weights, optimizer state, learning-rate scheduler, and epoch number. Checkpoints are saved after every epoch by default or at the configured `save_period`, and an interrupted run can resume by loading the latest checkpoint and setting `resume=True`.[52] This makes recovery from a failed training job straightforward; it does not make a monthly new-SKU update safe if the next job excludes historical examples.

YOLOv8 also has two useful fine-tuning controls. First, `cls_remap` copies classification-head rows for matching class names when class count or ordering changes; matching classes retain learned biases and, if head width is unchanged, weights. Second, `freeze` can freeze the first N layers or selected named layers, reducing the parameters changed during fine-tuning.[52] These controls can reduce unnecessary disruption during a dataset revision, but they do not protect complete detector behaviour across sequential class updates.

Ultralytics explicitly states that YOLOv8 does not natively support incremental learning or experience replay. It suggests a custom mini-batch routine that mixes a subset of new data with a random subset of old data.[63] Community guidance reaches the same operational conclusion: all classes that the model must detect should be represented during training, because a model trained later without an earlier class’s examples may cease detecting it.[68]

The practical risk is visible in a reported YOLOv8 sequence: a user trained YOLOv8m for 50 epochs on just over 5,000 person images with a one-class YAML configuration, then trained from that run’s `best.pt` for 50 epochs on just over 5,000 car images using a YAML configuration with `nc: 2` and the names person and car; person detection was lost despite attempts to freeze 5, 10, 15, and 20 layers.[68] A separate user report described mini-batch rehearsal achieving 100% precision but low recall, with best F1 only near a 0.12 confidence threshold.[68][63] That result illustrates why the release gate must include recall, F1, and per-class error review rather than accepting high precision alone.

A research path exists for reducing forgetting. Shmelkov et al.’s 2017 ICCV method trains on the new class while using a frozen prior detector to produce distillation targets for old classes. On VOC 2007, adding one class with distillation achieved 68.3% mAP on old classes and 67.8% overall mAP; the no-distillation update achieved 25.0% mAP on old classes, while the jointly trained baseline achieved 69.6% overall mAP. Adding five classes sequentially produced 62.4% mAP versus 65.9% when they were added together, demonstrating that repeated sequential releases can compound loss relative to a combined-data update.[64] This method was evaluated with Fast R-CNN, not YOLOv8, so it is an engineering design to implement and test rather than a built-in YOLO capability.[64]

For deployment, YOLO can be made operationally robust through release controls. A reported YOLOv8-on-Jetson-Orin operation retrained weekly and used two devices per line: the candidate ran in parallel for one hour, a supervisor compared frame-level predictions, the second device was updated only when divergence remained within an acceptance envelope, and failed candidates were rolled back automatically.[69] NVIDIA states that TensorRT engine files are executable artifacts containing compiled CUDA tactics and must be deserialized only when built by the deployer or received through a trusted channel.[66] The export and deployment environments should be version-pinned: Ultralytics advises using the same Ultralytics version for export and deployment, while TensorRT plans normally fail to deserialize if their recorded TensorRT version or GPU compute capability conflicts with the runtime environment.[66][55]

**YOLOv8 is moderately robust for monthly SKU updates only when replay-based retraining, frozen regression sets, version control, staged rollout, and rollback are added around it; it is not robust as an out-of-the-box incremental-learning system.** The deciding control is explicit old-SKU retention testing; a warehouse trial showing stable old-SKU and new-SKU precision, recall, and mAP through repeated monthly releases would improve this verdict.[63][68][69][64]

Derived — In the cited VOC 2007 incremental-detector study, adding five classes sequentially rather than together incurred a 3.5-percentage-point mAP penalty, or 5.3% relative to the jointly added result.[64]

Additional lifecycle tooling can shorten the operational path around YOLOv8: Roboflow describes dataset versioning, preprocessing, augmentation, training, evaluation, deployment, and run comparison in one workflow; it also supports uploading trained weights as a hosted versioned asset.[70][71] Roboflow describes an active-learning pattern in which production frames the model gets wrong are sampled, added to the dataset, and used to retrain the model, while Label Assist drafts annotations for human review.[71] This supports data collection and review for monthly SKU releases; it remains a retraining workflow, so the approved replay set and old-SKU release gates remain required.[71][63][68]

The YOLO update run should preserve its final training phase as well as its data mix: YOLOv8 uses online mosaic augmentation, and the documented practice is to disable mosaic for the final ten epochs because retaining it throughout training degrades performance.[71]

Parallel release path — For YOLOv8, human-approved new labels and a labelled old-example replay set are mandatory inputs; Ultralytics states that YOLOv8 has no native experience replay and identifies manual mixing of new and old data as the workaround. Gate each release separately on old-SKU, new-SKU, pallet-label, and damage holdouts. Promote a manifest-versioned QAT calibration range or calibration dataset, label taxonomy, checkpoint, TensorRT engine, and deployment configuration through a signed canary; retain the immutable preceding artifact set for atomic rollback. YOLOv8 QAT checkpoints carry quantization ranges into INT8 export, so QAT export does not require calibration data. A reported Orin deployment used a one-hour parallel candidate run and automatic rollback when prediction divergence breached its acceptance envelope.[63][56][69][66][67]

A 2025 YOLOv8 fine-tuning study reported negligible forgetting without Elastic Weight Consolidation (EWC) or Learning without Forgetting (LwF): standard fine-tuning produced that outcome in its experiment. The authors state that the adaptation–forgetting balance differs with model architecture, pre-training dataset, and target domain.[72]

The release acceptance report should also record false-alert rate, latency, memory use, and TensorRT engine size alongside per-class precision, recall, and mAP. Preserve the dataset manifest, training parameters, ONNX export, TensorRT build settings, engine hash, and validation report with the source checkpoint and calibration-set identity so that an accepted release can be reproduced.

The YOLOv8 exporter defaults its confidence threshold to 0.25 unless specified, while its NMS IoU setting comes from the prediction configuration; both settings need to remain fixed between FP16 and INT8 release evaluations.[127]

A monthly SKU programme is class-incremental learning: new classes arrive sequentially while the detector must retain earlier classes under bounded resources.[73] The release scorecard should separately report new-SKU acquisition and old-SKU retention: per-class precision, recall, and AP; macro-F1 or balanced accuracy for class imbalance; average performance across release cohorts; and forgetting, defined as each cohort’s maximum performance drop from its prior peak.[73] Replay-based learning mixes current examples with stored or synthetic earlier examples and is among the most effective anti-forgetting strategies; knowledge distillation instead trains the updated model to match the prior model’s outputs or intermediate representations while learning new labels.[73] These controls address the stability–plasticity dilemma: retaining old knowledge while adapting to new information.[73]

A production data loop can send frames to a labeling tool with weak labels from the current model, have human reviewers correct those labels, and append the corrections to the training set with date and reviewer tags.[69]

A monthly audit of a random 200-frame slice can check for label drift, missed corrections, and class imbalance before the next YOLOv8 update.[69]

Every TensorRT-based YOLOv8 refresh requires model re-export, engine rebuilding, quantization-aware-training validation, and on-hardware profiling; TensorRT is consequently best aligned with a fixed target GPU and an architecture stable for weeks or months.[25] The monthly release pipeline should make those build-and-validation steps mandatory before canary deployment rather than treating a newly trained checkpoint as a deployable Jetson artifact.[25]

On COCO, an incrementally trained detector achieved 37.4% mAP at IoU 0.5 and 21.3% mAP averaged over IoU thresholds 0.5–0.95, versus 38.1% and 22.6%, respectively, for a model trained on all 80 classes.[64]

### How robust is EfficientDet-D4’s model update pipeline for incremental learning

EfficientDet-D4 supports conventional transfer learning and continued training. Google’s EfficientDet instructions specify fine-tuning from an existing detector checkpoint using `--ckpt` rather than a backbone-only checkpoint, and state that rerunning training continues toward the configured maximum `num_epochs`.[33] The original EfficientDet work trained and evaluated on COCO 2017, which has 118,000 training images, using SGD with 0.9 momentum and 4e-5 weight decay.[10] These are established training controls, not a monthly warehouse update policy.

The wider TensorFlow ecosystem provides configurable model-development components. TensorFlow Model Garden offers model code to test, train, and retrain models; experiment definitions can use Python commands or YAML configuration. Orbit supports custom TensorFlow 2.x training loops, checkpoint saving, evaluation, summaries, and distributed execution across CPU, GPU, and TPU devices.[74] NVIDIA also publishes an EfficientDet PyTorch implementation with training, benchmarking, and inference scripts runnable in a Docker container.[75]

These tools make EfficientDet-D4 workable for a team that owns its training system.Judgment — A monthly D4 release should begin with a versioned prior checkpoint, then train with the new monthly SKU and damage set plus replayed old-SKU examples. Each candidate should be assessed on separately frozen historical-SKU and incoming-SKU sets, as well as a combined operational test set that contains varying label scale, package condition, lighting, occlusion, and camera viewpoint.

Catastrophic forgetting remains the deciding risk. Replay-based continual learning stores earlier examples and replays them during updates; it requires buffer memory and can overfit if stored examples do not cover the original input space.[65] Distillation is the alternative when historical image retention is restricted: the old model’s outputs become soft targets while the new model learns the new task.[65][76] Neither replay nor distillation is presented as a native EfficientDet-D4 lifecycle function in the supplied D4 tools.

The sequential-learning evidence gives the appropriate expectation. The incremental-detector study reports that repeated class additions can work with a moderate drop relative to a model trained on the combined dataset.[64][76] Its VOC 2007 experiment produced 62.4% mAP after five sequential additions compared with 65.9% when those five were added together, and its one-by-one class-addition sequence generally declined from 67.1% to 49.0% mAP across ten additions.[64] The study used Fast R-CNN rather than EfficientDet-D4, but it establishes why D4 releases require old-class regression gates.

D4 introduces deployment engineering risk as well. An NVIDIA TensorRT issue reported that the EfficientDet-D4 `create_onnx.py` sample failed in `update_shapes()` for a fine-tuned D4 checkpoint, while the reporter did not see the same failure with D7; a code workaround produced an engine but did not establish that the graph was optimal.[77] A separate TensorFlow issue reported a D4 custom-data run that completed without error but detected nothing, with near-zero AP and AR in the user’s reported evaluation.[78] These cases make export validation and post-export accuracy comparison mandatory release steps.

JetPack’s Triton Inference Server supports multi-framework inference and live model updates with zero inference downtime.[13] This is a serving capability, not a learning-retention mechanism. TensorRT engine plans record TensorRT build version and GPU compute capability, and mismatches can cause deserialization failure; version-compatible engines can be slower than engines built for a specific runtime.[66] The monthly release package should therefore contain a signed engine built for the deployed AGX Orin software image, a manifest of TensorRT/CUDA/JetPack versions, validation results, and the prior known-good engine for rollback.

**EfficientDet-D4 is moderately robust when the organisation builds the missing lifecycle controls; it has conventional checkpoint fine-tuning but no native continual-learning, replay, promotion, or rollback pipeline.** It is the weakest practical choice of the three for teams seeking a ready-made monthly-update path, because its TensorFlow/AutoML configuration and TensorRT export route demand more custom engineering.[33][65][19][77]

Derived — Across the cited VOC 2007 sequence from the initial 10-class model through ten one-by-one additions, mAP fell from 67.1% to 49.0%: an 18.1-percentage-point, or 27.0%, decline.[64]

The TensorRT conversion route is an additional lifecycle constraint for EfficientDet-D4. The NVIDIA TensorRT EfficientDet sample follows TensorFlow SavedModel-to-ONNX-to-TensorRT conversion and is deprecated as of TensorRT 10.14 because of `tf2onnx` dependency compatibility problems.[18] This makes a pinned, independently validated conversion container and engine-regression test a release prerequisite for every D4 update.[18][66]

Parallel release path — For EfficientDet-D4, human-approved new labels, a versioned old-example replay set or old-model distillation control, and separate old-SKU, new-SKU, pallet-label, and damage gates form the retention process. Fine-tune from the approved detector checkpoint, then version the INT8 calibration dataset, label taxonomy, model, TensorRT engine, and serving configuration together. Canary the signed engine on a camera subset and preserve the immutable prior artifact set for atomic rollback. EfficientDet documents fine-tuning from an existing detector checkpoint and continued training; replay and distillation provide the retention controls. JetPack Triton supports live model updates, while TensorRT plans require compatible runtime and GPU environments and trusted delivery.[33][65][13][66][67]

Monitor false package-damage alerts, missed labels, confidence-distribution shift, latency, and device health during the canary and fleet rollout, not only offline accuracy. The release artifact should identify the exact EfficientDet implementation and version, input transformation, TensorRT build recipe, and signed hashes in addition to the checkpoint, label map, calibration set, engine, and validation report.

### How robust is NVIDIA TAO DetectNet_v2’s model update pipeline for

NVIDIA TAO DetectNet_v2 is an NVIDIA-developed object detector included in the Transfer Learning Toolkit (TLT), the predecessor documentation line for the TAO workflow.[79] It supports pretrained-model transfer learning across resolutions and domains, loads matching weights from a prior TAO model, randomly initializes unmatched layers, and allows selected feature-extractor blocks to be frozen.[6] DetectNet_v2 therefore supports adapting a prior detector to a new warehouse dataset; it does not add a new SKU class without model training.

The TAO workflow has clear input and evaluation requirements. DetectNet_v2 accepts JPG, JPEG, or PNG images with KITTI detection labels; input width must be at least 480 pixels, height at least 272 pixels, and both dimensions must be multiples of 16.[6] Source class names can be mapped to target classes, including grouping similar classes under a common target label.[6] This grouping is useful only when SKU distinctions are not operationally required; if SKU identity matters, each required identity must remain separately labelled and evaluated.

DetectNet_v2 can resume an interrupted run from the latest checkpoint when invoked with the same command-line arguments, and checkpoint frequency is configurable through `checkpoint_interval`.[6] Its training diagnostics include mAP across classes, validation cost, and training cost; rising validation cost while training cost plateaus or falls indicates potential overfitting.[6] It supports a separate evaluation dataset through `validation_data_source`, allowing a frozen historical-SKU holdout to remain outside each monthly training set.[42] TAO Data Service is available for AI-assisted annotation, which can accelerate preparation of reviewed new-SKU frames.[80]

The release comparison must use one AP definition. DetectNet_v2 supports SAMPLE AP, the Pascal VOC 2007 11-point recall calculation, and INTEGRATE AP, the 2011 challenge-style calculation.[6]Judgment — The warehouse programme should choose one AP mode, IoU rule, confidence threshold, and class taxonomy before the first release, then preserve them across all monthly candidates; otherwise changes in reporting can masquerade as model improvement or regression.

DetectNet_v2 supports class-specific IoU thresholds in evaluation, so the threshold for each class must remain fixed when comparing monthly releases.[6]

TAO has the most integrated documented deployment route. The Finetuning Microservice automates model fine-tuning flows, and DeepStream SDK 9.2 can use TAO fine-tuned models through Inference Builder.[58] TAO model skills export checkpoints to ONNX, build a device-specific TensorRT engine with `trtexec` or `gen_trt_engine`, and pass the engine to DeepStream.[38] TAO also offers API-based Kubernetes execution for end-to-end model jobs, including multi-node GPU scaling, and TAO 7.1 introduced validation-metric-based best-checkpoint saving.[80][81]

This integration is not a retention guarantee. TAO’s pretrained DetectNet_v2 feature-extractor weights cannot be used for an object-detection application without retraining.[82] The documented DetectNet_v2 controls provide transfer learning, freezing, checkpoints, mAP measurement, and class mapping; they do not substitute for replayed historical examples or an old-SKU promotion gate.[6] For models with more than 10 classes, TAO notes that engineers may need to adjust the cost weight or balance samples per class, which reinforces the need to monitor new and old SKU classes separately.[81]

Deployment safety also requires a stricter process than simply replacing a file. A DetectNet_v2 TensorRT engine is machine-specific, and NVIDIA requires regeneration when the model, TensorRT libraries, or CUDA libraries change, including minor versions.[45] The exported label file must match the model output order, so changing the class list requires an aligned new label file and deployment configuration.[83] DeepStream’s on-the-fly model update supports zero application downtime, but it is alpha, limited to `deepstream-test5-app`, and assumes the replacement has the same network parameters.[84] It is not an adequate fleet rollback mechanism for monthly SKU changes that alter the output classes.

An external OTA system should provide atomic delivery and rollback. Mender describes operating-system A/B partition updates as atomic and able to roll back after failed installation.[67]Judgment — Apply the same release principle to model artifacts: stage the new signed engine and metadata beside an immutable prior engine, verify integrity and compatibility before activation, observe a canary camera group, and automatically restore the prior engine if the operational acceptance envelope is breached.

**TAO DetectNet_v2 is moderately robust for centrally trained monthly updates and has the strongest integrated training-to-DeepStream deployment path, but it still requires externally designed replay, validation gates, fleet rollout, and rollback controls to prevent old-SKU regression.** TAO is the preferred starting stack when NVIDIA-native deployment integration and managed lifecycle components outweigh the flexibility of a custom PyTorch or TensorFlow pipeline.[58][6][45][84]

TAO DetectNet_v2 adds documented data and compression controls to the monthly workflow. Its training and evaluation data are KITTI-format data converted to TFRecords; the converter lowercases class names, and the training class mapping must use those lowercase names or training can produce 0 mAP. DetectNet_v2 exposes `enable_qat` for Quantization Aware Training (QAT), which TAO defines as emulating lower-precision quantization during training to reduce subsequent lower-precision accuracy loss.[79][85] Before pruning, TAO recommends L1 regularization to make weights easier to prune; when retraining a pruned network, it recommends `NO_REG` regularization.[79]

TAO’s current deployment documentation specifies direct ONNX integration with DeepStream and states that `.etlt` is deprecated from TAO 5.0.0.[86] For each monthly class-taxonomy change, ship the model or engine together with the generated label file and DeepStream configuration, because label-file order must match prediction order.[86][79] Prebuilding the device-specific engine separates engine-generation time from deployment startup; direct model integration causes DeepStream to generate the engine automatically.[87][86]

TAO also supplies workflow components that reduce the engineering burden around centrally trained updates: TAO Finetuning Microservices deploy training workflows as scalable microservices; the Execution SDK dispatches training, evaluation, and AutoML workloads to NVIDIA Brev, SLURM, Kubernetes, and local Docker; and TAO Data Services provides annotation, augmentation, auto-labeling, and analytics tooling.[88][89][90] These components strengthen the operational update path, while replay-data composition and old-SKU promotion gates remain the controls that establish retention.[89][90][42][6]

Parallel release path — For TAO DetectNet_v2, human-approved KITTI labels, a versioned replay set or old-model distillation control, and distinct old-SKU, new-SKU, pallet-label, and damage gates are required before promotion. Version the INT8 calibration dataset or QAT configuration, generated label file, TAO checkpoint or ONNX model, Orin-specific TensorRT engine, and DeepStream configuration as one release. Canary the signed artifact set on a camera subset and retain the immutable prior set for atomic rollback. DetectNet_v2 supplies separate evaluation data and mAP diagnostics; TAO supplies the checkpoint-to-ONNX-to-device-specific-TensorRT-engine-to-DeepStream path. Its DeepStream on-the-fly update is alpha, restricted to identical network parameters, and therefore is not the rollback mechanism; use customized OTA delivery with atomic model-level activation and rollback.[42][6][9][84][67][66]

For a DetectNet_v2 release, preserve the selected calibration-data manifest and random seed alongside the TAO specification, batch settings, generated calibration cache, engine hash, and model hash so the INT8 build can be reproduced.[125]

Atomic rollback must restore preprocessing, post-processing, and detection thresholds together with the engine, label mapping, and configuration. A mismatched label map or threshold set can cause an apparent detection failure even when the TensorRT engine itself is correct.

### Synthesis

The three stacks support fine-tuning and checkpoint continuation, but none provides native, validated class-incremental learning that safely absorbs monthly new SKUs without historical controls. YOLOv8 offers the simplest custom workflow and flexible tracking integrations, yet Ultralytics states that incremental learning and experience replay are not native features.[52][63] EfficientDet-D4 offers conventional checkpoint fine-tuning but shifts the greatest lifecycle and export burden to the engineering team.[33][77] TAO DetectNet_v2 combines transfer learning, evaluation, TensorRT engine generation, DeepStream integration, API automation, and best-checkpoint selection most directly.[58][80][38][81]

1. **Conditional first choice: TAO DetectNet_v2 for an integrated NVIDIA training-to-Jetson lifecycle, subject to passing warehouse accuracy and throughput tests.** TAO provides automated fine-tuning flows, DeepStream Inference Builder support for fine-tuned models, a checkpoint-to-ONNX-to-device-specific-TensorRT-engine-to-DeepStream deployment path, and mAP and validation-cost training diagnostics. [58][38][6]
2. Choose **YOLOv8** when rapid custom experimentation and a mature PyTorch-oriented MLOps stack matter more than NVIDIA-managed integration.
3. Use **EfficientDet-D4** only if the team accepts ownership of TensorFlow configuration, incremental-learning controls, TensorRT export validation, and deployment automation.

If SKU identity is read from text on a pallet label rather than inferred from the label’s visual appearance, separate label localization from SKU recognition. The detector can locate the label while an OCR (optical character recognition) and catalog-matching stage identifies the SKU, avoiding a new detector class for each monthly SKU.

Where detector classes are needed, YOLOv8 can instead classify label templates, barcode or QR features, orientation, package families and damage types rather than assigning a detection class to every SKU.[126]

## Accuracy under the 100MB OTA limit

For this section, 100 MB means 100,000,000 decimal bytes, and the OTA pass/fail gate is a transmitted signed update below 100,000,000 bytes. Record three separate release quantities for YOLOv8, EfficientDet-D4, and DetectNet_v2: transmitted signed-update bytes, installed serialized TensorRT-engine bytes, and bytes for separately supplied runtime or rollback assets. TensorRT engine bytes depend on retained weights, per-tensor scaling metadata, and tactic-specific reformat or scale tensors; version-compatible deployment can also require a packaged lean runtime.[91][92] The practical accuracy floor is the lowest validated pallet-label and package-damage result that simultaneously meets the 100 MB transferred-update gate; it is a property of a chosen model, input resolution, compression method, calibration set, and deployment bundle rather than a universal detector number.

No candidate has a measured sub-100 MB package-size and held-out warehouse-accuracy pair, so every candidate’s practical accuracy floor is unmeasured.Judgment — Treat 100 MB as a release acceptance criterion: measure the transferred signed update, installed serialized engine, and separately installed runtime or rollback assets, then evaluate that exact artifact against the FP16 baseline on the held-out warehouse images.[91][92]

### What is the practical accuracy floor for YOLO v8 when

Across all three candidates, INT8 reduces storage pressure and can accelerate computation, but artifact composition means the final OTA size must be measured after export.[50][91] YOLOv8 offers a broad range of starting capacities and calibrated INT8 export; EfficientDet-D4 adds documented pruning and retraining; DetectNet_v2 has concrete sub-100 MB ResNet-18 weight-file examples plus QAT and pruning paths.[15][56][11][6][94]

The decisive comparison is not a universal compressed-model mAP floor. It is the candidate with a transmitted signed update below 100,000,000 bytes that preserves the prespecified pallet-label and package-damage requirements after export. **No candidate has an established numerical warehouse accuracy result for a deployable update below 100,000,000 bytes. DetectNet_v2 has reported ResNet-18 HDF5 training/model-file examples below that threshold, EfficientDet-D4 has raw-weight planning estimates, and YOLOv8 has calibrated INT8 export; selection requires the paired transmitted-package-size and held-out, class-specific accuracy result.**[94][33][5][91][92]

1. Export FP16 and calibrated INT8 candidates, then record transferred signed update bytes, installed serialized TensorRT engine bytes, and bytes for separately installed runtime or rollback assets. [91][92]
2. Validate each exported artifact on the same held-out warehouse split; report precision, recall, and mAP separately; accept only artifacts with at least 92% overall precision and an acceptable class-specific package-damage precision/recall trade-off. [18][96]
3. For models over 100 MB, apply QAT or pruning followed by retraining, then repeat the package-size and accuracy acceptance test.

Reserve device storage for the active and candidate releases during download, signature verification, installation, and rollback; the 100 MB transfer gate alone does not cover that local-storage requirement. Construct an accuracy-versus-artifact-size curve from several model variants and select the smallest release that meets predeclared per-class precision, recall, mAP, latency, and power gates.

There is no universal mAP50 threshold across datasets because identical values represent different performance levels on tasks with different difficulty.[96] The warehouse accuracy floor is consequently the operational acceptance threshold applied to each final sub-100 MB artifact: reject a candidate below 92% overall held-out warehouse precision or with an unacceptable package-damage recall-and-precision trade-off.[18][96] Precision is the proportion of reported detections that are correct, whereas mAP summarizes precision across recall levels and intersection-over-union thresholds; the 92% threshold is a precision requirement, not an mAP requirement.[18][96]

## TensorRT optimization gains

TensorRT is NVIDIA’s inference optimizer and runtime: it compiles a trained network into a serialized engine, meaning a hardware-specific executable optimized for one GPU, one TensorRT/CUDA software environment, a precision mode, and selected input shapes. Its practical gains come from layer fusion, reduced-precision arithmetic, dynamic tensor-memory management, and automatic kernel selection; enabling FP16 makes TensorRT attempt FP16 instead of FP32 wherever possible, although not all layer types support FP16. The relevant business outcome is more frames per second from a given Orin module, not an abstract TOPS rating.[4][5][50]

For this warehouse deployment, the useful comparison is an apples-to-apples **Engine Precision Pair**: the same trained detector, image geometry, batch or stream schedule, AGX Orin SKU, JetPack/TensorRT version, power mode, and post-processing path, run first as FP16 TensorRT and then as calibrated INT8 TensorRT. FP16 is a half-precision floating-point format; INT8 is signed 8-bit integer arithmetic. INT8 usually has lower memory traffic and faster compatible kernels, but calibration—using representative images to set numerical scales—can alter confidence scores, precision, recall, and mean Average Precision (mAP).[50][5]

### What TensorRT optimization gains does YOLO v8 provide on Jetson

YOLOv8 has the most direct TensorRT route of the three candidates. Ultralytics supports object-detection export to a TensorRT engine, and its configuration identifies `engine` as the TensorRT export format. DeepStream can then run that serialized engine through `nvinfer`, NVIDIA’s TensorRT-backed primary or secondary inference plugin.[5][37][17] The direct runtime API is the lowest-overhead production route when the application can own preprocessing, inference, and post-processing in one process; ONNX conversion creates a standalone TensorRT engine with less runtime overhead than Torch-TensorRT.[4]

TensorRT improves YOLOv8 execution by fusing compatible operations, choosing GPU kernels for the target device, managing activation memory, and selecting FP16 or INT8 where the graph and hardware permit. YOLOv8’s standard convolutional CSP-style backbone is also a favorable export target because standard CNN operations generally have better TensorRT support than custom transformer backbones with unsupported operators.[5][4][55] YOLOv8’s anchor-free head reduces the number of predicted boxes and accelerates Non-Maximum Suppression (NMS), the filtering step that removes overlapping duplicate detections.[19]

The strongest published YOLOv8 TensorRT Engine Precision Pair is an embedded YOLOv8n benchmark at 640-pixel input: mean prediction time at **batch 8** was 3.18 ms in FP16 and 2.30 ms in INT8.Derived — the INT8 prediction-time reduction is 27.7%, calculated as (3.18 − 2.30) ÷ 3.18, and the speed ratio is 1.38 times. Its COCO accuracy comparison used a separate **batch-1** validation run: mAP50 fell from 0.52 in FP16 to 0.46 in INT8 and mAP50–95 fell from 0.37 to 0.32. The batch-8 timing pair and batch-1 COCO accuracy pair therefore do not use the same batch condition. No native-runtime FP16-versus-TensorRT-FP16 comparison is reported in that benchmark.[5][97] Those values show the actual trade-off TensorRT deployment must manage: lower compute time and lower detection accuracy can occur together.

A separate YOLOv8n benchmark on Jetson Orin Nano 8GB, at 640 × 640 and batch 1, reports GPU-only latency of 20.88 ms for PyTorch FP32, 8.36 ms for TensorRT FP32, 4.43 ms for TensorRT FP16, and 3.49 ms for TensorRT INT8. It reported 286 FPS for TensorRT INT8 and 225 FPS for TensorRT FP16.[16] The benchmark reports GPU Compute Time only: PyTorch uses CUDA Events and TensorRT uses `trtexec` GPU Compute Time, both for GPU-kernel execution only; it excludes Python overhead, host-to-device transfer, and device-to-host transfer.[16] They demonstrate that TensorRT compilation and precision selection can materially improve YOLOv8 compute speed, while they do not represent camera-to-decision latency.

Published AGX Orin figures point in the same direction but use planning-grade sources and configurations. ### What TensorRT optimization gains does EfficientDet-D4 provide on Jetson AGX

EfficientDet-D4 is a different TensorRT engineering proposition. EfficientDet combines an EfficientNet backbone with a Bi-directional Feature Pyramid Network (BiFPN), which repeatedly fuses features across image scales, plus shared class- and box-prediction networks. Its compound scaling increases resolution, depth, and width together.[10] That design is parameter-efficient, but its complex topology can run slower on GPUs than FLOP counts alone suggest.[19]

NVIDIA documents an EfficientDet route in which an exported model is converted into a TensorRT engine for the target environment and used through DeepStream. The model artifact can travel between training and deployment systems, but each TensorRT engine is specific to a hardware configuration.[11] EfficientDet is not a bare-engine deployment: NVIDIA requires TensorRT open-source components, named plugins, a custom DeepStream bounding-box parser, label metadata, inference configuration, and DeepStream configuration.[11] This adds integration cost and creates more interfaces at which a monthly model release can fail validation.

TensorRT’s applicable optimizations are nevertheless the same core mechanisms: it compiles an engine for the target GPU, selects kernels per layer, fuses operations where possible, manages tensor memory, and can use FP16 or INT8 computation.[4][5][50] EfficientDet’s INT8 engine requires a calibration cache.

NVIDIA recommends the training data loader because it applies the training preprocessing and draws random batches across the training set; alternatively, a subsampled image directory must represent the training distribution.[11] TensorRT’s EfficientDet sample further states that more calibration images improve INT8 accuracy and reports that 5,000 images produced a good result for COCO-trained models.[103]

EfficientDet-D4 has a published TensorRT10 point of 33.55 ms on a T4 GPU at 1024 pixels, with 20.7 million parameters, 55.2 billion FLOPs, and COCO mAP50–95 of 49.7.[19] This illustrates that D4 is a high-resolution detector with a materially different input geometry from 640-pixel YOLOv8 tests.Judgment — Do not normalize D4’s expected AGX Orin latency from YOLOv8 FPS: a 1024-pixel multi-scale architecture changes memory traffic, kernel choice, post-processing behavior, and batching efficiency.

The EfficientDet-D4 TensorRT path has shown conversion sensitivity. A TensorRT issue reported that the EfficientDet Python sample’s `create_onnx.py` failed in `update_shapes()` for a fine-tuned EfficientDet-D4 checkpoint, while the issue author reported no equivalent failure for D7.[77] The user’s code change generated an engine, but the user did not know whether the graph was optimal.[77] An earlier TensorRT discussion also distinguishes exporter-produced inference models from TensorFlow Object Detection Zoo saved models, with the latter described as not optimized for inference.[104] These facts make model-export validation a release gate, not a formality.

TensorRT engine rebuilding is part of the D4 deployment lifecycle. NVIDIA states that a new engine is required when the model changes or the TensorRT/CUDA libraries change, including minor versions; use of an engine built against different TensorRT/CUDA versions is unsupported and can affect speed, accuracy, stability, or loading.[11] EfficientDet’s TensorRT performance should therefore be recorded with the exported graph hash, engine hash, plugin build, TensorRT OSS version, TensorRT/CUDA version, JetPack version, power mode, input dimensions, and batch profile.

TensorRT’s Global Performance Tuner can explore engine-builder routes, benchmark candidates, and optionally validate accuracy before selecting a route.[51] The tuner is particularly useful for D4 because its graph may offer multiple tactic choices and because plugin boundaries can obstruct fusion.

Per-layer profiling should inspect fusion and data-reformat kernels, since TensorRT can fuse several ONNX operations into one engine layer while adding device-to-device reorder work where layouts differ.[98]

TensorRT is the common acceleration layer for all three candidates: it creates target-specific engines, uses layer fusion, kernel selection, memory optimization, and FP16/INT8 precision, and must be rebuilt when the model or runtime changes.[5][11][9] YOLOv8 has the simplest direct path and the clearest related precision-pair benchmark; EfficientDet-D4 has the heaviest plugin and parser burden; DetectNet_v2 has the strongest integrated TAO-to-DeepStream deployment chain.[97][11][9]

## Edge active learning and the 92% precision target

Edge-based active learning is a workflow in which cameras retain selected frames for human labeling rather than sending every frame for review. It can reduce labeling effort and shorten response to new SKUs or damage appearances, but it is not itself a guarantee that a detector remains accurate after updates.

### Can edge-based active learning loops maintain pallet-label detection precision above

**No: active learning can prioritize pallet-label frames for incremental updates, but it cannot be credited with sustaining precision above 92% without periodic full-retraining gates.** Online active learning selects informative observations from a stream for labeling; incremental training then fine-tunes model parameters on a small new batch rather than restarting from zero. However, the incremental-learning review characterizes real-world task-agnostic incremental learning as early-stage, with no clear online real-time approach matching state-of-the-art results.[108][65]

Detection precision must be defined separately from mean average precision (mAP). For pallet labels, precision is the proportion of emitted pallet-label detections that are correct under a declared intersection-over-union (IoU) box-match rule and a fixed confidence threshold. mAP aggregates precision across classes and IoU thresholds, so it cannot establish a 92% operational precision target by itself. Ultralytics validation summaries also report precision at the threshold that maximizes F1, rather than necessarily at the deployed threshold; changing a confidence threshold changes the false-positive/recall trade-off.[37][20]

A practical pallet-label loop should use a batch, rather than update per camera frame, because batch-mode active learning is generally more efficient for image detection and permits diversity controls. The selection batch should combine uncertain detections, disagreement between models or model versions, diversity across cameras and lighting, and examples from new-SKU conditions. It should also retain a random-review control sample: highly ranked examples can be redundant, and random batch selection has outperformed active methods on some datasets.[109][108]

After expert annotation, fine-tune on the selected pallet-label images plus a replay buffer of older warehouse examples. Replay means retaining representative old images and labels so that learning new SKUs does not erase performance on existing labels; class-incremental systems use such a memory buffer and a forgetting constraint for that purpose. Increase the labeling rate after detected drift, since a changed operating condition requires more representative observations before the model can be safely adapted.[108][65]

The release gate must be independent of the update data. First, evaluate every candidate update on a temporally forward, manually labeled holdout set stratified by camera, site, label size, illumination, occlusion, and newly introduced SKUs. Second, monitor the same fixed-threshold precision on newly labeled production samples before adding those samples to training. Third, roll back a version that fails the 92% gate and trigger complete retraining when labeled monitoring identifies persistent drift or accumulated forgetting. Unlabeled drift monitoring can flag input-distribution changes, but it cannot fully identify a change in the input–label relationship or verify precision.[108][65]

For the documented TAO DetectNet_v2 `infer` subtask, confidence is not output and is generated as 0; its bounding boxes and class labels remain valid. Use an external score source or a DetectNet_v2 deployment path with usable confidence output for confidence-driven pallet-label sampling and confidence-threshold alarms.[81]

This makes incremental pallet-label updates feasible as controlled experiments between retraining cycles, but rules out treating active learning as a substitute for a fixed-threshold, independently labeled 92% precision service-level gate.

Acceptance protocol for pallet labels. Define a true positive (TP) as a pallet-label detection with the correct class and IoU at least 0.50 against one reviewed ground-truth box; define a false positive (FP) as an emitted detection not so matched; and calculate precision as TP/(TP+FP). Lock one deployed confidence threshold before the evaluation period, rather than using the validation threshold that maximizes F1.
For each calendar month, randomly sample and expert-label enough production frames to obtain at least 400 emitted pallet-label detections, stratified by camera, site, label size, illumination, occlusion, and new-SKU status. Promote or retain an incremental update only if observed monthly precision is at least 95% and the two-sided 95% Wilson interval lower bound exceeds 92%; with 400 emitted detections and 95% observed precision, the Wilson lower bound is approximately 92.6%. Also require at least 1,200 emitted detections in each rolling 90-day window, observed rolling precision of at least 94%, and a two-sided 95% Wilson lower bound above 92%; 1,200 detections at 94% observed precision give a lower bound of approximately 92.5%. These proposed gates use binomial Wilson intervals with the stated detection counts and observed precision rates. Because successive detections of the same pallet can be correlated, sample independent item, camera, and time groups or use a group-aware uncertainty calculation before treating a detection-count interval as a fleet-wide guarantee.[108] Evaluate every sampled frame before it enters an update batch, following test-then-train (prequential) evaluation.[108]

Roll back any candidate failing the monthly precision, rolling precision, or 90% recall gate. Start complete retraining after either a rolling-window gate failure or two consecutive failed incremental candidates; complete retraining trains a new model from scratch on all labeled data collected so far.[108]

Active learning is not a no-training mechanism: its closed loop is model training, selection of examples, label requests, and retraining, and it requires retraining and versioning infrastructure. Edge deployment can perform local selection of ambiguous samples for upload while reporting sample counts, bandwidth, and latency.[110]

Evaluate pallet-label precision over successive monthly releases against three controls: no update, random-selection updates, and periodic complete-retraining updates. Use informative and diverse active-selection batches, retain a random control because random batch selection can outperform active methods, and measure old-class forgetting with replay-buffer evaluation. Roll back an incremental candidate that fails the fixed-threshold gate; use broader complete retraining when a rolling gate fails or two consecutive incremental candidates fail.[109][108][65]

### Can edge-based active learning loops maintain package-damage detection precision above

**No operational claim of sustained package-damage precision above 92% is justified unless each incremental update passes a locked, independently labeled precision test.** Active learning has often reduced the number of labeled examples needed to reach a target accuracy in reported studies, but its selected training data are biased toward the model that chose them and may not represent the complete camera stream. The same literature reports mixed or negative active-learning results in some settings.[111][109]

Package damage is particularly exposed to drift: packaging materials, damage modes, lighting, camera angles, and SKU artwork can change both the input distribution and the meaning of visual cues. A drifted stream can make an existing model less accurate and can also make its sampling criterion less useful. When a real concept drift occurs, model update or replacement becomes necessary; complete retraining is normally used when new data are substantial or the prior model is no longer relevant.[108]

The package-damage loop should therefore operate as follows:

- **Select:** retain uncertainty, disagreement, and diversity cases, plus false-positive candidates and examples from rare operational slices. This avoids allowing common undamaged-package scenes to dominate review. [108]
- **Review:** obtain expert bounding-box and class labels. Label delay must be managed because slow annotation can cause redundant requests for similar frames, and annotation quality varies with case difficulty and annotator fatigue. [108][109]
- **Update:** fine-tune on reviewed cases plus a representative replay buffer, and measure forgetting rate as well as package-damage precision. Fine-tuning can preserve prior knowledge, but it does not ensure that it will do so. [108][65]
- **Promote or revert:** deploy only updates that exceed 92% package-damage precision on the untouched, time-forward holdout at the locked threshold and IoU rule; otherwise revert and expand labeling or run full retraining. [108]

DeepStream can restrict output by per-class confidence threshold, region of interest, and detected-object size. These filters may reduce false positives from irrelevant parts of a warehouse scene, but they can also suppress true damage detections; they are operating controls, not evidence that 92% precision is maintained.[17]

Pseudo-labeling can supplement expert review for high-confidence examples, but it carries confirmation-bias risk when incorrect predictions are reused as training labels. For package damage, where defects may be rare and visually ambiguous, human review of selected frames is the safer basis for the precision gate.[108][65]

This makes edge active learning useful for finding and labeling evolving damage cases; retain incremental deployment while its independent holdout precision gate passes, and use complete retraining when drift, new damage modes, or holdout precision failures exceed the incremental update’s capacity.[108]

### Synthesis

**The decision is conditional: use edge active learning to reduce labeling demand, but allow incremental deployment only while fixed-threshold precision remains above 92% on independent, newly labeled warehouse data.** Active selection is valuable because it targets uncertain, diverse, and under-performing scenarios; it is not a quality guarantee because query-selected data are biased and batch methods can underperform random sampling on some datasets. Incremental fine-tuning can avoid restarting from scratch, but replay and forgetting measurement are essential, and complete retraining remains the response to substantial drift or a failed release gate.[111][109][108][65]

1. Lock separate pallet-label and package-damage precision definitions: class, IoU rule, confidence threshold, and holdout window.
2. Run active selection alongside a random-review control and retain expert-reviewed labels.
3. Fine-tune with replay data, promote only versions passing the 92% gate, and roll back failures.
4. Schedule full retraining whenever labeled drift or forgetting repeatedly breaches that gate.

Ranked warehouse decision

Provisionally rank NVIDIA TAO DetectNet_v2 first, YOLOv8 second, and EfficientDet-D4 third. TAO DetectNet_v2 ranks first when integrated monthly deployment and rollback engineering is decisive: TAO provides an interface for automated fine-tuning flows, fine-tuned models can be used in DeepStream through Inference Builder, and its deployment path exports checkpoints to ONNX, builds a device-specific TensorRT engine, and feeds that engine to DeepStream.[58][9] YOLOv8 ranks second as the flexible benchmark and possible fleet winner when its held-out warehouse accuracy, sustained per-node camera capacity, OTA package size, and old-SKU retention surpass TAO. EfficientDet-D4 ranks third unless its small-target gain justifies its cost: D4 uses 1024-pixel input and an EfficientNet-B4 backbone, but DeepStream deployment also requires TensorRT OSS, `ResizeNearest_TRT` and `EfficientNMS_TRT` plugins, and a custom bounding-box parser.[10][11]

### Open questions

Open: the client-dataset INT8 latency per frame, FP16-to-INT8 mAP change, sustained-load power draw, and multi-stream capacity for YOLOv8, EfficientDet-D4, and DetectNet_v2. These are settled by a matched AGX Orin acceptance run using the 50,000-image warehouse corpus, production camera resolution, installed cooling and power mode, headless decode-to-metadata pipeline, and separate FP16 and calibrated INT8 engines. Open: the practical sub-100 MB accuracy floor for each candidate and whether edge active learning can keep precision above 92% without full retraining. These are settled by release-size-constrained compression trials and time-ordered monthly new-SKU tests that measure precision, recall, and mAP separately before and after selective-label updates.
