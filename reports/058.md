# Research on AI Suggestion Timing, Developer Flow, and Code Quality

## Executive summary

Use proactive inline suggestions only for short, high-confidence continuations at a meaningful coding boundary, and make larger, uncertain, or design-shaping generation explicitly requestable. Copilot, Tabnine, and CodeWhisperer all support this split, but the piece does not establish a product-specific winner for flow or code quality between developers with 2–5 and 10+ years of experience.

A one-second Copilot pause is a studied interface setting, while CodeWhisperer’s split-second objective is an engineering target, not a validated optimal latency threshold in milliseconds. During debugging, preserve the developer’s diagnostic thread and favor on-demand or boundary-triggered help; during new-feature implementation, proactively offer small local continuations when the active intent is already clear.

Explanations should expose assumptions, uncertainty, provenance, security signals, and validation cues to support calibrated review rather than make suggestions appear more authoritative.[1][2][3][4][5][6][7]

## The question and why it remains open

AI code completion is not one interaction. It ranges from a short continuation that a developer can pattern-match against an existing plan to a larger proposal that asks the developer to stop, inspect, and judge a possible implementation. That difference makes presentation timing consequential: the same model output can either remove routine typing or interrupt the construction of a mental model.

For enterprise teams, the design problem is therefore not simply how often an assistant is correct. It is how to offer useful code at the point of work without taking attention, authority, or review responsibility away from the developer. The three products considered here all work in the IDE, but their compared modes place the initiative and the unit of review differently.

### What suggestion-presentation mode is being compared for GitHub Copilot

GitHub Copilot’s compared mode is **proactive inline completion**. In supported editors, Copilot automatically offers autocomplete-style ghost text while the developer types. The suggestion may complete the current line, generate a new block, or propose an edit; developers can accept all or part, dismiss it, or keep typing to ignore it. GitHub also provides commands to trigger an inline suggestion and to open further alternatives in a separate pane.[8][9][10]

Copilot’s suggestion pipeline can use code from open editor tabs as well as local cursor context; it identifies completion opportunities and abandons requests if the developer has moved on.[23][130][63]

This is not merely conventional token completion. GitHub’s documentation describes suggestions that can span a current-line continuation, a block, or an edit elsewhere in the file. In Visual Studio Code, its next-edit suggestions can identify both the location of a related edit and its content, including insertions, modifications, or deletions. That gives Copilot a broader intervention surface than a cursor-only autocomplete menu, even though ghost text at the cursor remains its characteristic presentation.[11][12][13]

GitHub announced Copilot for technical preview in Visual Studio Code on June 29, 2021, and Copilot became publicly available in June 2022.[14][1] It was powered by the OpenAI Codex family of models and integrated into environments including Visual Studio Code, JetBrains IDEs, and Neovim.[1][15] Its initial interaction model made generated assistance visible inside the normal writing surface rather than requiring a developer to leave the editor for a search page or a conversational interface.

Copilot’s interface has always included both automatic and intentional routes. A developer can write a natural-language comment to guide a suggestion, explicitly trigger completion by shortcut, or open a multi-suggestion pane. The product’s normal inline behaviour remains proactive, but these controls let a developer shift from automatic continuation to deliberate generation and comparison.[16][8][9][3]

The distinction is important because a code comment is not simply another source of model context. It is an explicit statement of intent by the developer. In Barke, James, and Polikarpova’s 2023 *Proceedings of the ACM on Programming Languages* study, participants characterized comment prompts as offering more control than a system guessing from partially written code. One participant contrasted being interrupted while typing with writing a comment that expressed their mental model before seeing the proposed code.[3]

The study names two interaction states that are useful design vocabulary: **acceleration** and **exploration**. In acceleration, the developer already has a plan and uses Copilot as enhanced autocomplete to execute a focused logical unit. In exploration, the developer is unsure of a solution route, intentionally prompts the system with a comment or invokes the multi-suggestion pane, then compares, tests, and sometimes combines alternatives.[17]

These states differ in more than suggestion length. Acceleration uses unintentional prompting and rapid pattern matching against expectations; exploration uses intentional prompts, explicit examination or execution, broader function-level scope, and greater willingness to edit or debug generated code. In the 20-participant study, comment prompts took 57.2% of prompting time in exploration but 13.1% in acceleration, while code prompts accounted for 71.4% and context prompts for 15.2% of prompting time in acceleration.[3][17]

A one-second pause was the illustrative trigger for Copilot’s gray inline suggestion in the study’s interface. When a short suggestion matched the developer’s expectation, it could be inspected and accepted in a fraction of a second without leaving flow. This describes one studied interaction, not an experimentally established one-second optimum.[1]

Copilot’s automatic presentation can also create interruption costs. Barke, James, and Polikarpova found that long multi-line suggestions in acceleration were often dismissed and could distract developers away from typing flow; three participants had already disabled Copilot after months of access, citing distraction from always-on suggestions. The authors further observed that large blocks could cause developers to begin implementation before working out their desired high-level design.[3][1]

In GitHub’s recent inline-interface work, immediately displaying cached suggestions could disrupt developers, whereas a slight display delay better matched their typing rhythm; invoking the model immediately while they were still typing did not worsen their experience.[131]

**Copilot’s inline mode is best understood as a reversible, proactive offer: it is effective when it completes an already active local plan, but it becomes disruptive when its scope or timing forces evaluation before the developer is ready.** This makes a visible reject path, partial acceptance, and manual invocation part of the interaction’s core control model rather than secondary convenience features.[16][9][3]

For ordinary Copilot inline completion, the prompt is the current code context, cursor location, and recently typed text rather than an explicit natural-language request.

GitHub says Copilot's inline-suggestion pipeline also uses contextual material from open editor tabs. [23]

All three systems can generate more than one line, use surrounding code as context, and offer a developer a choice not to insert the output. The practical distinction is where the interface places the primary initiation and review burden: Copilot emphasizes automatic inline continuation, Tabnine emphasizes context-adaptive inline prediction at line, block, and function scope, and Amazon CodeWhisperer emphasizes using a natural-language task comment plus code context to generate a relevant implementation.[8][18][19][20][21]

#### GitHub Copilot: automatic continuation inside the coding surface

Copilot’s visual model is **inline ghost text**: code presented as dimmed text in the same editor where the developer is authoring code. This preserves spatial context and gives the developer an immediate comparison between the proposed continuation and the current program. GitHub says suggestions are visually distinct and no change occurs without deliberate acceptance.[13][8][23]

This presentation model emerged from neural code completion’s move beyond traditional lookup menus. Standard completion typically offers individual tokens in a popup list; multi-token completion is commonly shown inline as gray text and generally presents one proposal rather than a menu of many candidates. Copilot extended that model to line and block completions, including suggestions conditioned by comments.[24][25][8]

The product can therefore serve two different moments without changing surfaces. First, during local execution, a developer can let automatic ghost text propose the next statement. Second, during deliberate inquiry, the developer can write a comment and invoke a pane containing up to 10 alternatives. Participants in the Copilot interaction study used that pane to compare options, search for API examples, cherry-pick useful fragments, and assess whether alternatives converged on a common pattern.[1]

The pane creates a trade-off. Some participants preferred it to inline suggestions, particularly for exploration. Others found a separate window cognitively burdensome because they had to map code in the pane back to its insertion point; one participant said that seeing code where it would go was more valuable than making those additional connections.[3] This is a presentation consequence, not just an output-quality issue: alternatives help when comparison is the task, but they add attentional work when continued implementation is the task.

GitHub’s own evolution reflects the limitation of optimizing an inline system only for immediate acceptance. The company states that high acceptance can favour simple, short completions, so it added accepted-and-retained characters, code flow, and other measures to its optimisation objectives. That is a useful enterprise distinction: a keypress accepting a suggestion is an interaction event, whereas retained code and a non-disrupted workflow are closer to durable value.[25]

GitHub reported that a newer Copilot completion model had 35% lower latency, 12% higher suggestion acceptance, and 20% more accepted-and-retained characters; it did not give an absolute latency in milliseconds with those figures.[25]

GitHub also tracks shown rate, edit quality, time-to-first-token, and latency alongside acceptance and retention when evaluating completions.[132][23][25]

The product’s presentation mode is therefore broader than “AI predicts the next token.” It is a hierarchy of cursor completion, related edit proposal, and optional deliberate generation. **For interface design, Copilot demonstrates that proactive presentation is viable only when the suggestion is easy to ignore, bounded enough to assess, and complemented by an intentional route for larger or uncertain work.**[13][9][3]

#### Tabnine: inline prediction at line, block, and function scope

In June 2022, Tabnine was described as offering focused line completions and longer snippet suggestions directly in Visual Studio Code and IntelliJ IDEA. Its early user experience was described as closer to traditional autocomplete; by 15 June 2022, it had announced a shift toward language-model-driven autocomplete more resembling Copilot’s capabilities.[26][27][28]

The compared Tabnine mode is therefore **context-adaptive inline prediction**, including multi-line blocks and full-function implementations. Tabnine documents suggestions appearing inline in gray alongside native IDE pop-up suggestions while developers code. It says completions can continue to the end of a line, propose the next code block, or generate an entire function.[18][19]

The system’s long-form prediction is contextual rather than a separate chat transaction. Tabnine documents a full-function implementation when a developer begins a new line after a function declaration. It also supports natural-language-comment-to-code completion: after a developer writes a documentation-style comment expressing the desired task, Tabnine proposes the implementation on the following line.[18][19] Thus “multi-line prediction” is the chosen comparison emphasis, not a claim that Tabnine lacks comment-led generation.

Tabnine frames completion as suitable for small, mundane coding tasks, saving typing, and recalling syntax. It explicitly directs developers to Tabnine Chat for high-level design, general code questions, or understanding instructions. This division matters because it assigns inline prediction to low-friction continuation and a more deliberate interface to work that requires explanation or wider reasoning.[19][29]

Its documented controls retain authorial control at the granularity of insertion. Developers can accept the entire proposal with Tab; supported IDEs permit line-by-line acceptance, and Visual Studio Code also permits word-by-word acceptance. Continuing to type changes the available context and can produce a different prediction.[18][30]

Tabnine’s enterprise deployment choices also affect the timing problem operationally. Its completion models can run on a developer laptop, on a server behind a firewall, or in the cloud; Tabnine also describes self-hosting and private repository models.[30] These are data-governance and deployment options, not evidence that local deployment produces a particular user-experience outcome. They do, however, make latency, privacy, and enterprise controls part of one system design rather than separable procurement questions.

**Tabnine’s presentation model makes longer inline prediction appropriate for bounded implementation work whose intent is already visible in the declaration, comment, and local context; its own product boundary places design and explanatory work in an explicitly requested chat interaction.**[18][19][29]

#### Amazon CodeWhisperer: comment-to-code generation within the IDE

Amazon announced CodeWhisperer preview on 23 June 2022. As of 30 April 2024, it became part of Amazon Q Developer, including inline code suggestions and security scanning.[14][31] This review uses the historical CodeWhisperer name because the requested comparison concerns its documented interaction pattern.

CodeWhisperer’s distinctive compared mode is **comment-to-code generation**. A developer writes a plain-English comment that outlines a task, such as uploading a file to S3; CodeWhisperer uses that task description with the code already in the IDE to recommend a relevant snippet directly in the editor. AWS describes the system as considering surrounding functions, imports, variable names, coding style, and cursor location, rather than treating the comment as an isolated prompt.[32][21][22][33]

This interaction is more intentional in content than a pure next-token continuation, but not necessarily manual in display. After CodeWhisperer is enabled, AWS says recommendations arrive automatically as the developer begins writing code or comments. It can generate code from a function signature, comments, or both, with documented output spanning single lines, logical blocks, and complete functions.[32][6][7][34]

The product provides both proactive and on-demand access. Suggestions appear automatically during typing; the developer can also request a suggestion using Option+C on macOS or Alt+C on Windows. In the Lambda console integration, by contrast, CodeWhisperer required a manual fetch and showed a single suggestion, while the IDE extensions offered automatic suggestions and could show multiple ones.[35][22][34] This is a concrete example that presentation policy can vary by environment even for the same assistant.

In Visual Studio, a CodeWhisperer recommendation remains gray and pending until the developer accepts it with Tab or rejects it with Esc. [2][133][134][32]

AWS’s comment-to-code examples show a staged interaction. In the Lambda console, a developer writes a comment, activates suggestions on the next line, receives a function signature, accepts it, and then receives the rest of the function. That sequence limits the first review decision to a smaller commitment before presenting a larger implementation.[34] For enterprise interfaces, staged generation is a useful alternative to dropping a full function into a developer’s attention at once.

In an AWS CodeWhisperer walkthrough, an initial natural-language comment did not produce required DynamoDB attributes, but a refined comment did. [133]

CodeWhisperer also exposes information that matters to enterprise code-use decisions. Its reference tracker flags suggestions that may resemble open-source training data and annotates them with repository URL, file reference, and license information; users can filter such suggestions. Its security scanning identifies vulnerabilities and proposes remediations.[6][36] These are provenance and security-review aids, not demonstrated explanations of why a particular generated implementation is functionally correct.

CodeWhisperer also offers an explicit “Run Security Scan” action that the developer can invoke to scan both generated and developer-written code. [133][32]

The distinction matters because provenance is not the same as rationale. A repository URL and license can help a developer decide whether code may be used; a detector-library explanation can help a developer understand why a security finding was raised. Neither by itself tells the developer why the assistant selected a particular algorithm, whether all requirements were captured, or whether a code path is complete.[2][7][32]

Amazon Science states that CodeWhisperer suggestions need to appear “in a split second” to be useful and that a good idea arriving 20 seconds late is a distraction rather than help. It describes quantization and memory-access techniques intended to reduce latency and permit multiple recommendations without extra latency cost.[2]

CodeWhisperer demonstrates that a natural-language comment can serve as a compact declaration of intent while automatic in-editor presentation keeps the result near the work; the interface still needs explicit request, review, and provenance controls because the generated block remains a proposal rather than a verified implementation.[21][6]

### Why timing is consequential in enterprise development

Programming interruption research supplies the mechanism behind the interface risk. Programming requires concentration and the simultaneous management of multiple concepts. When a developer is interrupted, resumption requires recovering both mental and working context: artifacts, plans, goals, and task-specific representations.[37][38][39]

Parnin and DeLine (2010, Proceedings of the SIGCHI Conference on Human Factors in Computing Systems, 'Evaluating cues for resuming interrupted programming tasks')’s work on interrupted programming identifies increased task time, errors, loss of knowledge, and forgotten critical tasks as consequences of interruption.[40] Their session analysis found that only a small percentage of sessions resumed with coding in under one minute, while developers spent substantial time on non-editing activities before their first edit as they rebuilt task context.[39][41] A visible AI suggestion is not equivalent to a meeting or a notification, but a large unsolicited suggestion can impose the same basic cost when it redirects attention from the active problem state to evaluation of a new proposal.

Interruption costs depend on timing and task conditions. General interruption research identifies interruption duration, interrupting-task complexity, and the moment of interruption as important determinants of disruption. It recommends presenting interruptions at low-problem-state moments and preserving task state when an interruption is unavoidable.[42] A low-problem-state moment is a point at which the developer is not holding many unfinished intermediate decisions in working memory—for example, after completing a statement, ending a block, running a test, or finishing a multi-line paste.

Interruption research distinguishes an interruption that redirects attention to a secondary event from task switching between activities with different mental sets. The memory-for-goals account predicts that the active problem state can decay during the diversion and must be reconstructed on resumption, sometimes with errors.[135]

Controlled interruption research finds that longer interruptions produce longer resumption lags. It also finds that although interruptions can increase errors, a longer pause before resuming action can reduce errors by allowing cognitive re-engagement.[68]

A 2025 proactive-programming-support study operationalized such boundaries as an outdent from a Python code scope, executing code in the editor, and pasting more than one line. These are observable interaction events rather than guesses about a developer’s internal attention.[4][5] They provide a practical **boundary-trigger rule**: do not treat every keystroke pause as permission to intervene; prefer semantically meaningful pauses that plausibly close a local unit of work.

Software-development evidence also shows that interruption effects vary by activity. Programming and testing were more vulnerable to task switching than architecture and UI design because they require more active statements in working memory. Developers reported that meetings and interruptions were unproductive during development phases but common and constructive during planning, specification, and release phases.[43][44] The timing implication is not that all proactive assistance is harmful; it is that assistance must be sensitive to whether the developer is executing a fragile implementation chain or engaging in a phase where outside information is useful.

The evidence also resists a simplistic “never interrupt” rule. Some task switches are productive, including same-project idea exchange and rapid bug triage. In office work, interruptions can resolve questions quickly and improve team productivity, but interruptions at inopportune moments are associated with longer resumption, lower performance, more negative emotion, and more errors.[43][45] The relevant variable is contextual fit, not the mere fact that the system surfaced information.

Enterprise developers have further reasons to care about this trade-off. A 2025 study of IBM’s internal watsonx Code Assistant deployment examined expectations of speed and quality alongside ownership and responsibility for generated code.[46] Microsoft developers surveyed in 2026 wanted quality signals earlier in the workflow, along with explicit authority scoping, provenance, uncertainty signaling, and least-privilege access.

They also located the acceptable boundary of AI help near their professional identity: the value of tooling depends partly on where and how precisely it stops.[47]

These requirements make an always-on “accept or ignore” model incomplete. The user must be able to determine what the assistant is proposing, what it is based on where relevant, what risk checks apply, and whether the scope of delegation matches the task. CodeWhisperer’s reference tracking and security explanations offer examples of information that can support those decisions, while Copilot’s visual distinction and explicit acceptance preserve a basic human-in-the-loop boundary.[6][7][23]

Judgment — **Explanation availability should be treated as a calibration aid, not a persuasion feature.** In a completion interface, concise explanation should answer the decision-relevant question at the appropriate level: for a short continuation, why it fits local code context; for a larger generation, what intent, APIs, assumptions, tests, security checks, and provenance shaped it. The interface should disclose uncertainty and limits as readily as it supplies rationale, because an explanation that only makes output sound plausible can increase overreliance.

Current studies establish the need for this design but do not yet demonstrate a product-and-cohort causal effect of explanation availability on trust calibration. Developers have asked for cues that explain what differs between alternatives and why one might be selected; research also identifies a user-synthesizer gap in which programmers can overestimate a synthesizer’s capability.[3] CodeWhisperer’s provenance annotations and security-finding explanations give information for review, but they are not tested explanation treatments for generated-code trust.[6][7]

The quality problem reinforces the need for controlled timing and review. Functional correctness tests do not capture readability, completeness, or subtle errors, and generated code can be syntactically invalid or use undefined names. Faster code generation can therefore shift the bottleneck from authoring to checking.[28] An interface that makes generation instant but forces repeated, poorly timed verification may improve neither flow nor enterprise code quality.

The design consequence is selective display. Conditional suggestion display from human feedback (CDHF) uses a cascade of models to estimate whether a recommendation will be accepted and selectively hides suggestions, reducing latency and programmer verification time. Smart invocation research similarly targets the question of when to invoke completion, noting that excessive suggestions can interrupt developers who are concentrating.[48][49] These approaches do not establish a universal millisecond threshold; they establish that withholding a low-value proposal is a legitimate interface action.

JetBrains Central Console documents an enterprise analytics surface for AI-generated code inside JetBrains IDEs. It separates chat-based interactions from in-editor interactions; the latter includes Code completion, which autocompletes single lines, blocks, and entire functions in real time from project context, and Next edit suggestions, which predict segments to change and likely edits.[50] JetBrains also identifies quality improvement—finding problems, refactoring code, and adjusting code to follow best practices—as a main usage pattern among JetBrains AI Assistant users, while warning that developers may place too much trust in suggestions or insufficiently review them before acceptance.[51]

JetBrains’ documented evidence in this review concerns full-line code completion rather than deployment outcome metrics for JetBrains AI Assistant. JetBrains describes full-line completion as local, offline-capable, and instant; it requests and filters multiple candidates, displays selected line proposals while developers type, and lets them accept a proposal or continue typing while retaining regular completion. It claims syntactically valid code without compiler errors or IDE squiggles while directing developers to check logical accuracy. JetBrains separately describes AI Assistant as a broader product with context-aware chat, test generation, and documentation writing.[52]

JetBrains reports that it reduced average completion length and restricted when multi-line proposals appear: in its 2024.2 design, a multi-line suggestion appears only after the developer accepts a single-line suggestion.[136][137]

JetBrains’ full-line completion designers chose a single-line proposal as a compromise between keystrokes saved and code-review effort; they also filtered proposals likely to be cancelled or deleted immediately.[138]

Parnin and DeLine’s 2010 CHI study gives the interruption terms operational meaning. Interruption lag is the interval from stopping the primary task to addressing the interruption, and resumption lag is the delay in returning to the primary task; developers can use interruption lag to encode working state. Environmental cues about the working state, such as an error message associated with the bug being fixed, support prospective resumption when present both during interruption lag and resumption lag. Completing a subtask also leaves less intermediate state to recover.[53]

In their survey of 371 Microsoft programmers, Parnin and DeLine found that 77% took notes to track task progress and 58% made a mental note. The highest-rated resumption aids were Instant Diff (3.9/5), Change Summary (3.4/5), Code Thumbnails (3.2/5), and Activity Explorer (3.1/5).[54]

Their controlled feature-addition experiment interrupted participants 15 seconds after a non-comment edit, after more than three non-comment edits, or after a 12-minute timeout without changes. It measured resumption lag from restarting the task to the first IDE event: 20 seconds with a degree-of-interest treeview, 21 seconds with a content timeline, and 23 seconds with notes only (N=14). It measured edit lag from restarting to the first code edit: 2:30 with the treeview, 3:26 with the timeline, and 4:28 with notes only (N=9).[54]

The feature-modification experiment’s tasks were small feature additions, not debugging tasks.[139]

The same experiment found that activity-history cues made subjects about twice as likely to complete tasks as notes alone; the note-taking condition had half the task-success rate of the automatic-cue conditions. The chronological content timeline showed code selections, edits, saves, and builds, and participants rated it above note taking and the degree-of-interest treeview for speed, interrupted-task reminders, durability, and overall preference.[54]

These results make task-state preservation a concrete interface requirement when assistance interrupts maintenance or bug-fix work: present the proposal with recoverable local context, and preserve the developer’s recent edits, navigation, builds, and tests for return to the task.[54]

### Synthesis

The products differ mainly in emphasis: Copilot foregrounds proactive ghost-text continuation, Tabnine foregrounds context-adaptive line-to-function prediction, and CodeWhisperer foregrounds task comments as an intent-bearing route to generated code. All retain developer acceptance control, and Copilot and CodeWhisperer also support explicit invocation.[8][18][22][9] Read together with interruption research, the stronger design direction is selective proactive assistance for small, high-confidence continuations at task boundaries, plus on-demand generation for exploration, uncertain intent, debugging, and larger code blocks.[42][49][3] This does not mean that proactive assistance is uniformly harmful: timely information can resolve questions and preserve IDE context, but poorly timed suggestions increase resumption and verification work.[45][55]

For enterprise teams, code quality includes functional correctness, test adequacy, security and privacy compliance, maintainability, consistency with local architecture, review burden, provenance or licensing concerns, and whether another engineer can understand the change. Acceptance rate is not itself a code-quality measure: it can reflect useful assistance, automation bias, weak inspection, or a costly rejection interaction.

Whether these presentation modes improve calibrated trust, flow, or code quality for developers with 2–5 years rather than 10+ years of experience remains an empirical question.

While a developer writes code, CodeWhisperer continuously monitors activity and uses a client-side ML classifier to decide whether to suggest code, based on what the developer is doing and the likelihood that they need and want a suggestion.[56]

## What is established

AI coding assistance affects more than output volume: it changes the pace of writing, the attention needed to inspect generated code, and the continuity of a developer’s work. The established evidence therefore separates productivity measures—task time, pull requests, commits, builds, and perceived productivity—from flow and code quality. That distinction matters because fast generation can still impose review and resumption costs.

### What do Microsoft's productivity studies reveal about AI-powered code completion

Microsoft Research’s Peng et al. (2023) controlled experiment assigned 95 professional programmers recruited through Upwork to implement an HTTP server in JavaScript between May 15 and June 20, 2022. Forty-five developers received GitHub Copilot and 50 did not; 35 completed both the task and survey. The Copilot group completed the task 55.8% faster than the control group, with a 95% confidence interval of 21% to 89%. The study measured success as the first commit passing all 12 repository tests and measured completion time from repository creation to that passing commit.[57]

The 95 professional programmers in Microsoft Research’s controlled Upwork experiment had a mean of six years of experience.[140]

The same experiment found a 7-percentage-point higher task-success rate for the Copilot group, but the estimate was not statistically significant and its 95% confidence interval was [−0.11, 0.25].[57][58] Passing the 12-test suite is a bounded functional outcome rather than a broad measure of maintainability, security, or review quality.[57][58] Microsoft Research’s result therefore supports faster completion of its JavaScript assignment, while the task-success result does not show a reliable quality advantage.

Participants in Microsoft’s three-week workplace study valued Copilot for boilerplate, repetitive code, documentation, and comments, but also reported plausible-looking incorrect code and validation work that could erase time savings.[141]

Cui, Demirer, Jaffe, and Musolff’s February 2025 study, *The Effects of Generative AI on High-Skilled Work: Evidence from Three Field Experiments with Software Developers*, randomized access to GitHub Copilot at Microsoft, Accenture, and an anonymous Fortune 100 company.[15] The three workplace experiments covered 4,867 developers, lasted two to eight months, and gave a random subset access to an AI assistant offering intelligent code completions.[59][15] When pooled, the weighted-IV estimate was a 26.08% increase in weekly pull requests, with a standard error of 10.3 percentage points; pooled weekly commits rose 13.55% (SE 10.0) and weekly builds rose 38.38% (SE 12.55). The pull-request and build estimates were marked significant, while the commit estimate was not.[15]

At Microsoft, the same field-experiment table reports a significant weighted-IV pull-request increase of 27.38% (SE 12.88). Its Microsoft estimates for commits, builds, and build-success rate were not marked significant.[15] The authors use build success rate as their code-quality measure and report no negative Microsoft effect on that measure; Accenture’s build-success estimate was negative and statistically significant.[15] **Microsoft’s workplace result is higher measured workflow output, while build success supplies a narrow and mixed quality signal across organizations.**

The field experiments also identify heterogeneous workplace benefits. At Microsoft, Copilot significantly increased task completion for more recent hires and developers in junior positions, but not for longer-tenure or senior developers. The paper’s noisier subgroup estimates put short-tenure developers’ output gains at 27%–39%, versus 8%–13% for long-tenure developers; junior developers’ gains were 21%–40%, versus 7%–16% for senior developers. Conditional on adopting Copilot, junior and senior developers had no usage difference.[15] These are tenure and organizational-level comparisons, not the 2–5-year and 10+-year cohorts used in the product comparisons later in this report.

Across the later workplace experiments, short-tenured and junior developers were also more likely than their more experienced counterparts to continue using Copilot beyond one month.[63][142]

Microsoft’s earlier preview of its Microsoft and Accenture trials reported 12.92%–21.83% more pull requests per week at Microsoft and 7.51%–8.69% at Accenture, depending on specification. It also reported low Microsoft compliance and Accenture organizational change, with statistical significance reached only when periods with greater treatment-control uptake differences received heavier weight.[60] These estimates explain why pull-request figures should remain tied to their study design rather than treated as a single universal Copilot productivity multiplier.

The studies disagree at the task level. Peng et al.’s between-subject JavaScript experiment measured a 55.8% completion-time improvement, whereas the within-subject randomized experiment by Vaithilingam et al., summarized in the field-experiment paper, found no statistically significant completion-time difference even though participants preferred Copilot. The tasks and experimental structures differ.[61][62] The later workplace study explicitly contrasts its pooled estimate with the laboratory result, observing that ordinary development includes work beyond coding and contains tasks that are less amenable to completion assistance.[15]

Microsoft and GitHub also examined productivity as a multidimensional construct through the SPACE framework: satisfaction and well-being, performance, activity, communication and collaboration, and efficiency and flow. In the matched survey-and-telemetry study of 2,047 Copilot responses collected from February 10 to March 6, 2022, acceptance rate—accepted completions divided by shown completions—was the telemetry measure most strongly associated with aggregate perceived productivity. The authors argue that usefulness as a starting point for further work can matter more than literal correctness.[63] This makes acceptance useful for coarse monitoring, but it is not equivalent to output, correctness, or quality.

In GitHub’s matched survey-and-telemetry study of 2,047 Copilot technical-preview users, 27% of shown suggestions were accepted; acceptance had the strongest relationship among measured usage variables with aggregate perceived productivity (Pearson ρ = 0.24, P < 0.0001).[130]

In the four-week Copilot technical-preview observation period ending around February 12, 2022, the matched survey-and-usage study reported 27% acceptance of shown completions and more than 312 accepted completions per user per day.[63][130]

In that study, years of experience had a negative bivariate association with perceived productivity (ρ = −0.161, P < 0.0001), but its effect was not statistically significant after usage measures and demographics entered the regression.[130]

Judgment — For enterprise evaluation, use a measurement stack: task completion time for bounded work, throughput and build outcomes for ongoing delivery, and acceptance plus post-acceptance editing for interaction quality. The Microsoft studies make this possible, but their outcome measures should not be merged into one productivity number or used as a timing rule for inline suggestions.

A separate GitHub survey found that 73% of respondents reported that Copilot helped them stay in the flow and 87% reported that it helped preserve mental effort during repetitive tasks. These are respondents’ perceptions of flow and mental effort, distinct from Peng et al.’s observed task-completion time, Cui et al. (2024, no venue recorded, 'The Productivity Effects of Generative AI: Evidence from a Field Experiment with GitHub Copilot')’s weekly pull-request, commit, and build outcomes, and Cui et al.’s build-success measure.[60][64][57][15]

In GitHub’s survey of more than 2,000 developers, more than 90% reported that Copilot helped them complete tasks faster.[64]

Cui et al.’s field experiments measured pull requests, commits, builds, build-success rate, and Copilot suggestions shown and accepted; they did not measure suggestion-display latency.[15]

### What does academic research reveal about programmer interruption costs?

Parnin and Rugaber (2010, Software Quality Journal, 'Resumption strategies for interrupted programming tasks')’s 2010 *Software Quality Journal* study, *Resumption Strategies for Interrupted Programming Tasks*, analyzed 10,000 recorded sessions from 86 programmers and surveyed 414 programmers.[65][39] It describes interruption consequences as increased task time, errors, loss of knowledge, and forgotten critical tasks.

Parnin and Rugaber’s analysis counted 9,899 programming sessions involving 86 developers; they interpreted some long edit lags as possible debugging activity rather than directly classifying those sessions as debugging.[39]

It also cites industrial software-company observations of approximately one hour per day spent managing interruptions and a typical 15-minute recovery period; a cited Microsoft survey found 62% of developers regarded recovery as a serious problem.[39]

Parnin and Rugaber define **edit lag** as the interval between returning to a programming task and making the first edit. Across their sessions with editing activity, 10% had edit lag below one minute and about 30% exceeded 30 minutes. They propose that some of the longest lags may involve debugging, which can require substantial attention before an edit occurs.[39] This identifies debugging as a likely attention-intensive activity, not as a measured debugging-versus-feature-development comparison.

Interruptions matter because programming working state includes artifacts, plans, goals, and mental representations. Parnin and Rugaber describe much task knowledge as tacit and temporary, making it vulnerable when a developer is diverted before preserving it in code or notes.[39] Parnin and Rugaber’s interaction histories show that resumption usually involves reconstruction: in Visual Studio data, only 7.5% of 1,213 sessions involved a change without navigation to another method, and programmers navigated to other methods or classes in most sessions.[39]

Abad et al.’s mixed-methods study, *Task Interruption in Software Development Projects*, examined 4,910 tasks from 17 professional developers and surveyed 132 practitioners. It found self-interruptions more disruptive than external interruptions and negatively associated with interrupted-task performance. Programming and testing were more vulnerable to interruption than architecture and UI design, which the authors attribute to higher problem-solving and working-memory demands.[43] For programming and testing, afternoon interruptions, switching to a task of the same priority, and switching task type each increased interruption vulnerability.[43]

Abad et al. found that experience level made a limited contribution to interruption vulnerability: it significantly affected vulnerability only for testing interruptions, where less-experienced testers were more vulnerable. For testing tasks, developers’ perceived vulnerability did not correlate with experience level (Spearman rho = 0.13, p = 0.78).[43] Survey respondents nevertheless linked shallow task knowledge and learning to poorer post-switch performance: 110 respondents, or 83%, reported this relationship.[43] **The actionable pattern is task-state sensitivity: protect programming and testing when working memory is loaded, especially for developers still acquiring task knowledge.**

Timing research favors **breakpoint-aware deferral**—waiting for a natural low-workload pause rather than issuing attention-demanding prompts at a fixed interval. General interruption research finds that high-workload breakpoints create longer resumption lag than low-workload breakpoints and that delaying an interruption by a few seconds can be less disruptive.[39] In Fogarty et al.’s programmer-interruptibility experiment, programmers addressed most interruptions within 10 seconds, but when deeply engaged deferred them for a mean of 43 seconds.[39] These are behavioral response intervals, not a millisecond latency target for AI completion.

In a survey of 141 professional developers, 97% agreed that disruptive interruptions require extra time to regain focus, 95% that they require extra time to complete work, and 91% that they cause loss of work track; 46% agreed that interruptions increase errors and 39% that they reduce work quality.[135]

The distinction between a brief local disruption and full recovery is critical. Altmann and Trafton measured a 3.8-second mean resumption lag in a complex resource-allocation task, double the 1.9-second inter-action interval.[66] In a programming interruption-recovery study, developers averaged 1 minute 34 seconds to make the first non-comment edit and 6 minutes 31 seconds to reach meaningful execution.[67] First editing signals partial re-engagement; meaningful progress reflects substantially more complete context recovery.[67]

Pham, Zhou, and Kelleher measured the average 1-minute-34-second delay to a first non-comment edit and 6-minute-31-second delay to meaningful execution across 68 post-interruption periods.[67]

Microsoft’s large workday survey reinforces the flow cost in professional practice. Developers self-reported an average 8.64 minutes to resume after an interruption and an average longest uninterrupted coding period of 47.3 minutes; good workdays had 52.9-minute uninterrupted coding periods, compared with 39.3 minutes on bad workdays.[44] Meetings and interruptions were described as unproductive during development phases but constructive during planning, specification, and release phases.[44] This supports phase-aware assistance: the same prompt can be disruptive during active implementation and useful when coordination is the task.

Timing evidence is not uniform. In Abad et al.’s survey, 69% regarded early-stage interruptions as harmful after resumption and 38% regarded late-stage interruptions as disruptive, while the retrospective analysis found a temporal-stage effect only for deployment tasks. The paper also notes prior studies associating middle- or late-stage interruption with longer suspension and lower performance and work quality.[43] The stable design principle is therefore to infer interruptibility from current activity and task context, rather than infer it from elapsed time alone.

The self-reported longest uninterrupted coding period was 13.6 minutes longer on good than bad workdays—52.9 versus 39.3 minutes—which is a 34.6% increase relative to bad workdays. This makes uninterrupted-work duration a concrete enterprise outcome for timing-policy evaluation.[44]

The workplace interruptions examined by Parnin and Rugaber are task switches that stop planned work until the developer returns and recovers context; a nonmodal inline completion is a different mechanism because the developer can ignore it. Poorly timed or lengthy inline suggestions can nevertheless break typing flow by making the developer stop to read and evaluate them.[4][68][1]

Züger and colleagues’ FlowLight field research evaluated whether communicating developers’ availability could reduce workplace interruptions. It did not test whether inline AI code completions improve code quality.

Parnin and DeLine (2010, Proceedings of the SIGCHI Conference on Human Factors in Computing Systems, 'Evaluating cues for resuming interrupted programming tasks')’s 2010 study, 《Evaluating Cues for Resuming Interrupted Programming Tasks》, examined cues that help programmers recover goals, program state, and their next intended action after an interruption.[40]

### Which metrics are documented from JetBrains AI Assistant deployments?

JetBrains’ 2025 Developer Ecosystem survey reports surveyed use of AI tools for coding and development and company AI-integration stages, including pilots and partial rollouts; it is not a controlled deployment outcome for JetBrains AI Assistant.[69]

JetBrains Air’s *AI activity and impact* documentation, dated November 5, 2026, lists the currently documented enterprise analytics.[70] It covers chat-based interactions through Junie, Claude Agent, Codex, and AI Assistant chat, plus in-editor Code completion and Next edit suggestions. The analytics require IDE and AI Assistant version 2025.3.0 or later and Junie version 253.487.77 or later.[71]

The documented metric roster is broad but specific:

- **Contribution and origin:** AI contribution rate, code-origin breakdown, AI-generated code, AI-modified code, and separate lines modified by chat-based agents and in-editor features. AI contribution rate equals committed AI-generated lines divided by committed AI-generated plus human-authored lines. [71]

- **Acceptance and retention:** AI code acceptance rate, generated lines, accepted lines, and rejected or rolled-back lines. For in-editor Code completion, acceptance counts lines inserted into the editor; partial acceptance of one line counts as one accepted line, while multi-line suggestions count the inserted lines. Next edit suggestions count accepted inserted and deleted lines, including each step of a multistep flow. [71]

- **Activity and exposure:** messages sent to AI chats and suggestions shown by in-editor features. Each chat message increments chat activity once; each displayed in-editor suggestion increments suggestion activity once, regardless of its number of lines. [71]

Administrators can filter these charts by inclusive date range, tool, user, and group; filters of different types combine with AND, while selections within one filter type combine with OR. The charts therefore support segmented operational analysis, such as comparing acceptance, display volume, or committed AI contribution across teams and tools.[71]

The 2024 thesis *Beyond Acceptance Rates: The Effects of JetBrains AI Assistant and FLCC* supplies a separate deployment-scale behavioral analysis. It collected more than 40 million actions—editing, code executions, and typing—across 26,000 users of JetBrains AI Assistant and Full Line Code Completion (FLCC). It found that assisted users spent more time in their IDEs and typed more; manual testing declined in most cases or remained equivalent.[72] The thesis characterizes the overall direction as tentatively mostly positive while calling for interpretation of whether the behavioral changes are beneficial.[72]

FLCC is a distinct JetBrains code-completion feature, rather than an AI Assistant dashboard metric. Its fall-2023 Python EAP A/B test reported observed FLCC figures: enabling FLCC increased the proportion of symbols written with any completion from 16% to 24%, a 1.5-times increase with p < 0.001; the metric includes standard and inline completion sources.[24] FLCC’s mean CPU time from invocation to displayed suggestion was 150 ms, and cache reuse occurred in over 90% of completion events.[24] Its inline-completion acceptance rate was about 15%, versus about 27% for standard completion; the reported rates concern suggestions selected divided by suggestions shown and the suggestion lengths differed substantially.[24]

JetBrains reported local Full Line Code Completion inference benchmarks on an M2 Max of approximately 75 ms with ONNX Runtime, approximately 100 ms with llama.cpp in mid-2023, and 50 ms for the same LLaMA model with later llama.cpp inference.[143]

JetBrains separately states that its in-editor code completion has latency below 200 ms for most use cases.[73] The 150 ms FLCC measure and sub-200 ms product claim show that responsive inline completion is technically achievable; they are service-performance measures rather than human-interruption thresholds.

JetBrains reported that Full Line Code Completion reached at least 35% suggestion acceptance and 5% explicit cancellation, with millions of completions daily after its 2023.3 and 2024.1 releases.[136]

JetBrains’ public deployment documentation also includes scope conditions. Contribution and code-origin measures apply to committed code, so discarded exploratory work is excluded. The CloudByte account describes contribution rate and code origin as requiring IntelliJ IDEA 2025.3.0 or later, with the full set at 2026.1 or later, while its FAQ describes the contribution-rate and code-origin metrics as IntelliJ IDEA 2026.1-or-later only.[74] Enterprise dashboards should therefore record IDE version and distinguish committed-code outcomes from exploratory use.

**The documented JetBrains measures support operational monitoring of exposure, acceptance, post-generation retention, committed contribution, and tool provenance; they are not direct measures of developer flow, semantic correctness, or code quality.**[71]

JetBrains describes a 2.5 MB local CatBoost filter that decides whether to show or suppress a completion in 1–2 ms, using signals including typing speed, time since typing, suggestion repetition, reference resolution, token scores, entropy, and project and completion context. Its Early Access Program A/B tests reported a roughly 50% relative increase in acceptance rate and a roughly 40% reduction in explicit cancellation after filtering, while the ratio of completed code remained steady.[144]

In JetBrains’ fall-2023 Python EAP A/B test, enabling FLCC increased the ratio of symbols written with any completion by 8.0 percentage points, from 16% to 24%. This is the absolute change underlying the reported 1.5-times increase.[24]

A JetBrains Python Early Access Program A/B test reported approximately 38% Full Line Code Completion suggestion acceptance; the ratio of completed code increased from 0.17 without the feature to 0.22 with it.[143]

Displayed suggestions, accepted lines, and committed AI-origin lines use different denominators and are not a linked suggestion-retention measure: in-editor activity counts each displayed suggestion once regardless of line count; in-editor acceptance divides accepted lines by generated lines; contribution and code-origin measures concern committed code.[71]

Zoominfo’s suggestion-level acceptance measure gives partial acceptance full credit, unlike a measure that counts the number of accepted lines or characters.[63][145]

Public JetBrains AI Assistant material establishes neither an experimental millisecond latency optimum nor debugging-versus-new-feature suggestion-acceptance rates.[71][73][24]

JetBrains Air also documents organizational adoption and consumption measures: consumers using AI features, total AI-credit consumption, consumers reaching credit limits, AI-credit consumption by consumer or group and AI tool, token consumption by provider and model, and individual agent-session records containing the user, agents and models used, session duration, and consumption. AI credits, source-code lines, tokens, sessions, chat messages, and shown suggestions are distinct measurement units in these analytics.[75]

JetBrains makes these organization-level analytics available in JetBrains Console and through an Analytics API for adoption, activity, credit-consumption, and provider-and-model usage data.[75] JetBrains’ 2026 Developer Ecosystem Survey, a globally representative survey of more than 15,000 professional developers, reported that around 9% used JetBrains AI in IDEs and/or Junie at work.[76]

The metric definitions make retention observable at different interaction layers. For chat-based agents, rejected lines are discarded or rolled-back suggestions, accepted lines are added or removed lines not discarded or rolled back, and generated lines exclude read-only Junie Ask mode and AI Assistant Chat mode output. For Junie, rollbacks are subtracted from accepted added and deleted lines.[77][50] For in-editor features, Code completion generated lines are displayed editor suggestions, whereas Next edit suggestions generated lines are displayed lines available for insertion or deletion.[77]

For chat-based agents, JetBrains records generated, accepted, and rejected lines: rejected lines are suggested lines discarded or rolled back; accepted lines are added or removed lines not discarded or rolled back; and acceptance rate is accepted lines as a percentage of generated lines. Total generated lines exclude read-only modes, including Junie Ask mode and AI Assistant Chat mode.[71]

### Synthesis —

Microsoft’s experiments show faster bounded-task completion and higher workplace output with Copilot, with larger estimated gains among recent hires and junior developers; build-success results offer a limited quality measure and vary across organizations.[57][15] Programmer-interruption research shows why presentation policy matters: task switches consume attention to reconstruct context, and lower-workload breakpoints reduce disruption more reliably than fixed elapsed-time prompts.[39][43] JetBrains provides the instrumentation needed to test this policy in enterprise deployments—suggestions shown, accepted and rejected lines, AI contribution, code origin, feature activity, and filters by team and period—but not a direct flow measure.[71] The combined implication is to measure completion systems as a joint problem of generation quality, exposure control, acceptance, retained code, and task-resumption cost.

## GitHub Copilot inline suggestions

### How do GitHub Copilot's inline suggestions affect developer flow state

GitHub Copilot’s inline completion is a proactive presentation mode: a suggestion appears at the cursor as the developer types, without explicit invocation, and the developer can accept it with Tab, accept part, or continue typing. Its central interface trade-off is speed versus attention: an immediately useful completion can preserve momentum, while a suggestion that requires reading, judging, or dismissing can interrupt active authorship.[3][13]

Barke, James, and Polikarpova’s 2023 grounded-theory study of 20 programmers distinguishes **acceleration** from **exploration**. In acceleration, the developer already knows the next small logical unit and uses Copilot to write it faster; in exploration, the developer is uncertain, uses suggestions to find a starting point or possible API, and spends more time validating. Participants moved between the modes during the same task.[1][3]

**Inline suggestions preserve flow when they complete the small unit already intended by the developer.** In the acceleration example, the programmer recognized Copilot’s completion as matching their expectation, accepted it quickly, and remained in flow. The authors therefore recommend short, high-confidence completions when the tool detects acceleration.[78][3]

The same study found that unsolicited long, multi-line suggestions could break typing flow. One participant stopped transmitting an already formed line of code in order to read and assess the suggestion; three participants who had previously disabled Copilot cited distraction from always-on suggestions as a factor. The authors recommend avoiding low-confidence and long suggestions in acceleration mode and matching suggestion scope to the developer’s current logical unit.[3][1]

Task characteristics affected which mode developers used. Both the Chat Client and Benford’s Law tasks featured unfamiliar APIs, and every participant spent considerably more time in exploration on those tasks; the Chat Server task involved simple business logic, so participants leaned toward acceleration. During acceleration, code prompts accounted for 71.4% of prompting strategies and the multi-suggestions pane was rarely used because it could break flow.[1][3]

GitHub’s aggregate survey result is positive: 73% of surveyed users reported that Copilot helped them stay in flow, and 87% reported preserved mental effort on repetitive work. These perceptions coexist with the interaction finding that flow benefits depend on a completion fitting the developer’s immediate plan, rather than merely being available.[64][3][78]

In Accenture’s enterprise evaluation, 94% of surveyed developers said Copilot helped them remain in flow and reduce effort on repetitive tasks, and 90% said they spent less time searching for information.[146]

For the requested **2–5-year cohort**, GitHub Copilot research reports a broader pattern rather than a cohort-specific flow measure: developers with less professional coding experience benefited more from Copilot, and junior developers reported higher productivity gains and tended to accept more suggestions. The Communications of the ACM study recorded 451 respondents in the “2y” category and 358 in “3 – 5 y”; it also recorded 162 in “11 – 15 y” and 214 in “16 y”, but did not publish a combined 2–5-year flow-state result.[57][63]

The Copilot survey also used a “6–10 years” experience category and identified its highest category as “16+ years”; it did not publish outcomes for the requested combined 2–5-year and 10+-year bands. [63]

For the requested **10+-year cohort**, no published Copilot inline-suggestion flow-state result uses that exact threshold. The same survey used “11–15 y” and “16 y” categories, with 162 and 214 respondents, while the qualitative interaction study measured language expertise rather than years: its most language-expert participants spent more time in acceleration mode. Language expertise is task- and language-specific, so it is not a substitute for ten or more years of professional experience.[63][1][3][79]

A 2026 quasi-experiment supplies a closer presentation-mode result, although its groups are not the requested bands. It compared Copilot automatic suggestions with disabled, on-demand suggestions in two maintenance-oriented tasks among novices and industry “experts” with at least three years of programming experience; experts had a median of five years of Java experience, ranging from three to over 15 years. Automatic suggestions were associated with higher distraction and lower actual and perceived productivity for experts, whereas they were associated with higher productivity and satisfaction for novices.[80]

The same study operationalized frustration through heart-rate-variability RMSSD, where lower values indicated higher inferred frustration. Experts’ median RMSSD was 129.42 ms with automatic suggestions and 140.88 ms with them disabled; novices’ medians were 89.96 ms and 92.23 ms respectively. The enabled-versus-disabled comparisons had Benjamini–Hochberg-adjusted p = 0.818 in both groups.[80]

For both experience bands, the usable design rule is plan-fit: proactively show compact inline completions when the current logical unit is predictable; make long continuations explicit, dismissible, or on-demand when the developer is actively executing a known plan. This preserves the low-friction benefit of acceleration without forcing attention onto suggestions that redirect active authorship.[78][3]

An April 2022 observational and interview study of 19 first-time Copilot users in an introductory programming course adds a distinct interruption finding: the constant stream of real-time, unprompted suggestions distracted participants because many tried to read each suggestion, and some said it disrupted their thinking. The authors observed shepherding—students spending much of their time trying to coerce Copilot to generate intended code—and drifting, in which they repeatedly accepted, adapted, deleted, and replaced suggestions without direction.[81]

In that study, accepted longer suggestions were frequently modified or deleted, whereas accepted short suggestions were less likely to be changed or deleted. This supports the existing plan-fit rule with evidence that shorter completions reduce immediate post-acceptance rework.[81]

Microsoft’s 2022 controlled experiment with 95 engineers building a JavaScript HTTP server found that the Copilot-access group completed the task 55.8% faster; the reported largest benefits were among developers with less experience, older programmers, and programmers who coded more frequently. This establishes a task-completion result for Copilot access, not a 2–5-year versus 10+-year inline-flow comparison.[82][83]

A field study in Okta’s engineering organization found statistically significant self-reported reductions after Copilot adoption in time spent context shifting, coding, documentation, testing, and total work hours. Participants reported saving 1.06 hours per week in coding and 1.56 hours per week in testing; they also reported improved motivation and perceived skill. These individual efficiency indicators did not produce statistically significant increases in monthly pull requests or lines of code, apart from monthly PR review count.[84]

Accenture’s enterprise evaluation reported that 88% of suggested Copilot code was retained in the editor.[146]

Copilot telemetry provides a behavioral complement to the flow accounts. Ziegler et al. (2022, no venue recorded, 'Productivity assessment of neural code completion') define acceptance rate as the fraction of completions shown that are subsequently accepted into the source file; across their analyses, it was the strongest usage predictor of aggregate self-reported productivity (ρ = 0.24, P < 0.0001).[85][86] Their survey included the SPACE dimension Efficiency and Flow, but the reported correlation is with aggregate productivity rather than a direct flow-state measure.[86] The authors also identify reviewing suggestions as a potential detriment to programming flow, supporting the distinction between an instantly pattern-matched small completion and a suggestion that requires deliberative review.[86]

ZoomInfo reported that, over 26 days from November 11 to December 9, 2024, its Copilot deployment accepted 33% of shown suggestions but 20% of suggested lines. Its suggestion-level rate counts a partially accepted suggestion as accepted regardless of how many of its lines were inserted.[145]

In Copilot telemetry, mean unchanged retention of accepted completions fell from 0.64 at 30 seconds after acceptance to 0.46 at 600 seconds; retention when edits with Levenshtein distance below 33% counted as mostly unchanged fell from 0.86 to 0.76 over those same intervals.[132]

The grounded-theory study further found that professional programmers and participants with prior Copilot experience spent proportionally more time in acceleration mode, whereas unfamiliar APIs produced significantly more exploration. Code prompts comprised 71.4% of acceleration prompting; comment prompts comprised 57.2% of exploration prompting. Execution was used for validation in 38.8% of acceleration interactions, while examination was used in 71.2% of exploration interactions.[87]

Ziegler et al.Acceptance rate was their strongest usage predictor of aggregate self-reported productivity (ρ = 0.24, P < 0.0001), while their survey’s SPACE dimensions included Efficiency and Flow.[86]

GitHub’s 2022 survey reported that 73% of developers said Copilot helped them stay in flow and 87% said it preserved mental effort during repetitive work.[88] Neither figure is reported separately for developers with 2–5 years or 10+ years of experience.[89]

### How do GitHub Copilot's inline suggestions affect code quality across

GitHub Copilot’s code-quality evidence is stronger for overall samples than for either requested experience band. A Copilot user survey found that years of experience negatively predicted agreement that Copilot helps developers write better code, and that highly skilled, more experienced developers were less likely to report writing better code with Copilot. This is a self-reported association about perceived quality, while juniors’ greater suggestion acceptance concerns usage behavior.[63]

GitHub’s randomized code-quality trial recruited 202 developers with at least five years of experience: 104 received Copilot access and 98 did not. Participants completed a web-server task with 10 unit tests; blinded reviewers then evaluated submissions using a rubric, producing 1,293 reviews with at least 10 reviews per submission.[90]

The separate GitHub code-quality experiment required at least five years of Python experience and used a restaurant-review web-server task.[61]

The controlled web-server task in GitHub’s Copilot code-quality trial was a Python task.[147]

These results show that Copilot-assisted work can improve functionality and review-related quality in a bounded task among developers with at least five years’ experience. They do not divide that population into the requested 2–5-year and 10+-year cohorts, so neither cohort can be credited with the trial’s measured advantage.[90]

The experience pattern nevertheless matters for interface design. The 2026 automatic-versus-on-demand Copilot study found that novices usually modified less than 30% of automatically accepted suggestions, whereas experts frequently modified more than 50%; experts also reported significantly more concern about code quality when automatic suggestions were enabled, while novices reported lower concern. Acceptance therefore is not a quality measure: it can conceal substantial rework and different verification burdens.[80]

Qualitative Copilot research identifies the mechanism behind that verification burden. Participants said generated code could be harder to debug because they understood it less well than code they had written; one participant failed to localize a subtle generated-code error. Participants requested validation support, including automatic property-based tests and live displays of relevant runtime values.[1]

Artifact benchmarks provide a separate quality signal, not a developer-cohort outcome. In the 2023 HumanEval Python benchmark, Copilot generated correct code for 46.3% of problems; generated solutions with at least one code smell had an average estimated remediation time of 9.1 minutes. The benchmark evaluates validity, correctness, security, reliability, and maintainability of generated outputs, rather than the quality of work produced by developers with particular experience histories.[14]

**For developers with 2–5 years versus 10+ years of experience, the defensible conclusion is not that inline Copilot produces different code quality, but that experience changes perceived value, acceptance, and likely review effort.** Enterprise interfaces should consequently couple acceptance with visible validation pathways—tests, diagnostics, and easy inspection—rather than treating an accepted completion as verified code.[63][1]

The ANZ Bank corporate Copilot study, conducted from mid-June through the end of July 2023 with more than 100 engineers, adds code-quality measures from controlled Python algorithmic challenges. Its paired analysis found fewer bugs for the Copilot group than the control group (p=0.033) and fewer code smells (p=0.007), both across 17 observations. The Copilot group’s unit-test success ratio was 12.86% higher, but the reported p value was 0.060; SonarQube produced only one non-zero vulnerability data point.[82]

ANZ’s self-reported Python-proficiency grouping found completion-time improvements of 52.27% for Beginner participants, 41.6% for Intermediate participants, and 40.48% for Advanced participants. The study combined Novice with Beginner and Expert with Advanced. These proficiency results do not create the requested 2–5-year and 10+-year code-quality cohorts.[82]

The April 2022 novice-programmer study adds a qualitative correctness mechanism: participants were often observed adapting incorrect Copilot code, which took them further from a correct solution into a debugging rabbithole. It also reports that novices may struggle to identify whether a Copilot suggestion is correct.[81]

Enterprise and project-level findings do not all show quality gains. In Okta’s field study, Copilot adoption produced no statistically significant change in lines-of-code measures, and the authors’ selected organizational-output metrics showed no statistically significant increase in monthly PR count. A generalized synthetic-control study separately estimated 5.9% higher project-level code contributions after Copilot adoption, no code-quality change, and an 8% increase in coordination time.[84][91]

Pearce and colleagues’ security evaluation found that participants with AI-assistant access wrote less secure code than controls on four of five programming tasks and were more likely to believe that their code was secure.[92] The evaluation identified unsafe library choices or use, missed edge cases, and inadequate input sanitization as mechanisms for these vulnerabilities.[93] This is a code-security concern, not a measured Copilot inline-suggestion effect for either the 2–5-year or 10+-year cohort.[92]

### Synthesis

Copilot inline completion supports flow when it behaves as enhanced autocomplete: the developer has a plan, the proposed code is short, and the completion fits the current logical unit. Aggregate users report flow benefits, but long always-on multi-line suggestions can interrupt typing and lead developers to disable the feature; first-time novice users also reported that the continuing stream of unprompted suggestions disrupted thinking and led to shepherding and drifting.[64][3][78][81]

Across the requested 2–5-year and 10+-year bands, no direct study measures either flow-state or code-quality differences from Copilot inline suggestions. Broader studies point toward greater reported benefit and acceptance among less-experienced developers, while experienced developers report less perceived code-quality benefit and, in the broader expert grouping, better outcomes with automatic suggestions disabled. The strongest measured quality gains apply to an overall sample of developers with at least five years’ experience.[57][63][90][80]

1. Enable proactive, one-line or small-unit completions during predictable, repetitive implementation.
2. Suppress or defer long completions during continuous typing and established-plan work.
3. Offer on-demand generation, alternatives, and validation tools for exploration, debugging, and code requiring careful review.

## Tabnine multi-line predictions

Tabnine presents adaptive inline completions while developers type. Its prediction span runs from a token or line to the next code block or a full-function implementation, using current-file context, project structure, and coding patterns.[19][27]

### How do Tabnine's multi-line predictions affect developer flow state across

The authors’ controlled study reports average recommended snippet lengths of 1.97 lines for GitHub Copilot, 1.38 lines for Tabnine, and 1.51 lines for CodeGeeX. The authors identified Tabnine’s rapid response and generation of new recommendations with every keystroke as a possible reason suggestions went unnoticed and acceptance was lower; these observations do not isolate longer multi-line predictions.[94] The Tabnine IntelliJ README describes Tabnine Pro: “As you type, Tabnine Pro serves whole-line, full-function, and even natural language to code completions.” It says whole-line completion accepts an entire line with one keystroke, full-function completion generates a function without exiting the editor, and natural-language-to-code completion lets a developer describe the wanted script or function.[94][30]

Judgment — **No measured Tabnine flow-state result separates developers with 2–5 years’ experience from those with 10+ years’ experience.** The comparison remains unsettled; it requires the same flow measure, tasks, languages, and prediction configuration across both cohorts. Experience can matter for AI assistants generally: one study reports that assistance could increase completion time for experienced participants, depending on task type, but it neither identifies Tabnine nor uses the requested year bands.[95]

The design implication is to treat uninterrupted inline presentation as an interaction property, not proof that either experience cohort remains in flow.

A controlled study of 27 computer-science students included 18 participants with 2–5 years of Python experience and nine with over five years; it examined ACATs and found that effects varied by task and experience, and that highly experienced participants could be hindered on particular tasks.[94] The study’s Tabnine observations link rapid, every-keystroke recommendation generation to suggestions remaining unnoticed and to lower acceptance.[94]

Across GitHub Copilot, Tabnine, and CodeGeeX in that study, edited-line completion was the most frequent recommendation method despite low acceptance, while the two multi-line recommendation methods occurred less frequently. For each ACAT, accepted snippets were longer than rejected snippets. In the Management System Development task, accepted snippets were significantly longer than in the other two tasks.[94]

A Google Cloud customer account reports that CI&T developers accepted 90% of Tabnine’s single-line suggestions and attributes an 11% productivity increase across projects to Tabnine use; it does not specify the cohort size, reporting period, task mix, or acceptance definition.[148]

### How do Tabnine's multi-line predictions affect code quality across developers

Across selected reviewer exercises, Tabnine’s suggestions were competitive for boilerplate and idiomatic patterns, while multi-line suggestions were good for boilerplate but variable for complex logic; complex multi-file operations sometimes required manual adjustment.[27] Other selected-task observations included out-of-scope code, nonexistent database fields, irrelevant tests, indentation errors, and an initially non-compiling C++ quicksort response; a follow-up request produced a correct partition-function prototype.[27][96][29]

Judgment — **No measured code-quality effect of Tabnine multi-line predictions is established for developers with 2–5 years’ experience, and none is established for developers with 10+ years’ experience.** The selected reviewer exercises report no aggregate code-quality metric or experience-cohort result.[27][96][29]

For enterprise use, this makes multi-line prediction appropriate for readily verifiable boilerplate and familiar idioms, while complex logic and multi-file changes need explicit review before incorporation.

Completion acceptance and fewer keystrokes are not valid proxies for code quality.

The ACAT study scored each task out of three points by allocating scores to implementation steps and comparing assisted with unassisted work. Its average task-score differences were 1.61 for GitHub Copilot, 0.85 for Tabnine, and 0.90 for CodeGeeX.[94]

In a June 2023 experiment on 100 generated Java methods, Tabnine generated 13 correct methods (13%). The study classified methods as invalid when they failed to compile, semantically incorrect when they failed at least one available test, plausibly correct when they passed available tests, and correct when manual inspection judged their semantic behavior equivalent to the developer implementation, allowing defensive checks.[97]

For the 45 external-dependent Java methods, defined as methods with at least one dependency on a method in another project class, Tabnine generated 11% correct methods; the corresponding rates were 15% for Copilot, 11% for ChatGPT, and 4% for Bard.[97]

### Synthesis

Tabnine is an inline, variable-length prediction system rather than a single-line-only completer.[19] Its available observations support a task-complexity distinction: boilerplate can be accurate, whereas semantic, multi-file, and complex-logic work can require correction.[27] The same observations do not justify treating smooth presentation, acceptance, or apparent accuracy as evidence of sustained flow or high-quality output for either requested experience cohort.[27][96][29]

Judgment — **Design the interface to keep short, low-risk continuations inline, but pair longer predictions with conspicuous review affordances and avoid assuming seniority alone predicts benefit.**

## Amazon CodeWhisperer comment-to-code generation

CodeWhisperer’s distinctive mode is comment-to-code generation: a developer writes a natural-language task description and the IDE recommends a snippet, function, or logical block using that comment and the surrounding code as context. This matters for flow because the interaction can replace an API lookup or boilerplate-writing episode, but it can also impose a review and refinement episode before code is safe to retain.[55][6][32]

### How does Amazon CodeWhisperer's comment-to-code generation affect developer flow state

Amazon’s one-sprint CodeWhisperer comparison reports that users spent more time in flow and that inexperienced engineers received a larger boost than more experienced engineers. It also reports faster task completion—20–50% faster in the sprint comparison, and 57% faster with a 27% higher task-success likelihood in a preview productivity challenge.[98]

A qualitative AWS disaster-recovery-team account complements that pattern: senior software development engineers reportedly concentrated longer when CodeWhisperer took over basic, time-consuming work, while engineers less familiar with Boto3 APIs avoided repeated switches to API specifications and back to the IDE. API familiarity, rather than years in the profession, is the relevant distinction in that account.[99]

The reported inexperienced-versus-more-experienced difference does not map to the requested 2–5-year and 10+-year cohorts because Amazon does not define either group in years. The 2025 CodeWhisperer interaction study likewise cannot supply that comparison: it involved two groups of 10 Computer Science students—undergraduates in the first study and one undergraduate plus nine graduate students in the second—and measured interaction traces and retained content rather than flow state.[98][100]

That study does show a workflow relevant to flow design: participants commonly accepted end-of-line comment or syntax completions and then refined them, rather than treating acceptance as final adoption.[100] **For enterprise interfaces, the supported flow mechanism is removal of a concrete lookup or routine-implementation burden, not seniority measured in years.**[99][101]

The 2025 CodeWhisperer study authors recorded complete generated insertions in 6.88% of interactions in Task 1, 5.62% in Task 2, and 3.82% in Task 3; the share fell as task difficulty increased.[102] They also recorded IDE focus and unfocus events, including episodes in which developers consulted outside sources or paused to read and think rather than continuing to accept end-of-line suggestions.[102] The authors observed developers using Stack Overflow and ChatGPT when CodeWhisperer suggestions were insufficient and recommended integration with trusted search or documentation sources.[102]

A product-comparison report gives CodeWhisperer a real-world suggestion latency of 0.5–1.0 seconds, with higher spikes, and reports 27–31% overall acceptance, with higher acceptance in AWS-integration scenarios.[103] The same report characterizes developers with 2–5 years of experience as tolerating delays below 500 ms and valuing explanations and proactive engagement, and developers with 10+ years as sensitive to 100–250 ms latency and preferring explicit or triggered suggestions.[103]

A 2026 longitudinal-study literature review reports that whether AI coding assistance supports or disrupts flow depends on the task rather than the tool alone.[104] In its matched sample of 94 developers, flow-state ratings changed from 3.54 to 3.36, a −0.18 change; 27% reported improved flow and 35% reported reduced flow.[104]

## Where findings conflict: timing, tasks, and trust

Suggestion timing is not a cosmetic setting. It determines whether an AI completion acts as a low-friction continuation of an intended action or as an interruption that forces the developer to abandon their current mental plan and evaluate generated code. The evidence also separates acceptance from value: a suggestion can be accepted quickly yet be poorly understood, hard to debug, or later removed.

### How do flow-state findings compare among GitHub Copilot's inline suggestions

GitHub Copilot’s inline ghost-text interaction is flow-compatible in acceleration mode: the developer already knows the next action and uses a completion to execute it faster. In exploration mode, the developer is uncertain, explicitly prompts the tool, considers alternatives, and validates more extensively; interactions are slower and deliberate. Developers moved between these modes during a task.[3][1]

**Long unsolicited completions break flow when the developer is already driving.** Copilot participants reported stopping mid-typing to read and judge multi-line suggestions, rather than transmitting an already-formed plan into code. Some dismissed long suggestions, and three participants had disabled Copilot after months of use partly because its always-on suggestions were distracting. The authors consequently recommend short, high-confidence suggestions in acceleration mode.[1][3]

This creates an apparent conflict with positive Copilot flow perceptions: a reported GitHub survey found that 73% said Copilot helped them stay in flow and 87% said it reduced the mental effort of repetitive tasks, while another reported 88% could maintain flow with less frustration.[110] These are broad self-reports, whereas the grounded study identifies a specific failure mode: lengthy, unexpected inline completions arriving during fluent typing. Together, they support a mode- and presentation-dependent result rather than a uniform flow benefit.[110][1]

The requested 2–5-year versus 10+-year comparison has not been measured for Copilot inline suggestions, Tabnine multi-line predictions, or CodeWhisperer comment-to-code generation. The Copilot study involved 20 participants and classified target-language experience as Never, Occasional, Regular, or Professional rather than years of employment; its more language-expert participants spent more time accelerating.[1][3][79] Years of experience are also an imperfect proxy for expertise because software expertise is task-specific and shaped by deliberate practice and individual differences.[101]

Amazon’s one-sprint CodeWhisperer presentation reported more time in flow and a larger boost for inexperienced engineers than for more experienced engineers, but did not define those groups in years. No equivalent Tabnine multi-line-prediction flow outcome is documented here.[98][111] Thus, the flow comparison supports a clear interface decision: detect interaction state, not tenure alone, and keep proactive inline output short when the developer’s next move is evident.

### What does research reveal about optimal suggestion latency thresholds in

Research reports feasible implementation latencies, not a universal latency at which flow, acceptance, or code quality improves. JetBrains’ fall-2023 Python EAP A/B test reported 150 ms average CPU time from Full Line Code Completion invocation to display; cache reuse occurred in over 90% of completion events.[24] JetBrains described 150 ms as suitable for perception, but this is a deployment metric rather than a tested flow threshold.[24]

Google reported approximately 40 ms median ML serving time in a parallel completion system and used a less-than-100-ms end-to-end budget for semantic checks. This ensured the ML path added no latency to completions; it does not establish that 40 ms or 100 ms is optimal for every developer or suggestion.[113] Code4Me V2 separately reports 200 ms average completion latency, and JetBrains states below-200-ms latency for most in-editor-completion use cases.[114][73]

A Copilot interaction example describes suggestions appearing after a one-second typing pause, with a short expected completion accepted in a fraction of a second without disrupting flow. That one second is a trigger after inactivity, not system response latency. Copilot can also be configured either to request inline suggestions on every keystroke or only after a typing pause, demonstrating that trigger delay and generation/display latency are distinct variables.[1][115]

GitHub’s later inline-suggestion experiments found that invoking the model immediately while a developer was still typing did not worsen experience, but immediately displaying cached suggestions could be disruptive. A slight display delay better matched typing rhythm and supported flow.[131]

GitHub reported that invoking its inline model immediately while a developer was still typing did not worsen the measured experience, whereas immediately displaying a cached result did. It selected a slight delay before display, separating when inference starts from when ghost text becomes visible.[131]

In GitHub client-side experiments, invoking the model immediately during typing did not worsen the experience, but immediately displaying cached suggestions was disruptive; the team chose a slight delay before presentation.[131]

**Latency should be designed as suggestion utility, not as a fixed millisecond target.** The display model defines utility as expected time saved by showing rather than withholding a suggestion, including generation latency, verification, editing, and the time to write code manually. Lower latency and higher predicted acceptance make a suggestion more likely to be useful, but the decision depends on what must be checked and repaired.[116]

Copilot’s extension records a heuristic opportunity to show a completion separately from when it is shown and accepted, and it may abandon a request still in flight if the developer moves on before the response is ready.[63] It can request completions at arbitrary code positions rather than only after an explicit syntax trigger such as typing a period.[130]

For automatic single-line completion, latency affects feedback rate because a developer may type again before a completion arrives. Longer multi-line output can justify somewhat more delay if its extra quality offsets the wait.[117][118] This rules out treating 150 ms, 200 ms, or one second as a universal design rule: maintain a low-latency path for proactive micro-completions, while letting explicit, longer requests wait longer for richer context and validation.

Google’s production measurements report acceptance rates only for suggestions visible for more than 750 ms: 25% for single-line completions and 34% for multi-line completions. The greater-than-750-ms condition is visibility duration, not generation or display latency.[113]

Miller’s 1968 response-time landmarks are approximately 100 ms for an immediate-feeling response, 1,000 ms for uninterrupted mental flow, and 10,000 ms before attention may wander. These are general interactive-system heuristics, not code-completion acceptance or quality thresholds.

### How do suggestion acceptance rates relate to interruption timing during

**Debugging.** No accepted/shown numerator and denominator is paired with interruption-display timing for debugging.[4] A 2025 proactive programming-support study recorded 1,004 human–AI interaction episodes: debugging accounted for 26.4%, while four debugging disruptions accounted for 7.27% of recorded disruptions.[1][100] These are interaction and disruption shares, not acceptance rates.[4]

Developers often wanted assistance after execution produced an error because execution provides both an explicit turn-taking point and actionable program output. Preferences split, however: some participants welcomed proactive error feedback, while others expected it to introduce more errors and complicate debugging.[5] General interruption research reinforces restraint: high-dominance on-screen interruptions increased code-comprehension time, and interruptions during code writing were associated with greater stress than during other tasks.[119][80]

Behavioral filtering offers a general acceptance result, not a debugging rule. In one deployment, filtering suggestion requests through developer-behavior telemetry raised acceptance among issued suggestions from 18.4%—427 accepted of 2,319 suggestion events—to 34.2%—486 accepted of 1,422 issued suggestions. Its definition counted passive rejection after 30 seconds of inactivity, so this rate should not be equated automatically with other products’ acceptance metrics.[120]

The debugging decision follows directly: offer a compact, non-blocking assist after a run-time error or failed test, but make it immediately dismissible and retain an on-demand route. That uses a natural handoff without assuming that debugging developers uniformly welcome proactive intervention.

How do suggestion acceptance rates relate to interruption timing during new feature development

The Copilot grounded-theory study focused on code authorship rather than debugging, testing, or feature-versus-maintenance task comparisons, and the CodeWhisperer task study supplies no feature/development timing split.[1][100]

Across 398 proactive interventions in the 2025 programming-support study, 212 interactions (53.3%) led to effective engagement, 48 (12.1%) were disruptions, and 138 (34.7%) were ignored or unnoticed. Effective engagement included adapting AI changes or responding to an agent message; these are proactive-agent engagement and disruption measures, not suggestion-acceptance rates.[4] Implementation—the closest recorded process category to feature work—accounted for 18 disruptions, or 32.7% of all disruptions.[4]

Copilot telemetry has reported more than one-fifth of suggestions accepted overall, but this cannot be converted into a feature-development acceptance rate or a recommendation to interrupt implementation.[121] The strongest timing implication is instead selective proactivity: show short, likely-useful continuations when behavior indicates acceleration; suppress or defer uncertain, lengthy, or low-likelihood suggestions while the developer is actively constructing a feature. The implementation-stage disruption result makes on-demand access particularly important for design-heavy or novel feature work.[1][4]

In the behavior-filtering deployment, acceptance among suggestions that were issued rose by 15.8 percentage points, from 18.4% to 34.2%—an 85.9% relative increase. This quantifies the potential value of withholding low-receptivity suggestions before they enter the developer’s attention.[120]

Within the proactive-programming-support study, implementation represented 38.2% of human–AI interactions but 32.7% of disruptions, a disruption-to-interaction representation ratio of 0.86; debugging represented 26.4% of interactions but 7.27% of disruptions, a corresponding ratio of 0.28. The observed disruption mix was therefore more concentrated in implementation than debugging relative to each activity’s share of interactions.[4]

Parnin and Rugaber (2010, Software Quality Journal, 'Resumption strategies for interrupted programming tasks')’s 2011 study, 《Resumption Strategies for Interrupted Programming Tasks》, found that resuming programming work requires reconstruction of task context rather than simply returning to the cursor.[65] This makes active diagnostic work—where a developer is maintaining a causal hypothesis, program state, and search history—a particularly interruption-sensitive state.

Peng et al.’s 2023 controlled study, 《The Impact of AI on Developer Productivity: Evidence from GitHub Copilot》, found that participants with Copilot completed a bounded programming task faster than control participants. The result concerns task-completion time rather than suggestion acceptance, display timing, or enterprise feature work.

### How does explanation availability for AI suggestions impact developer trust

Trust calibration is reliance aligned with actual performance: validated trust means accepting correct suggestions, while discerning trust means rejecting incorrect ones. A plausible explanation can accompany an incorrect suggestion; calibration therefore requires examining acceptance of correct code and rejection of incorrect code, not confidence, high acceptance, or stated trust alone.[122] This distinction matters because participants given AI assistance in a security-programming study more often produced insecure solutions on four of five tasks while believing their answers were more secure; 87% of secure responses required significant user edits.[93][92]

Available evidence does not show that attaching a natural-language explanation to a code suggestion causes developers to accept correct code more often or reject incorrect code more often. Copilot participants asked for information showing what alternatives do differently and why one should be chosen. CodeWhisperer provides provenance information—repository URL, file reference, and licence—for suggestions resembling open-source code, enabling review before incorporation. These are useful comprehension and governance features, but not measured trust-calibration effects.[3][6][32]

In a three-week Microsoft workplace study summarized by DX, about 20% of participating engineers initially trusted AI-generated code and 30% considered AI tools reliable. Developers reported time savings on boilerplate and repetitive work, but plausible incorrect outputs and validation time could offset those gains.[141]

Copilot’s ordinary inline suggestion supplies proposed code in context but does not normally explain why that code is appropriate.[23]

Roughly 95% of surveyed Accenture developers said they learned from Copilot suggestions; that reported learning does not measure the effect of explanations on calibrated trust.[146]

**Inspectable validation has stronger calibration-relevant support than explanatory prose alone.** In a 17-participant live-programming comparison, six participants without projection boxes misjudged their solution’s correctness, compared with none using projection boxes. Participants reported that live runtime-value displays helped them preview and compare alternatives, and the intervention reduced over- and under-reliance on tasks amenable to execution-based validation.[17][78]

Confidence signals also require caution. Across more than 24 million real-world interactions, a general Platt-scaled post-hoc confidence calibration model did not improve confidence-signal reliability on average; dynamically personalized calibration could work, depending substantially on interaction data per user.[123] More generally, explanation research is mixed: chain-of-thought explanations reduced under-trust and increased validated trust in one study, but did not improve discerning trust or error detection; when outcome feedback was introduced, explanation effects did not hold.[122]

The interface implication is to offer explanations and provenance on demand, with concise cues and optional detail, while making verification executable where possible: tests, static checks, previews, runtime values, and retained-code feedback. Explanations should support a review decision rather than present an authoritative rationale that substitutes for it.[1][124]

Vaithilingam, Zhang, and Glassman’s 2022 study, 《Expectation vs. Experience: Evaluating the Usability of Code Generation Tools Powered by Large Language Models》, documents that developers can have difficulty evaluating generated code and that actual use can differ from prior expectations. This supports measuring inspection, error detection, later edits, and final code quality alongside trust ratings.

### Synthesis

Across timing, tasks, and trust, the evidence favors state-sensitive assistance over a universal proactive policy. Short, high-confidence inline completions fit acceleration because they can be assessed without breaking typing flow; long unsolicited blocks impose reading and validation costs. Debugging creates a useful but preference-sensitive handoff after execution errors, whereas implementation carries a recorded disruption risk and should retain on-demand control.[1][5][4]

No product-by-tenure comparison supports different timing rules for 2–5-year versus 10+-year developers. Tenure should therefore configure defaults and explanation depth only tentatively; observed interaction state, language familiarity, task novelty, and verification cost are more immediate signals. Low response time enables proactive micro-completions, but no millisecond value is an empirically established optimum. Finally, acceptance is not calibrated trust: favor suggestions that are easy to validate and measure retained, tested outcomes as well as acceptance.[101][116][24][78][92]

For **Copilot**, the strongest broad experience pattern is not a 2–5 versus 10+ result. In the three-company field experiments, less-experienced developers had higher adoption and greater productivity gains. Microsoft’s own tenure split was at an undisclosed median between 2 and 4 years, not at 10 years; its short-tenure group adopted Copilot at 81.6% versus 72.1% for the long-tenure group, and accepted 25.4% versus 24.3% of suggestions, a difference reported with p=0.14. The reported output estimates were larger for short-tenure than long-tenure developers—27% to 39% versus 8% to 13%—but the authors describe those subgroup estimates as noisy and not conventionally statistically significant.[59][15]

Microsoft and partner field-experiment reporting also found that short-tenured and junior developers continued using Copilot more often than more-experienced developers; it did not give continued-use rates for the requested 2–5-year and 10+-year bands. [142]

That evidence is useful for an enterprise interface because it rejects a one-size-fits-all policy. It does not, however, allow a product team to label a developer with four years of experience as equivalent to a field-study short-tenure developer, nor to label a 12-year developer as equivalent to the study’s long-tenure group. Tenure at one employer, job level, years of professional coding, language expertise, task familiarity, and prior AI use are different variables. In Copilot’s survey and telemetry study, junior developers tended to accept more suggestions and report greater productivity gains, yet the association between acceptance and perceived productivity persisted within every experience group.[63][15]

The Copilot quality record also cannot supply the requested cohort comparison. A controlled quality study recruited 202 developers with at least five years of experience, randomly assigning 104 to Copilot and 98 to no-AI access. In its bounded API task, Copilot-access developers were 53.2% more likely to pass all 10 unit tests, blind reviewers were 5% more likely to approve Copilot-authored code, and reviewers rated it higher for readability, reliability, maintainability, and conciseness. These are direct Copilot quality results for that study population overall, not separate evidence for 2–5 or 10+ years.[90]

The field experiments use a narrower quality proxy: build success rate. They find no negative effect on build success at Microsoft, while the Accenture estimate is negative; the report also warns that build success is not a complete account of code quality. Separately, a 21-person preliminary experiment found more Copilot-assisted lines but more subsequent deletion, while a user study found Copilot-generated code comparable to human-authored code in readability and complexity. These results concern different quality constructs—compilation, revision, readability, and complexity—so they should remain separate rather than be converted into one quality score.[15][28]

For **CodeWhisperer**, the comparative benchmark result is often mistaken for a developer-outcome result. Yetiştiren et al.’s 2023 HumanEval study manually generated solutions for 164 Python problems in Visual Studio Code and evaluated validity, correctness, security, reliability, and maintainability. It reports correct-code rates of 46.3% for Copilot and 31.1% for CodeWhisperer. Among generated solutions containing code smells, estimated remediation time averaged 9.1 minutes for Copilot and 5.6 minutes for CodeWhisperer; among identified bugs, estimated elimination time averaged 15 minutes for Copilot and five minutes for CodeWhisperer. The authors caution that repair-time estimates alone cannot rank bug-free generation capability.[14]

Those figures answer a narrow question: how the tested versions’ generated artifacts performed on HumanEval. They do not answer whether an engineer accepts a comment-to-code suggestion at the right moment, understands it, stays in flow, or produces better enterprise code after reviewing and integrating it. The benchmark also covers only Python and uses an average of 7.7 test cases per problem.[14]

The CodeWhisperer interaction study provides a different signal. Two studies of 10 students each observed natural-language comments such as Create, Write, and Make being used to direct CodeWhisperer. Suggested code-line retention increased across three tasks from 39% to 58% to either 65% or 66%; comment retention rose from 38% to 58% to 88%. Complete generated insertions became less common as task difficulty rose, from 6.88% to 5.62% to 3.82%. That is evidence that users refine, retain, and increasingly rely on generated content across those tasks, not an acceptance, quality, flow, or professional-experience result.[100]

For **Tabnine**, it is important not to fill the gap with Copilot or general completion evidence. Tabnine documents three relevant forms: on-the-fly completions, full-function completions, and natural-language-comment-to-code completion. It describes suggestions adapting to context as the developer types, and says that a user can continue typing to obtain alternatives. Its documentation also says a natural-language comment can declare the desired task and trigger code on the following line. Those are presentation and control affordances, not comparative measurements of flow or quality.[18][30]

Tabnine does have vendor and review signals that may inform product instrumentation but cannot establish the requested outcomes. A Tabnine executive said codebase awareness of open IDE context increased suggestion acceptance by 40%, without disclosing the denominator, period, or experience breakdown. A review reported that complex multi-file operations sometimes needed manual adjustment. An older vendor-authored comparison rated Tabnine as fast but described irrelevant, malformed, or semantically incorrect suggestions in selected examples; its own author called the assessment subjective and disclosed that it was written by Codeium’s team.[111][27][96]

The decision this makes possible is a disciplined one: treat Copilot’s experience-sensitive interaction findings, CodeWhisperer’s output-quality benchmarks, and Tabnine’s presentation documentation as separate evidence streams, not as a six-cell product ranking.

The same discipline applies to flow. Copilot users have reported flow benefits: GitHub’s survey found 73% said Copilot helped them stay in flow and 87% said it preserved mental effort during repetitive work; an Accenture survey found a majority said they could maintain flow while using Copilot. These are useful perceptions of the overall experience, but they do not identify suggestion timing, exact experience bands, or an objective flow-state measure.[64][125]

In an Accenture evaluation, 94% of respondents reported that Copilot helped them remain in flow and spend less effort on repetitive work.[146]

A more direct mode comparison comes from a 2026 quasi-experiment of automatic versus disabled/on-demand Copilot suggestions with novice and expert profiles. Novices had median actual productivity of 0.46 with automatic suggestions enabled and 0.15 with them disabled; experts showed the reverse, 0.41 enabled and 0.75 disabled. Experts also reported significantly higher distraction with automatic suggestions and frequently changed more than 50% of accepted suggestions; novices usually changed less than 30%. The expert group included industry developers with at least three years of programming experience and Java experience ranging from three to over 15 years, so it overlaps both requested cohorts rather than separating them.[80]

This study is especially important because it distinguishes accepting a suggestion from receiving value from it. Acceptance can be followed by costly repair, and a low acceptance rate can still conceal useful ideas that a developer chooses not to insert verbatim. GitHub’s telemetry work finds acceptance rate is the strongest predictor of perceived productivity, but its own conditional-display research warns that optimizing display only for acceptance can reduce suggestion quality.[63][48]

Judgment — An enterprise evaluation should define success as calibrated contribution, not raw acceptance: an accepted suggestion should be checked for retained code, later revision or reversion, build and test outcomes, review outcomes, security findings, and the developer’s reported interruption burden. This prevents an interface from winning by proposing only short, easy, low-value text or by making acceptance effortless while pushing validation and repair downstream.

Proposed enterprise validation test — Randomize proactive versus requested Copilot display and the display moment while holding candidate suggestions comparable. Stratify developers into 2–5-year and 10+-year experience cohorts and tasks into debugging and new-feature work. Record suggestions shown, accepted, edited, retained, tested, and reviewed, alongside flow and resumption outcomes. This test evaluates the automatic-versus-on-demand interaction contrast, implementation and debugging interaction stages, and suggestion utility as a function of acceptance and latency.[80][4][116][24]

No head-to-head study compares the three named presentation modes across the two requested experience bands. The literature also lacks a common flow instrument and a shared quality rubric covering correctness, security, maintainability, and review burden across those products.

For both the 2–5-year and 10+-year cohorts, direct flow-state evidence is unavailable for Copilot inline suggestions, Tabnine multi-line predictions, and CodeWhisperer comment-to-code generation.[57] For both cohorts, developer code-quality evidence is indirect for Copilot, Tabnine, and CodeWhisperer because the available quality measures are not separated into the requested experience bands and presentation modes.[18][94][57][14]

### When should suggestions appear proactively?

Proactive presentation means the system offers a completion without an explicit request. It is valuable when it removes an unnecessary request-and-wait cycle at a moment the developer can use the help. It is harmful when it competes with active reasoning, creates verification work, or makes the developer react to the tool rather than drive the task.

**The evidence favors conditional proactivity: show a compact, relevant suggestion at a natural breakpoint or a moment of likely receptivity, not whenever a completion is available.** Microsoft’s workday research found interruptions and distractions harmed focus or planned work in 13.8% of 4,005 explanatory responses, and developers described the need for a continuous work block. Programmer-interruption research similarly found 83% of surveyed developers thought task switching harmed primary-task performance when background knowledge was shallow or they were still learning.[44][43]

A natural breakpoint is an observable transition that gives a developer a chance to assess new information: finishing a multi-line change, writing an intent-bearing comment, running a program, committing, or reaching a reviewable task boundary. In a five-day field study of 15 developers, interventions at workflow boundaries such as post-commit achieved 52% engagement, while mid-task interventions such as after a declined edit were dismissed 62% of the time. The study examined 229 AI interventions across 5,732 interaction points, so its result is about receptivity to the proactive feature studied, not a universal completion-acceptance rate.[126]

The same study found that well-timed proactive suggestions took 45.4 seconds to interpret, compared with 101.4 seconds for reactive suggestions. This does not mean reactive help is intrinsically worse: it means a proactive intervention that arrives with the right workflow context can reduce interpretation time. That distinction matters for interface design. The timing policy should predict whether the system has a concrete, contextually usable contribution, rather than merely detect that the developer has paused.[126]

Codellaborator’s 18-participant study adds practical timing triggers. Across 398 proactive interventions, 53.3% led to effective engagement, 12.1% were disruptions, and 34.7% were ignored or unnoticed. Multi-line change, user-written comment, and program execution were the most effective triggers, with engagement rates of 73.1%, 69.2%, and 66.7%, respectively. By contrast, code-block completion alone produced excessive affirmatory messages, and users ignored around 50% of those signals.[4][5]

Program execution is a particularly useful breakpoint for debugging because it creates explicit turn-taking and produces evidence—an error, output, failing test, or stack trace—that an assistant can interpret. Participants in the same study often wanted help after execution errors, although preferences differed: some welcomed proactive feedback while others feared it would add errors and complicate debugging. The right default is therefore a quiet, inspectable diagnostic affordance after an error, with the content expanded only when the developer asks or has enabled that level of help.[5]

Proactivity also fits repetitive, locally constrained authoring. Copilot’s qualitative research distinguishes **acceleration**, where the developer has well-formed intent and uses assistance in small logical units, from **exploration**, where suggestions help plan, find APIs, or consider alternatives. Long suggestions can break flow during acceleration because they take time to read and evaluate. This supports short inline completions for predictable boilerplate, syntax, local transformations, and repeated patterns—but not unsolicited large blocks during active implementation.[28]

The system should also use a display controller. Conditional suggestion display from human feedback, or CDHF, uses models predicting whether recommended code will be accepted and selectively hides suggestions. In retrospective Copilot telemetry from 535 Python users over two weeks—4,749 sessions, nearly 1,675 hours, 168,807 shown events, and 33,523 accept events—the observed acceptance rate was 21.4%, which the authors explicitly say is not Copilot’s average rate. CDHF could retrospectively hide 25.3% of shown suggestions while guaranteeing that 94.7% of the hidden suggestions would have been rejected; with no latency constraint, it could hide 52.9% while guaranteeing 91.3% would have been rejected.[48][116]

A behavioral-telemetry deployment points in the same direction. After filtering suppressed 768 of 2,190 incoming suggestion requests and issued 1,422 suggestions, acceptance among issued suggestions rose from 18.4% before filtering to 34.2% after filtering. The study also associates sustained high-speed typing with focus or flow and lower receptivity, while slower or fragmented typing coincided with greater acceptance likelihood. Its active deployment involved nine sustained experienced users, so the exact rate should not be generalized; the interface principle is to suppress unnecessary inference and display during evident focused typing.[120]

Judgment — Implement a **receptivity controller** with three gates: first, relevance and likely value from code context; second, an interruptibility signal from activity and task state; third, a presentation-cost test that rejects large or uncertain suggestions from the inline channel. The controller should treat a user-written comment, a completed multi-line edit, a compiler or test result, and an explicit pause after execution as stronger evidence than code-block completion alone.

There is no validated universal suggestion-latency threshold in milliseconds. GitHub documents latency, time-to-first token, acceptance, shown rate, edit quality, retention, and accepted-and-retained characters as evaluation metrics, but it publishes no optimal latency value. Visual Studio lets users choose a pause-before-showing debounce for Copilot, but gives no duration. A user proposed 400 ms; that is a preference proposal, not a measured optimum.[25][23][115][127]

The often-cited 750 ms figure is also not a generation-latency threshold. Google’s production completion tables report acceptance for suggestions visible for more than 750 ms: 25% for single-line completion and 34% for multi-line completion, with 21 and 73 average characters per accept respectively. Visibility duration says that a developer had time to see a suggestion; it does not say the model should wait 750 ms before presenting one.[113]

Judgment — Use latency as a budget, not a universal trigger: begin speculative generation while the developer types or at an inferred pause, but render only when the receptivity controller admits it. Measure time-to-first-token and time-to-complete-suggestion separately from display timing. A fast irrelevant interruption remains an interruption; a slightly delayed completion that appears at a useful boundary can have greater value.

In the five-day proactive-IDE study, well-timed proactive suggestions took 55.2% less time to interpret than reactive suggestions: 45.4 seconds rather than 101.4 seconds. This quantifies the interaction-time benefit associated with the study’s well-timed proactive interventions.[126]

Present proactive completions as visually subordinate ghost text that ordinary continued typing can overwrite or dismiss. Do not steal editor focus, insert code automatically, use sound, or open attention-demanding pop-ups for an unsolicited completion.

### When should suggestions appear on-demand?

On-demand assistance means the developer deliberately asks for a suggestion through a shortcut, comment, selection, chat request, or alternative-suggestion control. Its main value is agency: the developer chooses when to incur attention, evaluation, and possible editing costs. Its main cost is that the developer must decide when the assistant might help and express the request.

**The evidence favors on-demand presentation during concentrated implementation, uncertain relevance, complex generation, and debugging before a clear error-driven breakpoint.** Microsoft’s developer workday research identifies agency—the ability to organize work and avoid externally imposed disruption—as important to developers. Copilot research likewise finds that manually deciding when to request help requires a mental model of when AI will help and creates a cognitive burden, so on-demand invocation must be lightweight rather than a prompt-writing exercise.[44][28]

The 2026 Copilot automatic-versus-on-demand experiment provides the clearest direct design result. Experts had higher actual productivity when automatic suggestions were disabled and assistance was requested on demand, and they reported higher distraction and higher concern about code quality when automatic suggestions were enabled. Novices showed the opposite productivity pattern and were less likely to see automatic suggestions as intrusive. The appropriate enterprise policy is not to infer that all developers with 2–5 years want automatic suggestions and all with 10+ years want manual ones; it is to offer a visible default that adapts to observed interaction and lets each developer override it.[80]

A developer-written comment is an intent cue that may trigger an automatic suggestion. Tabnine documents comments-to-code completions triggered by real code comments, and CodeWhisperer documents automatic recommendations as developers write code or comments. Deliberate invocation is separate: CodeWhisperer provides a shortcut to force a suggestion, while Copilot provides a manual inline trigger and a separate pane for additional suggestions.[19] Copilot participants described natural-language comment prompts as giving them control because they could state their mental model before seeing the suggestion.[32][22][9] In exploration mode, comment prompts accounted for 57.2% of prompting time, compared with 13.1% in acceleration mode, and use of the multi-suggestion pane increased. This supports comment-led intent expression and deliberately requested alternative panes for architecture, unfamiliar APIs, algorithm selection, new-feature scaffolding, and larger transformations.[3][1][28]

Tabnine’s documented comment-to-code mode lets a developer trigger completion with a real code comment, and CodeWhisperer provides contextual suggestions based on comments written in the IDE. These comment-based routes are automatic suggestion triggers, not inherently on-demand generation. For deliberate generation, expose CodeWhisperer’s force-suggestion shortcut and equivalent explicit request controls; a comment can remain a reviewable specification whether the resulting suggestion appears automatically or is deliberately requested.[19][22][32][9]

Debugging needs a bifurcated policy. Before execution or while tracing a hypothesis through unfamiliar code, unsolicited generated code can distract from problem understanding. After a failed execution, test, build, or static-analysis finding, the system has concrete evidence and may surface a compact diagnostic cue proactively. The developer should then choose whether to request a fix, an explanation, a test, or alternative hypotheses. This matches the observation that participants sought help during debugging after errors, while disagreeing about whether proactive fixes themselves were welcome.[5][128]

The distinction between debugging and new-feature development is therefore one of interruption timing, not a demonstrated task-specific acceptance-rate difference. The supplied research does not report acceptance rates for debugging versus feature development at different interruption moments. It does show that implementation accounted for 38.2% and debugging for 26.4% of recorded human–AI interactions in one proactive-agent study, and that participants wanted different degrees of proactivity at different development stages.[4]

New-feature work should usually begin with an on-demand intent declaration, then move into conditional inline acceleration once the developer’s plan is clear. A feature task often includes planning, unfamiliar APIs, broad context, and multi-file implications, all of which make a quick local completion less reliable. The Grounded Copilot study found tasks involving unfamiliar APIs drove exploration regardless of language expertise or prior Copilot use, whereas a task involving simple business logic led participants toward acceleration.[1]

Judgment — Design a **two-phase feature policy**: first, prompt- or comment-led generation for planning, API discovery, and initial scaffolding; second, short proactive inline completions only after the developer has established a local pattern. This preserves intent control early and minimizes repeated invocation later.

On-demand is also appropriate where acceptance would conceal verification work. In novice Copilot observations, students stopped to decipher large unhelpful blocks, accepted and adapted suggestions they did not understand, and sometimes entered repeated “drifting” cycles. The study recommends shorter suggestions because shorter accepted suggestions were less likely to be changed or deleted. Even though this study concerns beginners rather than the requested 2–5-year cohort, its interface implication applies broadly to large, unsolicited blocks: make them requestable, staged, or reviewable in parts.[129]

Trust calibration requires the same separation between availability and reliance. Calibration means accepting correct assistance and rejecting incorrect assistance, rather than accepting more often. A general trust study defines validated trust as accepting correct AI suggestions and discerning trust as rejecting incorrect ones. It found that outcome feedback may be more diagnostic for calibration than explanation style alone; explanations by themselves did not reliably help people reject incorrect suggestions when trial-by-trial outcome feedback was available. This was a math and design-evaluation study with a simulated 50%-accurate chatbot, so it is a design analogy rather than code-assistant evidence.[122]

Code-assistant evidence supports validation support more directly than explanations. In the LEAP study, six participants without runtime projection boxes misjudged their solution’s correctness, versus none with projection boxes; the authors interpret reduced validation cost as reducing over- and under-reliance. Google’s semantic checks filtered 80% of uncompilable Go suggestions; over six weeks, single-line acceptance rose 1.9-fold in languages with those checks versus 1.3-fold where they were absent, which the authors attribute presumptively to greater trust.[17][113]

Judgment — Offer explanations as optional, task-linked evidence rather than as persuasive prose. For a completion, show the relevant context, referenced APIs or symbols, likely assumptions, test or type-check status, security warnings, and a one-action path to run or inspect validation. For a debugging fix, lead with the failing test, error, or trace evidence that motivated it. This gives developers grounds to accept or reject rather than merely a reason-shaped narrative to trust.

Enterprise telemetry should reflect this policy. JetBrains’ AI Activity and Impact dashboard documents AI contribution rate, code acceptance rate, per-tool code origin, and activity such as chat and suggestion volume, filterable by user, group, and date range. AI contribution rate is AI-committed lines divided by total committed lines. The dashboard’s overall AI code acceptance rate is accepted suggestion lines as a percentage of generated lines across included AI tools and features. For Code completion, accepted lines are lines inserted into the editor, with a partially accepted single line counting as one line and multi-line acceptance counting inserted lines; for Next edit suggestions, accepted lines include inserted and deleted lines and accumulate after every step of a multistep flow. Generated lines are the lines shown as Code completion suggestions or the lines available to insert or delete for Next edit suggestions.[71] These are adoption and retention indicators, not direct measures of flow, code quality, debugging efficacy, or calibrated trust.[71][74]

The dashboard’s scope matters to interpretation. Its contribution and code-origin measures count committed code, excluding discarded exploratory sessions, uncommitted code, Central CLI activity, JetBrains Air activity, and tools outside the JetBrains ecosystem. The deeper contribution and origin view is described as IntelliJ IDEA-only, with version-dependent availability; PyCharm, WebStorm, Rider, and GoLand teams receive adoption and credit numbers rather than the same deeper code-impact view.[74]

The decision this makes possible is to instrument proactive and on-demand paths separately: measure show, ignore, dismiss, accept, edit-after-accept, retain, validate, revert, and review outcomes by task stage, user preference, and experience band—rather than using a team-wide acceptance rate as a proxy for either productivity or quality.

### Synthesis

The evidence supports a negotiated interface, not a permanently proactive or permanently manual one. Conditional proactive suggestions work best when they are short, relevant, easily ignored, and triggered at meaningful boundaries such as comments, multi-line changes, or program execution; proactive interventions at arbitrary code-block completion or during sustained focused typing are more likely to be ignored or disruptive. On-demand controls protect agency and suit exploratory, complex, uncertain, and high-verification work, while imposing an invocation burden that should remain low. Copilot’s novice–expert mode study supports adaptation by user profile, but its cohorts do not equal 2–5 and 10+ years; Tabnine and CodeWhisperer do not fill that comparison gap. Treat explanation availability as secondary to visible validation evidence and outcome feedback.[126][5][120][80][28][122][113]

1. Enable short proactive inline completion only when a receptivity controller predicts high contextual value and low interruption cost.
2. Treat a developer-written comment as an intent cue that can trigger an automatic suggestion; make explicit invocation the default for large or uncertain generations. [19] [32] [3]
3. Trigger optional debugging help after executable evidence—failed tests, build errors, logs, or static-analysis findings—not merely inactivity.
4. Let every developer set automatic, pause-triggered, and manual modes, with immediate dismiss, snooze, and partial-accept controls.
5. Evaluate timing by retained and validated contribution, later rework, review, and defect outcomes—not acceptance rate alone.

### Open questions

No direct comparison establishes flow state, code quality, acceptance rate, or explanation-driven trust calibration for all three named products across 2–5-year versus 10+-year developers, or separately for debugging and new-feature work. No validated millisecond threshold identifies when an AI coding suggestion should appear. These questions would be settled by instrumented, randomized enterprise IDE studies that retain product mode, experience cohort, task type, trigger timing, latency, acceptance and partial acceptance, retained-code quality, defect outcomes, resumption cost, and calibrated reliance as distinct measures. Documented JetBrains AI Assistant deployment metrics also remain unspecified here; a deployment report would need to state the metric definition, population, period, denominator, and outcome rather than treating product availability or adoption as evidence of flow, quality, or trust.
